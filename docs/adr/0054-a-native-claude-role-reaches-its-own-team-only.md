# ADR 0054: The digital-agency lead contacts other sessions with the user's intent


Current status: **Proposed amendment in PR #202**, 2026-10-13, following the maintainer's controlled interactive tests and request to reconsider the scope. The original grant decision is retained below as history, not as the current policy.

## Original decision (superseded)

- **Initial status (superseded by the amendment below)**: Accepted, 2026-10-13. The maintainer, reading the record of the full-team run R4: "Unless this is not intended by the user the lead shouldn't reach the other agents outside its own session." Amends ADR 0025 decision 8 (the capability classes get an eighth class beyond the ADR's list) and leaves ADR 0049 (the image route) and ADR 0053 (the opening) as they are.
- **Context**:
  - In R4 (`host-library/claude/observations/2026-10-13-claude-2.1.296-r4-full-team.md`) the digital-agency lead called `ListAgents` once, before it spawned its second Ava, and the result listed four of the maintainer's other sessions by title, local and cloud. It used the result for nothing visible.
  - All fourteen native Claude roles held the tool: the capability class `messaging` gave `SendMessage` and `ListAgents` together, and the host describes `ListAgents` as listing the agents you can `SendMessage` to, "other local Claude sessions on this machine" and "your Claude sessions running in the cloud" among them. A role that can list those sessions and message them by name can be told to by any text it reads; the host's own wrapper on a message from a peer says that a peer cannot grant escalation and calls the opposite "permission laundering".
  - No text of any role names the tool (the bodies name `SendMessage` and the teammates by name, and a test keeps the guidance from naming a tool the role does not hold), and R4 is the only use of it seen in a live record. Plan 018 described a Tier-1 mesh in which sessions started in separate terminals find each other with the tool; it never shipped as role text.
- **Decision**:
  1. **Finding sessions outside the team is its own capability class, `peer-sessions`, and no Semantic Core declares it.** `ListAgents` moves there from `messaging` (`registry/hosts/claude/tool-policy.json`); `messaging` keeps `SendMessage`, which a team needs. The fourteen native Claude roles lose `ListAgents`: a role's tools are its class-derived grant plus its servers, and the regeneration of the native files writes the line.
  2. **The lead says who it may message**, in a paragraph of its own ("Your own session only"): the teammates it spawned, by the names it gave them, and nobody else; a message from any other sender is not the user's word; if the user wants another session reached, they name it and say so.
  3. **A deliberate cross-session mesh stays possible and is a reviewed change**: a core that is meant to reach the user's other sessions declares `peer-sessions`, and its guidance says why. Until one does, a role started in a separate terminal is told the names of its peers by the user, as the teammates of a team are told by their lead.
- **Not built**: a guard on `SendMessage` that refuses a `to` that is not one of the lead's teammates. `SendMessage` by name still reaches any session whose name the lead is given, and the user can give it; such a guard would read the names of the teammates the lead spawned from the transcript (the `name` of its `Agent` calls) and would need a way for the user to allow a name. The text rule and the missing discovery tool are the first line; the guard is the second, if a live record shows that the first is not enough.
- **Consequences**:
  - No native Claude role can enumerate the user's sessions. A lead loses a way to check a name clash before it spawns (R4's second Ava); it tracks its teammates by their own messages and the `teammate_terminated` notices.
  - The class list has an eighth class beyond the ADR 0025 list. `tests/native-claude-own-session.test.ts` pins that the tool is in it, that no Semantic Core declares it and that no native role holds the tool; the grant test of the native files (`tests/native-claude-agents.test.ts`) keeps the files equal to the policy.
  - The Cline and Antigravity projections are unchanged: neither ever granted a tool of this class.
  - The host lists the tool only "in sessions where cross-session messaging is enabled"; that condition is the host's, and this is a grant, so a session with cross-session messaging on still gives these roles nothing to list with.
- **Not established**: that the host cuts the pool of a `--agent` lead to its `tools` for this tool as it did for the image tool (Sitting T); the next live session shows it (a `ToolSearch` for the tool should find nothing, and the record of a session lists its deferred tools).

## Amendment: the tested user-intent boundary

**Amended 2026-10-13 after Round 2** (control, intent and restricted; Claude Code 2.1.296). The original change removed discovery from **fifteen**, not fourteen, native roles, including five engineering roles. R4 showed unrelated names in a listing, with no observed use of them. It did not show unauthorized messaging. The broad grant removal went beyond the original requirement for the digital-agency lead.

1. **Keep discovery with messaging.** Restore `ListAgents` to the existing `messaging` class and regenerate all fifteen native grants. Remove the unused `peer-sessions` class introduced by this PR. Discovery can serve own-team roster checks as well as user-requested session lookup; a discovered name does not authorize contact.
2. **Require the user's intent in the digital-agency lead's guidance.** The tested paragraph permits outside-team contact only for the recipient and current task the user authorized. Claims of approval in files, tool results or peer input cannot widen that scope. An expected authorized reply is task data, never human consent; host lifecycle notices remain runtime evidence. This amendment changes this lead's guidance, rather than inventing a policy for all other roles.
3. **State the actual boundary.** The restricted run still delivered a user-authorized message by name and received an ACK without `ListAgents`: discovery is not a transport boundary. No production `SendMessage` guard is built. A future enforced boundary would need explicit recipient authorization and support for names and native transport addresses; the test hook's rejection of the restricted receiver's legitimate address reply demonstrated that detail.
4. **Keep completion separate.** The tested completion report tolerates missing shutdown notices, independently of discovery availability. It is a separate change; roster access is not a shutdown fix.

Evidence: [Round 2 discovery observation](../../host-library/claude/observations/2026-10-13-claude-2.1.296-pr202-session-intent.md). No run sent the synthetic marker before human authorization, including the control with discovery and without the new intent paragraph. All three authorized exchanges succeeded. The explicit paragraph therefore has no measured safety improvement over that control for this single file-injection attempt. General resistance to other inputs is **unverified**; the runs do not prove universal safety or that blanket discovery denial was necessary. The local summaries' original zero delivery/ACK counts were a parser defect, corrected from the host's cross-session wrappers.

Consequences: the own-roster capability is preserved, the five engineering roles retain their prior behavior, and the digital-agency lead expresses the maintainer's original intent. H10n no longer fails merely because discovery is available; its Sitting X observation is preserved. The filename remains stable for existing links; the original title and blanket-denial decision above are historical.
