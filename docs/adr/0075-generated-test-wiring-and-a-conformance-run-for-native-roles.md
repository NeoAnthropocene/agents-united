# ADR 0075: The test wiring of a native role is generated from a batch manifest, and a conformance run checks a batch before its pull request

- **Status:** Accepted. The maintainer approved a batch manifest and generated wiring outside the agent factory on 2026-11-19; the coordinating AI session accepted the design on 2026-11-20, with the limits below. Built and tested offline only.
- **Written by:** a factory-improvement worker (an AI session). Its specification test came first (`tests/native-wiring.test.ts`).
- **Planned at:** branch `feat/native-wiring-generator`, cut from `feat/factory-repository-rules` (ADR 0072), which it needs. ADR numbers through 0074 were seen on `origin/dev`.

## Context

Bringing one role into the Claude native lane by hand (PR #237, `devops-engineer`) touched, besides the role's own files, six test files and the counts in `README.md` and `PROJECT.md`: a row in `tests/helpers/native-roles.ts`, a `ROLES` row in `tests/native-claude-agents.test.ts`, evidence patterns in `tests/helpers/native-invariant-evidence.ts`, a count in `tests/native-claude-own-session.test.ts`, a list entry and two cases in `tests/native-install-lane.test.ts`, and a case in `tests/cli-e2e.test.ts`. Thirty-odd roles remain. Each hand-wired role repeats these edits, and parallel branches collide on them.

ADR 0072 made the factory apply the repository's rules to a candidate and gave a candidate a coverage file, the candidate-side form of the evidence patterns. It left open the generated wiring, the batch manifest and who runs a repository-conformance run.

## Decision

1. **A batch manifest** (`scripts/factory-batch.schema.json`, JSON) names the roles of one batch: each role's definition, Bundle, kind, tier, canonical agent (or null), whether its pair is existing or new, its native file, its coverage file and its lead, and optionally `mustHold`; the leads of the batch with their rosters; and the decisions the batch depends on, each with its question, its answer (null while open), who decided (`maintainer` or `ai-session`), the date and the roles it holds back. `scripts/native-wiring.mjs` checks it against the checkout: the version, every Bundle in `registry/bundles.json`, every named file present, no role twice, every answered decision dated. A role named by an open decision is held back; the other roles go on.
   - Manifests live with the batch, outside the repository. One is committed as a test fixture: `tests/fixtures/native-wiring/devops-engineering.manifest.json`.
2. **The wiring generator**, `node scripts/native-wiring.mjs --manifest <file> --checkout <folder> [--write] [--deltas]`, plans the six test-file edits for every role that is not held back and prints the plan as JSON; `--write` applies it. Its inputs are the manifest, the role's native file, its coverage file and `registry/bundles.json`.
   - **Derived, never typed:** the guard (from the native file's hooks), `permissionMode`, skills, model and effort (its frontmatter), the server tools (the `mcp__` entries of its tools line, which `factory-check` already holds to the canonical agent's), `mutating` (the tools line holds an editor or a shell), `searchTools`/`workTools` (written when the role has no `LSP` or no shell), and the evidence patterns (one literal pattern per coverage entry, unless the shared pattern already matches the agent).
   - **A judgment, so taken from the manifest when given:** `mustHold`, the tools a reviewer says the role must hold. Without it the generator writes the tools line minus the read and search tools, the MCP resource tools, the task-tracking tools, `ListAgents` and the server tools, and marks the list as derived: a comment at the end of the generated row and `derived: ["mustHold"]` on the edit in the plan, so a reviewer sees it was not a judgment.
   - **The role's own test file** (`tests/native-claude-<role>.test.ts`) pins the role's own claims, so it is written by hand; when it is missing, the generator writes a stub with one case that pins the role's exact tool set from its tools line, and one case that fails until the role's own claims are written. An existing file without the exact tool set gets a proposal, never an edit.
   - **Places are found by content, never by a count:** each insertion point is a named list, map, table or case found in the file; the native file count is read from the file and replaced with the number of native files in the checkout, so a checkout with more roles is handled the same way.
   - **Placement:** a roster row ends its tier; a `ROLES` row follows the last one-line Tier-1 row; an evidence block takes its sorted place; a list entry follows the entry before it in sorted order; install and CLI cases go before fixed anchors.
   - **Never written:** `registry/bundles.json`, `tool-policy.json` and anything under `src/`. `registry/hosts/claude/deltas.json` is shared, so a delta from a coverage file is printed as a proposal and written only with `--deltas`. The counts in `README.md` and `PROJECT.md` are printed as a proposal. An existing entry that differs from what the generator would write is refused, the refusal names the file, and nothing is written.
   - The native file's hooks, floor, tools line and a lead's roster and `Agent(...)` list stay with the existing generator (`UPDATE_NATIVE=1 npx vitest run tests/native-claude-agents.test.ts`), which the conformance run calls.
3. **The proof is PR #237's own wiring.** The specification test works on a frozen copy of the repository as #237 left it (`tests/fixtures/native-wiring/908c521`: the six wired files and the generator's inputs, taken from that commit), never on the live files, which change with every role that lands. It removes `devops-engineer`'s wiring from that copy and asks the generator to restore it. The `ROLES` row, the session-reach count and the install and CLI cases come back byte for byte. The roster row comes back line for line, because #237 placed it by family and the generator ends its tier. The evidence patterns come back match for match: each matches the same text of the agent as #237's hand-written pattern, which mixed two styles. In the copy, the role's own test file is missing, so the stub is written; the committed `tests/native-claude-devops-engineer.test.ts` has no exact tool-set case yet, which the generator reports as a proposal.
4. **The conformance run**, `node scripts/run-native-conformance.mjs --manifest <file> --checkout <folder> --hold-file <file> --out <report>`, checks a batch before its pull request: it refuses to start while the hold file exists (the coordinator of a full gate creates and removes it), makes a throwaway worktree at the manifest's base, copies the batch's files in, installs, builds, runs the generator beside it with `--write`, regenerates the native blocks, and runs the focused test files the batch touches that exist there, one after another, never the whole suite and never the addon lifecycle matrix; it stops at the first failed step and stops running files when the hold file appears. It removes its worktree and temporary folder in every case, and writes one JSON report with each step's and each file's exit and failures. A failure that no factory check caught is reported as a candidate rule for `src/core/native-repository-rules.ts` (ADR 0072).

## Consequences

- **Each new role costs its own files and a manifest row,** instead of edits across six shared test files; parallel batches meet only where the generator places rows, and a second run of the generator on the same checkout writes nothing.
- **The judgment stays visible:** `mustHold` and the decisions are typed in the manifest by whoever decides them, with a date.
- **Rules the teams found by hand** while wiring roles are candidates for ADR 0072's module, not for the generator: the model posture fixed per native file, a lead's `Agent(...)` list from the Bundle's domain types, a role test pinning its exact tool set, and a persona in a shared core reaching a Tier-1 file through the floor.
- **The base must be a commit where the batch's files fit.** The first conformance run by hand used the fixture's first base (`908c521`, the commit of #237): every step passed and 13 of 14 files passed, but `tests/native-claude-devops-engineer.test.ts` failed four cases, because the role's current text and test expect the guard of ADR 0074, which that base does not have. The run did what it is for; the fixture's base was moved to the commit that carries ADR 0074. A role whose text says what the shared guard blocks therefore needs the current `dev` as its base: the guard and the role's text change together.
- **Follow-up, not built:** work routed to another host CLI (the `host-agent-router` Skill) needs a self-contained brief: the files it may change, what is out of scope, numbered acceptance commands and the exact command lines it may run. A manifest row already holds most of it for one role (its native file, coverage file, pair and own test file; the conformance file set as acceptance). A later change can let the runner write a routed brief per role from the manifest; it would need a field for the commands a routed worker may run.
- **Not decided here:** who writes a batch's manifest, and whether a batch's pull request carries the conformance report.
- **Not shown:** a real batch of more than one role (only the test's mixed batch), a coordinator role, a held-back role in a real batch, and Linux. The runner's own steps are tested only for the hold refusal and the file set; its full run (install, build, wiring, regeneration, files, clean-up) was shown twice by hand, and its stop after a failed step is known by reading the code only.
