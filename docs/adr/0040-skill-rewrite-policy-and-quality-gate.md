# ADR 0040: Skill Rewrite Policy and the Templated-Skill Ratchet

- **Status**: Accepted — 2026-10-04 (decided by the executing session of Plan 035 while the maintainer was away, on the conservative default; every point below is reversible and is listed in the plan's "Decisions taken while the maintainer was away"). Builds on ADR 0023 (the skill intake procedure), ADR 0024 (licence tiers) and ADR 0039 (the full native digital-agency roster).
- **Context**: Prior art searched first: `registry/skills/` (188 skills), `scripts/generate-skills.cjs` (the generator of the engineering skills), `tests/e2e-skills-depth.test.ts` (a depth check that a 150-line template passes: it looks for the words "trigger", "input", "edge case", "error" and a code fence), `docs/skill-intake.md`, `host-library/_upstream/skills.json` (provenance), the Skill Consultation Map tables in `registry/hosts/claude/agents/agency-*.md`, and `plans/028-*` and `plans/030-*`. The audit (`docs/skill-quality/digital-agency-audit.md`) measured the 53 skills of the `digital-agency` bundle: 15 are one template with the title swapped, 6 more are partly generated, 2 are 27-line stubs, the five `workflow-agency-*` skills are loaded by no native role, and six have no verifiable provenance. Across the whole catalog 62 of 188 skills are templated or stubs. The existing depth test did not notice, because it checks that sections *exist*, not that they say anything.
- **Decision**:
  1. **A skill is fit for purpose when a teammate who loads it can do something it could not do from its own knowledge.** A rewritten skill states, for the role that loads it: when to load it and when not to; the decision rules it applies (what to do in which situation, with thresholds where a threshold exists); at least one worked example from a realistic brief (numbers and names, not `<placeholder>`); the anti-patterns it refuses; the evidence it must produce (what a reviewer checks); what it hands to which teammate, in the Open items and handoff vocabulary of ADR 0039; and the limits of what it knows (what it did not check). It does not tell a non-code role to run `npm run typecheck`.
  2. **The seven mandatory sections of PROJECT.md §7.2 and the front matter stay.** A rewrite keeps the headings (`Overview & Purpose`, `Execution Triggers`, `Input/Output Requirements`, `Step-by-Step Runbook`, `Code & Config Exemplars`, `Edge Cases & Error Recovery`, `Verification Checklist`) so the depth and portability tests, the host size limits (under 500 lines, under about 5k tokens) and every consumer of the layout keep working. `metadata.author` stays `agents-united`, `version` becomes `3.0.0`, `icon` and `disable-slash-command` stay, no `metadata.source` is added to original work. What changes is that the content under each heading is the skill's own. `tests/skill-rewrite-contract.test.ts` pins this for every skill at `version: 3.0.0`: the seven headings, the size limits, none of the template's tell-tale phrases (`deterministic framework`, `npm run typecheck`, `Clean git working directory` and the like), a worked example, anti-patterns, the evidence to produce and a hand-off, no allowlist marker left behind, and a native role that loads it when it belongs to the digital-agency bundle.
  3. **Verdicts, not a blanket rewrite.** Each skill gets one verdict in the audit: *keep*, *revise* (the content is real, the frame is wrong), *rewrite*, *merge*, *drop* or *adopt upstream*. A good skill is not rewritten for the sake of it. This plan executes *rewrite* and *revise*; it **proposes** *merge* and *drop* to the maintainer and executes neither (a removal changes the counts stated in README and PROJECT.md and four bundles).
  4. **The ratchet.** `scripts/skill-quality/measure.ts` computes each skill's **templated share**: the fraction of its content lines (headings, fences, code blocks, table rules and lines under three words excluded; the skill's own name replaced by a placeholder in every spelling) that appear in a **frozen corpus** of lines that three or more skills carried at the audit (`tests/fixtures/skill-boilerplate-corpus.txt`, 93 lines). A skill at 0.30 or more is *templated*; a hand-written in-house skill under 30 content lines with no `references/` or `scripts/` is a *stub*; third-party skills (a `metadata.source` that is not this repository) are never stubs; `workflow-*` skills are phase scripts (ADR 0016) and are exempt from the stub rule. `tests/skill-quality-ratchet.test.ts` fails the suite for any templated or stub skill that is not on the allowlist, so **a new skill cannot be a template**.
  5. **The allowlist is a directory of marker files, and it only shrinks.** `tests/fixtures/templated-skills/<skill>` is one small file per skill that failed at the audit (62). A rewrite deletes its own marker in the same pull request; the test fails when a marker stays for a skill that now passes, and fails when a marker exists that is not in the frozen initial set (`tests/fixtures/skill-quality-initial.txt`), so a marker can never be added. Because every pull request touches only its own files, **parallel rewrites cannot conflict**, and because the corpus is frozen, **one skill's rewrite cannot change another's score**. The corpus is regenerated only by a new ADR, never to make a skill pass.
  6. **Original skills are written in our own words.** The reference repositories (obra/superpowers, garrytan/gstack, affaan-m/ECC, all MIT) are read as untrusted data in a quarantine and mined for ideas; nothing is copied. A new skill that follows an idea of one of them credits it in README "Credits & Acknowledgments" as inspiration, with the repository and the pinned SHA read, and carries no `metadata.source` (it is not an adaptation). Anything copied would follow `docs/skill-intake.md` in full: licence, pin, attribution, adaptation, host check, bundle, wiring, bookkeeping, and `hostlib:audit`.
  7. **A skill nobody loads is a finding.** Where a native role plainly owns the topic, the skill is wired into that role's `| Situation | Skill | Load when |` table with a test (the intake rule, step 7). The five `workflow-agency-*` skills are rewritten as playbooks the lead loads, not left as dead files.
- **Consequences**:
  - Positive: the debt is counted and cannot grow; each rewrite is an independent pull request; the measure is deterministic, offline and cheap (it reads files).
  - Negative: the measure sees only repetition, not truth: a skill can be unique and wrong, so the rewrite still needs review by reading, and S1 does not claim otherwise; the corpus is a snapshot, so a future template with new wording would pass until someone looks; 62 markers sit in the repository until their skills are rewritten, 39 of them for skills outside the digital-agency bundle that this plan does not touch.
  - Not established: that rewritten skills change what a teammate delivers in a live session. That is a live-hardening question (Plan 035, M3); until then the claim is only that the skills are no longer templates.
  - Open: whether the 39 other failing skills are rewritten, merged or dropped (the maintainer, or the `agent-factory` bundle of Plan 033).
