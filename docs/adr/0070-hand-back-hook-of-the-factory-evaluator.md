# ADR 0070: A hook checks the factory evaluator's hand-back before it leaves the evaluator

- **Status:** Accepted by the maintainer, 2026-11-18 ("Hand-back hook"), on the results of the agent factory's pilot on a real agent and of its re-run. Those results are recorded in the host-library observation `2026-11-18-claude-2.1.325-factory-pilot-devops-engineering.md`, which is on another branch and not on this one. Built and gated offline; nothing of it is observed on the Host yet (see Consequences). It reverses, for this one hook, the maintainer's earlier choice of "Nothing new, record limits" for the factory hooks (P12, [ADR 0067](0067-claude-factory-realization-delivery.md)).
- **Planned at:** `2eaeccf`, on the branch `fix/evaluator-result-reliability`. ADR numbers through 0069 were seen on that branch.

## Context

The read-only worker `factory-evaluator` follows the Skill `evaluate-artifact` and hands back a review result. The coordinator saves it as `result.json` and checks it with `check-review.mjs --job --result`. The coordinator may never edit a refused result; it may start one fresh evaluator, with the checker's reason in the prompt.

The pilot on a real agent, and its re-run, gave six evaluator results across two sessions, of which one was accepted. After the evaluators were told the citation limit and that the hand-back is exactly one JSON object (the texts of this branch before this decision), both results of the re-run were refused again: one had a JSON syntax fault at character 2462 of a record of 10,305 characters (the saved file was byte-identical to the evaluator's hand-back), the other had two bad citations (a quote one line below the cited line, and a range of six lines). A model cannot rule such faults out when it writes that much exact JSON and exact line numbers in one answer, with no way to check them. The evaluator has no Bash and no Write and cannot run the checker; that is deliberate and does not change.

What the Host's own documentation says, as read for this decision (`host-library/claude/pages/hook/hooks.md`, `.../tools/tools-reference.md`, `.../agent/sub-agents.md`):

- A `PreToolUse` hook in a subagent's frontmatter matches a tool by name (`hooks.md`, "Matcher patterns"); its stdin carries `tool_name`, `tool_input`, `session_id`, `cwd`, and, inside a subagent, `agent_id` and `agent_type` ("Common input fields"). For `SubagentHandback` the report is `tool_input.message` (`hooks.md`, "SubagentStop input").
- Exit code 2 from a `PreToolUse` hook blocks the call, and Claude sees the stderr text as the denial reason ("Exit code 2", "PreToolUse decision control"). For `SubagentHandback` the Host has a limit of its own, `hooks.md:2026` ("PreToolUse `ask` decisions in auto mode"): "To stop a `SubagentHandback` call, return `"deny"`. Claude Code then tells the subagent, up to three times, that its report wasn't delivered and to call the tool again. If your hook keeps denying, the subagent ends without delivering a report through this tool, and the conversation waiting on it gets a note saying so." The paragraph names the JSON `"deny"` decision. Whether the same holds for a block by exit code 2 is not in the library for `SubagentHandback`; the general rule for `PreToolUse` is that a hook that blocks by exiting 2 "routes the same way as `"deny"`: Claude sees the stderr message as the denial reason" (`hooks.md:1980`). The paragraph does not say whether the third denial ends the worker or a fourth attempt is still made, and nothing in the repository has observed it.
- `SubagentHandback` is provided only in auto mode, to subagents the Agent tool runs locally other than forks (`tools-reference.md`). Where it is absent, the worker's final message is its report.
- A command hook's default timeout is 600 seconds, and a timed-out `PreToolUse` hook does not block the call ("Timeouts").
- A project subagent's frontmatter hooks run only after the workspace is trusted, and a `-p` session does not count as trusted (`sub-agents.md`, "Hooks in subagent frontmatter"; [ADR 0042](0042-enforce-the-lead-mode-line-with-a-pretooluse-gate.md)).

## Decision

The maintainer chose a check at the hand-back. A hook on the evaluator's hand-back tool runs the checker before the result leaves the evaluator. When the result would be refused, the evaluator sees the reason in its own context and corrects it. The evaluator stays read-only: it gets no tool.

1. **A pre-check mode of the checker.** `check-review.mjs --precheck <result-file> [--job <absolute-job.json>]` runs the same checks as `--job --result`, on a result file anywhere, with the same reasons and details. It is one implementation with two entry points: `checkResult` takes a `precheck` flag. Skipped in pre-check mode, because they only make sense for the saved file: the rule that the file is the review root's own `result.json`; the postflight that the saved file did not change; the second `recheck()` of the job's pins after the result checks (`checkJob` has just made the first). Without `--job` it only checks that the file is exactly one JSON object. Exit codes: 0 accepted; 1 refused for what the result says; 3 the job or the input is at fault. The saved-file mode is unchanged.
2. **How the hook finds the job.** The result carries `jobId` and `jobDigest`. `review-job.mjs`, which the coordinator already runs, also writes a pointer file `<temp>/agents-united/review-jobs/<jobDigest>.txt` holding the absolute path of the job file and nothing else. No new step for the coordinator. The pointer is a locator, not evidence: the checker verifies the job's own digest against the result's, so a pointer to another job makes the pre-check refuse as the checker would. A failed write of the pointer does not fail the job build.
3. **The hook script** `scripts/precheck-handback.mjs` ships with the Skill (a `requiredSupport` entry of its binding, so a review job pins it and the install records it). It reads the hook input; takes `tool_input.message`; checks it as above; and on a refusal exits 2 with, on stderr, one line that says this is the hand-back check and which attempt it is, then the checker's full reason. On acceptance, or when the text is JSON but no pointer exists for its digest (the worker is not doing a factory review), or when the job or the input is at fault (exit 3), it exits 0 and says nothing. Text that is not JSON at all is blocked with the not-JSON reason; no pointer is needed. It blocks at most TWO times for one worker (keyed by `agent_id`, else by session id and job digest; state under `<temp>/agents-united/handback-checks/`): the first and the second refused attempt are blocked, and the third attempt goes through as it is. The number is the constant `HANDBACK_MAX_BLOCKS` in `src/core/handback-check.ts`; the block message, the sentence the evaluator is told and the tests derive from it. The exit code stays 2, the form the repository's guards use. The caller's check stays the judge.
4. **It fails open, on purpose.** Any error of its own ends in exit 0, and its handler carries no `onFailure: "block"`. This differs from the guards of [ADR 0068](0068-guard-failure-mode-and-claude-floor.md), which must fail closed. This is not a safety guard; a result it lets through is still checked by the caller; and a hook that blocked every hand-back whenever it failed would strand the worker, which the Host ends without a report if its hand-back keeps being denied (`hooks.md:2026`). It writes only its temp state and a temporary result file, which it removes.
5. **Wiring.** The hook is a second `PreToolUse` entry in the frontmatter of `factory-evaluator` only, after its unchanged read-only guard entry: matcher `SubagentHandback`, `node ${CLAUDE_PROJECT_DIR}/.claude/skills/evaluate-artifact/scripts/precheck-handback.mjs`. `src/core/handback-check.ts` is the one place that says so: the generator of the frontmatter block (`UPDATE_NATIVE=1`), `factory-check`, the factory binding check and the startup mechanics check all ask `expectedWorkerHooks(role, guard)`, so each accepts the entry for this role and refuses it for any other and refuses an `onFailure` on it. The doctor reads guards by script name and needs no change; the installer and uninstaller already own every file of the Skill.
6. **The texts.** The evaluator is told, in one wording in the Skill's hand-back step, `references/handback.md` and its agent's native part, that where the Host supports it a hand-back the caller's check would refuse is blocked with the reason, that it corrects every item and hands the complete result back again, and that after two blocked attempts the next goes through. The coordinator's texts say that the caller's check remains the judge and that a headless session runs no such hook.

## Consequences

- It reverses, for this one hook, the maintainer's earlier choice of no new factory hooks (P12, "Nothing new, record limits"). The two guards and their failure mode (ADR 0068) are unchanged.
- The hook fails open, and why: it is not a guard, the caller still checks, and a blocking failure would strand the worker. A hook that does not run (script gone, Node missing, trust not given) means today's behaviour: the result goes to the caller, which may refuse it.
- A headless session (`claude -p`) does not run a project agent's frontmatter hooks (ADR 0042), so headless reviews keep today's behaviour. The coordinator's check is the same in both.
- The final-message fallback is not covered. `SubagentHandback` is provided only in auto mode; where it is absent the worker's final message is its report, and no `PreToolUse` event exists for it. A `SubagentStop` hook receives `last_assistant_message` and can block the stop, but when the worker did use `SubagentHandback` that field holds the closing text and not the report, so a `SubagentStop` check would block a worker that had already delivered. Telling the two apart needs a read of the worker's own transcript. That was not built; it is a limit.
- The cap is two blocks, not three, because of the Host's own limit quoted in the Context (`hooks.md:2026`): "up to three times", then the subagent "ends without delivering a report". With a cap of three the hook would let the fourth attempt through, exactly on that limit; if the Host counts three denials and then ends the worker, the fourth attempt would never happen and the review would be lost, which is worse than a result the caller's check refuses. With two blocks the third attempt is delivered under either reading. The Host's own behaviour after repeated denials is not observed. After the second block the hand-back passes, and the caller's check may still refuse it; one fresh evaluator turn remains the coordinator's rule.
- The Host's temp folder state (pointer files, block counts) is not cleaned by this record; it is small, and a pointer is useful until its job is gone.
- A global install of the evaluator would name `${CLAUDE_PROJECT_DIR}`, which is whichever project is open; the factory is a workspace route, and the inline form of the role keeps the guard only.
- Nothing of it is observed on the Host yet. It needs an interactive sitting in auto mode, in a trusted workspace, on Claude Code 2.1.325 or later: that the hook fires on `SubagentHandback` in a subagent's frontmatter, that the evaluator sees the stderr text and corrects it, and, after two blocked attempts, that the THIRD attempt is delivered (the Host's behaviour after repeated denials, `hooks.md:2026`, is not observed; this is the test of the cap). The offline tests drive the script as a child process with the documented hook input; they cannot show the Host's behaviour.
- The alternative was not chosen: a checker that corrects line numbers itself. It would turn a refusal into an edit of the evaluator's result, which the coordinator's rule (never edit a refused result) and the independence of the review forbid.
