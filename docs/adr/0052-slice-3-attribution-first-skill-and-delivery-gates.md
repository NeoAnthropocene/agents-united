## Decisions

1. **One authoring job.** `author-skill` creates or repairs one skill in a user-selected draft source directory. Inputs name the task, intended user/role, host/surface, local or upstream intent, source/output roots, existing files or references, constraints and evidence budget. Outputs are the complete skill folder, before/after diff, final-file hashes/inventory, attribution/provenance disposition, commands/raw outputs/actual exits, quality findings, unverified items and next action. Local intent ends with a draft; upstream intent prepares the existing contribution template for `dev`. Neither intent automatically installs, commits, pushes or publishes.
2. **Attribution remains a contributor rule.** Reuse `registry/rules/skill-attribution.md`, declared by `agent-factory` only, with an on-demand binding for each host actually delivered. Copied/adapted material needs a supported licence, pinned upstream, required notices, truthful metadata and README credit. An independently written skill credits inspiration and omits `metadata.source`. Compare against a named upstream with the candidate scan before claiming adaptation; a low-overlap result alone does not prove originality. A `not-found` provenance result has a named owner and exact resolution task. These obligations also apply to private drafts. Describe native activation separately from enforcement; prose attribution is not a script guard.
3. **Loading is a delivery gate.** Before any non-reference `author-skill` delivery is merged, the implementation handoff must name a real loading role, native source/installed path, consultation trigger, invocation and supported surface. Test the binding and required skill/rule/support-file edges against the actual installed set in a fresh private workspace. Missing role, missing rule or missing required support file must block that delivery, rather than pass from a catalog listing. Reference-only status cannot disguise an intended runnable skill. The existing maintainer entry points remain; they do not by themselves prove that a contributor workspace has a loader. If a new native role or availability mechanism is needed, its concrete paths/contracts and reviewed host inputs must be included in the separately scoped implementation design before editing; it is not silently supplied by this decision.
4. **Claude first; truthful prerequisites.** Shared content should stay host-neutral. The first claimed native delivery follows the accepted Claude stage, then Codex, Antigravity and Cline in order. No current decision creates support on unfinished hosts. A draft-only milestone may use a declared repository checkout and Node >=24 to run existing validators, with absolute source/output roots outside managed outputs. Checkout-only tools must not be described as installed-package commands; missing prerequisites are blocked or unverified. Managed Option A installation, a per-bundle availability implementation and a new tool-packaging interface remain separate reviewed work. Keep `agent-factory` under construction until useful entry points and the applicable delivery gates pass.
5. **Quality is measured on the final version.** Apply the seven required sections, a skill-specific worked example, anti-patterns, evidence and hand-off. Use the ADR 0040 compact layout: `SKILL.md` <=90 lines and <=6000 characters; trigger-first description <=1024 characters; longer content in support files with checked links; no command injection or template filler. Reuse the frozen corpus and ratchet (templated share <0.30; no stub verdict), portability, licence and layout validators; do not add an allowlist marker or weaken a gate to pass the first skill. Original metadata identifies this project, has a real version/licence and no invented upstream source. `assets/` support is retained; maintainer `evals/` are never installed.
6. **Evidence cases before implementation.** At the public authoring/binding/install seams, announce exact paths and one intended failing behavior before each minimal change. Cases must include: one complete local draft with no publication/install; a repair preserving user edits outside its scope; an adapted source missing its licence/pin; original work with false adaptation metadata; unavailable validation tools; missing loading role/rule/support file; source/output overlap; contributor exclusion with shared-asset preservation; and upstream preparation without a sent PR. Store an eval pair (same prompt with and without the skill) plus an unrelated control prompt under maintainer-only `evals/`. Preparing those fixtures is authorized; running a paid host eval is not. Do not invent a success threshold or claim behavioral improvement without measured results.
7. **Required verification and review.** Run narrow meaningful red/green cases, skill quality/portability/licence/layout/link checks, applicable core/contract/native conformance, `npm run hostlib:verify` and `npm run typecheck && npm test`, saving and reading complete raw outputs and actual exits. Use the full addon lifecycle matrix if shared resolution/ownership changes. Evaluate the final edited artifacts and identify rendering, interaction, invocation and live-host checks not performed. Maintainer quality review and repository CI remain required; evaluator packaging is not implemented here. No skill combination/removal or blanket rewrite of the historical 39-skill group is authorized.

## Loading prerequisite approval and implementation — 2026-10-12

The maintainer explicitly approved [the concrete loading design](../../plans/033-slice-3-claude-loading-design.md): Claude’s built-in `general-purpose` role through `context: fork`, `agent: general-purpose`, `background: false`; the attribution rule projected as a tracked on-demand reference under the skill; and optional `hostAvailability` restricted to Claude workspace/native delivery. This resolves the prerequisite review required in decision 3.

`InstallEngine.install()` checks all required delivery choices from existing state before migrations or writes; `UpdateEngine` preflights the whole request before legacy migrations. Missing native loader/rule/support blocks delivery. Existing bundles without availability metadata retain their lanes. The first skill’s direct-item request is the complete declared factory toolkit, so it retains the same native loading/ownership path; a partial restricted item must select its required bundle. The shared skill helper applies user-scoped draft text and stages repairs with baseline checks; it checks prerequisite file presence, while actual checkout validators remain separate and explicitly unverified until run. Maintainer-only eval fixtures do not install.

The accepted authorization does not include commits/push, merge or paid host/evaluation runs. Local deterministic checks and prepared fixtures establish source and installation integrity; runtime invocation/behavior and a published PR’s CI remain unverified. Existing R3 evidence and adjacent-plan boundaries are preserved.
