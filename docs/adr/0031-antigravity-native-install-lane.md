# ADR 0031: The Antigravity Native Install Lane

- **Status**: Accepted — 2026-10-02 (product owner: "go in order", after the guard hook; the order of ADR 0026). Implements ADR 0026 decision 6 for Antigravity and builds on ADR 0029 (the Cline lane) and ADR 0030 (the package shape).
- **Context**: Prior art searched: `src/core/installer.ts` (the base store copy loops, the compound lane, the sticky per-host record), `src/core/cline-projector.ts` and `claude-projector.ts` (the other lanes), `src/core/hosts.ts` (the `agents` host is "Google Antigravity & Master Library" and is not projection-capable because it is the canonical store), `src/core/doctor.ts`, `tests/native-install-lane.test.ts`, ADR 0029 and 0030, and the real-session observations. What the evidence says: Antigravity's layout (`.agents/agents`, `.agents/rules`) is the canonical store the base install already writes and tracks by hash, so a native file can land on a path the store owns (`orchestrator-engineering.md`, `git-guardrails.md`); the store's rule copies carry no frontmatter and are silently dropped by the host (observed); the store's prefixed agent copies carry a frontmatter `hooks:` key that hides them from discovery (plan 031).
- **Decision**:
  1. **One flag, a third record.** `--native` and `--no-native` now also cover the canonical store: `nativeLanes.antigravity`, beside `nativeLane` (Claude) and `nativeLanes.cline`. It applies when the main library is installed (the default target); a store-less Claude-only install never records it. Sticky across `agents update`, reflected by a dry run.
  2. **The store skips what a native file replaces.** With the lane on, the five native agents and the six native rules are installed as tracked projections (`host: antigravity`, kinds `role` and `rule`, owned by the installing bundle) **instead of** the store copies they replace: the prefixed specialist copies and the coordinator file, and the six frontmatter-less rules. Everything else in the store (the host entrypoint rule, the skills, assets with no native file) is untouched.
  3. **Switching is clean and refuses to lose work.** Turning the lane on clears each replaced store copy first, but refuses (unless `--force`) when the user edited one, and an unmanaged file at a native path is refused like any projection target. Turning it off prunes the projections before the store loops run, so the legacy copies are written back. A store copy's owners are inherited by its native projection, so a bundle installed earlier does not lose its ownership.
  4. **The native projections carry no canonical asset.** A canonical pointer would make the shared lockfile logic create an empty store record for a skipped asset on every install, so the native files are owned by the bundle (`ownedByBundle`) and found by path, like Cline's native-only files.
  5. **The doctor knows the lane.** Native Antigravity files take part in the presence, drift and stale-render checks, with `agents update <bundle> --native` as the repair command, and the legacy frontmatter check no longer asks a native agent for a `model:` key (it leaves the model to the host default, ADR 0030 decision 8).
  6. **Not in this slice: the hooks file.** `hooks.json` is shared with the user's own hooks and needs a merge, not an overwrite, so the guard (`registry/hosts/antigravity/hooks/`) is installed by a following slice.
- **Consequences**:
  - Positive: the standing rules reach Antigravity at last (the legacy copies are dropped by the host), and the native agents are the ones discovered; the lane is opt-in, sticky, drift-checked and removable like the other two.
  - Negative: while the lane is on, the library no longer holds the legacy copies of those eleven assets, so the doctor's agent count and `agents start` rely on the native files (the coordinator keeps the path `agents start` expects); a bundle installed before the flip and not re-installed keeps its legacy copies until its next install.
  - Open: the hooks merge; `GEMINI.md` inside `.agents/rules/`, which the docs would also expect to start with frontmatter and which has no native file yet; macOS, Linux and the 2.0 and IDE surfaces.

## Addendum (2026-10-03, the guard install; resolves decision 6 and the first open item)

The hooks file is merged by the lane now. **Decision 6 is superseded**, the rest stands.

1. **The script is a tracked projection, the registration is a merge.** `.agents/hooks/agents-united-guard.js` is a native file like the agents (kind `hook`, owned by the installing bundle, hash and managed marker as a trailing comment, refcounted across bundles, removed with the last owner, covered by the doctor's drift and stale-render checks). It is planned whenever a native role is, so any bundle that installs native agents brings it.
2. **`.agents/hooks.json` is the user's file and is only merged** (`src/core/antigravity-hooks.ts`, modelled on the Claude session guard): strict JSON only, so a file with comments or a trailing comma is never rewritten and the entry is printed for a hand edit; every other hook, the key order, the indent, the line endings and the final newline are kept, so removing our key restores the user's bytes; the file is deleted only when agents-united created it and nothing else is left. Ownership is the key name `agents-united-guard`, and its content is compared canonically (key order and white space do not matter). A key the user edited, or switched off with `enabled: false`, is `modified`: it is never repaired automatically and the doctor says so. An older entry of ours is recognised by the hash the lockfile recorded (`antigravityHooks.entryHash`) and replaced.
3. **The key exists exactly while the script is a recorded projection.** The installer syncs it after the lane step (so it follows the lane, `agents update`, `--no-native` and a second bundle), and the uninstaller removes it once the script's last owner is gone. There is no separate flag: the guard is part of the lane and sticky with it, per host.
4. **The doctor judges the guard by our key alone.** With the lane on and a native role installed that holds a shell or an editor (the catalog's `shell` and `edit` tools, pinned by test), it warns when the script is missing, `hooks.json` is missing or invalid, or our key is absent, disabled or edited. A hook the user adds never reads as drift, because `hooks.json` is not a hashed projection. A lane with no such role says nothing.
5. **Scope.** The lane writes the workspace file (`.agents/hooks.json`), like its agents and rules. The global file (`~/.gemini/config/hooks.json`) is not touched, and the docs name a CLI `settings.json` hook source as well that is not relied on (hook guide). Not verified: a real session through the installed files (see the plan log for what was and was not run).

## Addendum (2026-10-03, decision 2 of the probes: the legacy GEMINI.md; amends the lane's file set, does not change decisions 1 to 6)

Probe (a) of `host-library/antigravity/observations/2026-10-03-agy-1.2.16-probes.md` showed that agy 1.2.16 reads a frontmatter-less `GEMINI.md` in `.agents/` and in `.agents/rules/`, so beside the native rules the same policy reached the agent twice, from the legacy file (all of it, always on) and from the native rules (two `always_on`, the rest on demand). Prior art searched: `registry/rules/GEMINI.md`, `src/core/registry.ts` (`BASELINE_RULES`: the file is always resolved), the Claude and Cline projectors (both skip the host entrypoint rules, so nothing reads the store copy), the native rule set and the lockfile's projection records.

**Decision (maintainer, 2026-10-03): with the lane on, the lane omits the legacy `.agents/rules/GEMINI.md`.**

1. **It is omitted while any native Antigravity rule is a recorded projection.** The test is the lockfile, not the bundle being installed, so a second bundle cannot bring it back; a lane install with no native rule keeps it as the only baseline.
2. **Migration.** A store install made before is cleaned on the next install or `agents update` (the lane is sticky): a link is unlinked (never the registry), an unmodified copy is removed, and the lockfile record goes. A copy the user edited is left in place, no longer tracked (so uninstall never removes it) and reported at install; `--force` removes it as for any native replacement. A file the lockfile does not record is the user's and is never touched.
3. **Turning the lane off brings it back** through the ordinary store loop.
4. **What is lost, stated plainly:** the legacy file has a section on skill attribution and provenance (author metadata, README credits, adaptation standard) that no native rule carries; it matters to someone adapting skills inside this repository, less to a user's project, and it stays in the registry (`registry/rules/skill-attribution.md`). The native rules also make four of the six topics on demand instead of always on, which is the lean-context intent.
5. **Not established:** a real session with the file omitted (the omission was checked offline only), the symlinked `GEMINI.md` the default install creates (the probe used a real file), and the size cost of the overlap that is now avoided.
