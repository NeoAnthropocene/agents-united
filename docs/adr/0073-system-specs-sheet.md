# ADR 0073: A System Specs Sheet gives orchestrators and specialists the machine facts, collected once

- **Status:** Accepted by the maintainer, 2026-11-19. His words for the decisions: "Automatic at Step 0" (collection by the lead, with the fixed probe list); "It may only require for the planning phase, so collect it once, and check if environment changed when a subagent need it. Also subagentd should be able to request an update from the orchestrator if they understand the development environment has been changed." (freshness and roles); "Yes, as described" (confirming the reading of those words); and, for the goal, to start from the pilot (the Claude host, `digital-agency`) and then apply the rest "for the pilot and host native core contracts".
- **Planned at:** `574fdde` (the base of the branch `feat/system-specs-sheet`). ADR numbers through 0070 were seen on `origin/dev`; 0071 and 0072 are used by the factory worker on its own branches.
- **Written and reviewed by:** AI sessions (a worker and its orchestrator) with the maintainer's decisions above. The Skill went through three independent review rounds, each static, before this slice; the pilot text was not yet seen in a live session.

## Context

No orchestrator of this repository knew the machine it ran on. A plan that picked a runtime, a container tool, a build parallelism or a download size guessed, or probed one tool at a time, differently in every session, and a specialist could not tell a missing tool from a tool nobody had looked for. Facts about the machine are not facts about the project, and they carry private values (the user name, the machine name, the home folder, environment values) that must never reach a brief, a report or a repository.

The findings that shaped the Skill, from the three review rounds: a timed-out probe must end its whole process tree; a system tool must be started by an absolute path and never by a bare name that the working folder could shadow; a sheet found in a folder is untrusted input (a repository can ship one); a version call can download (Corepack shims), so the probes run with the network switched off for them; a tool that is found but fails is not the same as one that is not found; and a short account name inside an ordinary word cannot be removed without damaging real OS names.

## Decision

1. **A shared Skill and one script.** `system-specs` (ADR 0069: written once, host-neutral) holds `scripts/specs.mjs` (Node 20+, built-ins only), a format reference, a worked example and evals. The script has two commands: `collect` and `check`.
2. **An allowlist, not a filter.** The sheet holds OS, CPU, memory, GPU, free disk, shells and a fixed table of developer tools, each probed by one version call. It never holds the user name, the machine name, the home folder or an absolute path, environment values, git remotes, or any account or credential state. The reference lists what the scrub covers and what it does not.
3. **Collect once, with a fingerprint.** `collect` writes the sheet and reuses it whatever its age; reuse is decided by a fingerprint stored as hashes only (each probed tool and shell: found or not, file size and modification time; the absolute PATH entries; OS release, architecture, memory). Identical, or different only in PATH, is a reuse; any other difference, or an invalid or foreign sheet, collects again and names the parts that differed. There is no age limit.
4. **`check`.** A read-only test that starts no process and compares the current fingerprint with the stored one: `unchanged` (0), `changed: <names>` (3), no usable sheet or another format (1). It states its blind spots: an in-place update with the same size and time; a shim manager (pyenv, volta, asdf, rustup, corepack); WSL, the GPU, the macOS developer-tools state; the CPU, GPU and OS text.
5. **Who refreshes.** The coordinating agent collects once while planning and hands the sheet over by path. A specialist that is about to rely on the sheet runs `check` when it holds a shell. On a change, or when its own work shows a difference, it reports it and asks the coordinating agent for an update, at most once per task, and never refreshes the sheet itself. The coordinating agent runs `collect --refresh` and tells the specialists that depend on it. An agent working alone may refresh itself.
6. **Delivery by the brief.** In the pilot the lead's Step 0 gains one point (load the Skill, run `collect` once from the project folder with the shell it holds, say in one line what was collected and where the sheet is, plan with it, refresh only on request), and the brief template gains a `Specs:` line with one rule. The eleven role files and their cores are untouched. A failure of the collector (exit 1 or 2, no Node) never blocks the work: the lead says so once and plans without the sheet. The point runs after the install-record read and so after the mode line, which a hook enforces for every other call (ADR 0044).
7. **The pilot is the Claude-native digital-agency lead only.** `system-specs` is in the digital-agency Bundle. No core changed, so the Cline and Antigravity lanes of this lead, and every other lead, are unchanged. A host-neutral core clause for every orchestrator comes with the roll-out to the other Bundles and Hosts, as its own decision.

## Consequences

- Every brief of the pilot lead names the sheet; five of the eleven specialists hold no shell and so cannot run `check`: they rely on the sheet as given and report differences they observe.
- The Skill is installed with the Bundle on every Host, but only the Claude-native lead uses it until the roll-out.
- Limits, stated plainly: the blind spots of `check` above; not verified on macOS or Linux (fake-runner tests only; the POSIX dangling-link test runs for the first time on Linux CI); Corepack's network switch is from its documentation, not run live; a short or stoplisted account name inside plain text is not removed; the evals were not run through a model.
- Hooks (a start-up collection, or a check before a specialist's first shell call) are a possible later layer; this decision adds none.
- No live session has run the pilot text yet. Until one does, "the lead collects at Step 0 and the specialists check" is a described behaviour, not an observed one.
