# ADR 0034: An Implicit `.agents/` Store Gets No Antigravity Lane, and a Native Cline Lane Leaves Out the Skills That Shadow Its Workflows

- **Status**: Accepted — 2026-10-04 (maintainer: "go", after being shown the finding and a recommendation; a first reply asked whether a skill form would lose the function, and the answer was no, but it would not remove the conflict). Builds on ADR 0029 (the Cline lane), ADR 0031 (the Antigravity lane) and ADR 0033 (skills as copies).
- **Context**: Found in the first real Cline session of the plan 032 close-out (CLI 3.0.68, observations `host-library/cline/observations/2026-10-03-cli-3.0.68-pilot.md`). Prior art searched first: `src/core/hosts.ts` (`planInstallTargets`: a store is added for any fan-out host except Claude alone, recorded as `addedCanonicalStore`), `src/core/installer.ts` (the Antigravity lane runs whenever the store is the state dir; the Claude lane drops the skill of a workflow's name from `.claude/skills`), ADR 0029 and ADR 0031 (decision "one `--native` covers every host being installed"), and the Cline guides (every enabled skill is a `/<name>` command). Two facts. (1) With `-t cline --native` the `.agents/` store exists only because Cline needs it, yet the Antigravity native lane ran there and wrote agents, rules, a guard hook, `hooks.json` and `mcp_config.json` that only Antigravity reads; the same happened for a Claude install with `--plugin`. (2) In the same install the three native Cline workflows (`/workflow-implement`, `/workflow-review`, `/workflow-test`) were unreachable: the generic skill of each name sits in the shared `.agents/skills/`, a skill is a slash command and Cline loads `.agents/skills/` before `.cline/skills/`, so the skill answered `/workflow-test` (the session loaded it through the `skills` tool). With the skill removed, the host expanded the workflow file into the conversation and the lead followed it.
- **Decision**:
  1. **`implicitStore` records why the store exists.** It is true when `.agents/` was only added for another host (Cline, the Claude plugin lane) and Antigravity was not asked for, false when it was (`-t agents`, the default, or `--canonical-store`). The CLI computes it from `planInstallTargets`; it is recorded in the lockfile (`implicitStore: true`, absent otherwise), sticky across `agents update`, and an explicit option overrides the record in either direction.
  2. **An implicit store gets no Antigravity native lane.** No native agents, rules, guard hook, `hooks.json` or `mcp_config.json`; a dry run plans none either. The store keeps the legacy canonical copies, as in a plain Cline install.
  3. **With an implicit store and the native Cline lane, the generic skills a native Cline workflow replaces are left out of the store**: `workflow-implement`, `workflow-review`, `workflow-test` (read from `registry/hosts/cline/workflows/`), as the Claude lane already does in its own skill folder. Existing copies migrate on the next install or `agents update`: a link is unlinked (never the registry), an unmodified copy is removed, an edited copy stays, is no longer tracked and is reported, `--force` removes it. `--no-native` brings the skills back.
  4. **When Antigravity is a target the skills stay**, because Antigravity has no native workflows and relies on them, and the shared store cannot hold two versions. Doctor then warns that the native workflow is shadowed and names the way out.
  5. **A store that already carries the Antigravity lane is an Antigravity library whatever the option says** (the recorded lane or any `antigravity` projection), so a later implicit install cannot take the lane away. Lockfiles written before this field behave exactly as before.
  6. **Not chosen:** converting the native Cline workflows into native Cline skills. A Cline workflow is a markdown runbook the lead follows with the `subagent_*` tools, and so is a skill, so nothing functional would be lost; but a native skill would still be shadowed by the store's generic one, so the same removal is needed, and putting the Cline text into the shared store skill would hand Antigravity instructions for tools it does not have. It stays a possible follow-up for the auto-invocation a skill description gives.
- **Consequences**:
  - Positive: a Cline-only or plugin-only install no longer carries Antigravity-only files; the native Cline workflows are reachable by their command names, which a real session confirmed once the skill was out of the way.
  - Negative: an install that adds Antigravity later (`-t agents`) must run `agents update` for the three skills to return; a store shared by Cline and Antigravity keeps the shadowing and only warns; a workflow projection leaves an empty-hash pointer record for the skill it replaces, which is harmless (doctor is clean) and not a record of an installed file.
  - Open: the Cline IDE surface; how the host orders a skill and a workflow of the same name in versions other than 3.0.68; whether `.agents/plugins/<bundle>/skills/` copies of the three skills (still written) could ever shadow (they did not in the retest).
