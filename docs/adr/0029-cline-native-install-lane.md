# ADR 0029: The Cline Native Install Lane

- **Status**: Accepted — 2026-10-02 (product owner: "run for the next", the order fixed in ADR 0026: guides, profile and tool policy, native package, install lane). Implements ADR 0026 decision 6; builds on ADR 0028.
- **Context**: Prior art searched: ADR 0026 decision 6 (one `--native`, recorded per host), ADR 0027 decision 2 (skills in `.cline/skills/`, doctor warns on shadowing), ADR 0028 (roles native, orchestrator a rule and skill, guard narrowed, `.agents/skills` wins over `.cline/skills`), `src/core/native-package.ts`, `claude-projector.ts`, `installer.ts`, `doctor.ts` and `tests/native-install-lane.test.ts` (the Claude lane), `src/core/cline-projector.ts` (the legacy lane), and the observations of CLI 3.0.68. The Claude lane stores one boolean, `nativeLane`, at the top of the lockfile; the legacy Cline lane projects every role, the orchestrator included, plus a coordinator rule and an Agent Plugin package.
- **Decision**:
  1. **One flag, a record per host.** `--native` and `--no-native` apply to every fanned-out host that has a native package (Claude, Cline); an unset flag inherits each host's recorded choice, so `agents update` cannot swap native files back. Claude keeps the existing `nativeLane`, Cline records `nativeLanes.cline`, so lockfiles from earlier releases stay valid and a Claude-only install never records Cline. The flag's help text and the README say so. **The flag is read from the typed arguments** (`explicitNativeFlag`): the CLI library defines `--no-native` beside `--native`, and for such a pair it reports `native: true` when neither is typed, so on `dev` the Claude lane was already switched on by default through the CLI, contrary to its documented opt-in, and the Cline lane would have followed. Without the flag the lane is now off again for both hosts, and a recorded choice is inherited.
  2. **What the Cline lane installs.** The four configured agents from `registry/hosts/cline/agents/`; the native workflows from `registry/hosts/cline/workflows/` in place of the same-named projection; the orchestrator rule and skill named after the bundle's orchestrator role, **instead of** its configured agent and the legacy coordinator rule (ADR 0028 decision 6); and the guard plugin, whenever a native role is installed. Each carries a managed marker (`profile: cline-native`, the source hash) so the existing hash and freshness checks apply. Anything without a native file keeps its legacy projection, and `--no-native` prunes the native-only files and restores the legacy ones. The legacy Agent Plugin package, domain rules and other bundles' roles are untouched.
  3. **Skills the registry already ships are not copied to `.cline/skills/`.** They are portable as written and `.agents/skills`, which Cline loads, already serves them; a `.cline/skills` copy would be shadowed (`.agents/skills` wins) or redundant. Only skills with no registry source, today the orchestrator's, go to `.cline/skills/`. This narrows ADR 0027 decision 2, which assumed a copy of every skill.
  4. **The doctor warns on two things, on whichever host it is asked about**, because both are recorded in the lockfile: a native role whose `tools:` holds `run_commands`, `editor` or `apply_patch` while the guard plugin is missing, and an `.agents/skills/<name>` that shadows an installed native `.cline/skills/<name>`. A fresh install gives no warning (the false-positive doctrine of ADR 0017), which decision 3 makes possible. Read-only roles need no check: the host enforces their `tools:` list and the hash check catches an edit.
  5. **Plumbing.** Native files with no canonical asset (rule, skill, plugin) are declared by the installing bundle (`ownedByBundle`), refcounted like any projection, and treated as bundle-derived coordination on removal; a new projection kind, `plugin`, names the guard.
- **Consequences**:
  - Positive: Cline gets the same opt-in, sticky, drift-checked native lane as Claude, with the safety checks that matter to a user and no translation report.
  - Negative: the lockfile has two spellings of one idea (`nativeLane` for Claude, `nativeLanes` for the rest) until a major version; the legacy `.agents/skills/workflow-*` skills still coexist with the native workflows of the same names in a Cline install, a pre-existing overlap.
  - Open: which of a skill and a workflow of the same name wins `/<name>` on Cline; updating a real older Cline install; two bundles sharing the guard plugin in a real session; MCP wiring and the IDE (out of scope here).
