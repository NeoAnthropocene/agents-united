# ADR 0055: Completion does not wait for shutdown notices

- **Status**: Accepted through PR #203, merged 2026-10-14. Proposed 2026-10-13 as an independent follow-up authorized by the maintainer after the PR #202 experiments. Amends the delivery method of the native Claude digital-agency lead in ADR 0039 and Plan 035; keeps the structured request/reply protocol.
- **Context**:
  - The maintainer repeatedly saw specialists shut down while the lead waited indefinitely for missing approvals or host termination messages. R4 also distinguished approval calls in peer records, notices delivered to the lead, and the maintainer's UI observations. A missing message does not establish that a peer is running.
  - Round 2 control/intent/restricted runs used the same proposed completion paragraph. Each lead verified revised work, dispatched two accepted shutdown requests, and returned its first Completion report in 6.253/6.999/7.558 seconds, with no host termination notice before the report and no human intervention. Discovery availability did not determine that outcome.
  - Restricted received Ava's late notice after its report and then said it was still waiting for Kaan. This is a remaining wording/state flaw even though first delivery already succeeded. The additional late-event clarification is **not yet verified live**.
- **Decision**:
  1. **Deliver verified work after shutdown dispatch.** Continue to wait for actual work and specialist reports, verify the deliverables, then send each teammate the structured shutdown request. Once every request is accepted, immediately deliver the final Completion report and return control. If a request fails, report its failure and unresolved state with the verified work rather than waiting indefinitely or declaring shutdown.
  2. **Keep evidence separate.** Report request status, approval observed and host termination observed for each teammate. Dispatch is not exit. Missing approval or host evidence is not observed, not still running. The maintainer's UI observation is user-reported and remains distinguishable from the host record.
  3. **Completion is stable after delivery.** A late approval or lifecycle notice updates only the evidence table and states Delivery remains complete. It cannot restart a wait for another missing notice, initiate polling, or require the user to supply one. Never wake a finished teammate merely to get a termination notice.
  4. **Host cleanup remains the host's responsibility.** No fabricated host notice, process killing, independent liveness inference, or production Stop hook is added. The lead's instruction is copied into the installed native role and tested for that contract; it is not enforcement of host termination.
- **Evidence**: [Round 2 completion observation](../../host-library/claude/observations/2026-10-13-claude-2.1.296-completion-report.md), with compact timings and the residual late update. Initial reporting was observed in three two-specialist flows. The late-event clarification, declined/failed-request branch, nine-specialist flow and every teammate process's exit remain **unverified live**. No further paid session was launched by the executor.
- **Consequences**:
  - The user receives verified work without having to announce that a missing-notice teammate already terminated. Cleanup uncertainty remains visible and does not masquerade as unfinished delivery.
  - This change is independent of discovery grants and PR #202's session-intent decision. It changes only the Claude digital-agency lead's native text; tool grants, structured protocol, other roles, other hosts and the mode-line wait remain as on dev.
  - Live evidence proves the initial reporting improvement for these runs, not the cause of missing host notices or universal adherence to the new late-event sentence. A disposable follow-up kit is prepared locally for maintainer feedback; it does not start a model session automatically.

## Applicability amendment, 2026-10-16

The maintainer's [Desktop full-agency exercise](../../host-library/claude/observations/2026-10-16-claude-2.1.299-desktop-full-agency.md) set `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` to `1` and still ran ordinary native subagents. Claude Code documents coordinated Agent Teams as CLI-only (checked 2026-10-16), and the recorded launch results differ from the CLI team sessions of the 2026-10-14 diagnostic: the Desktop launches answered "Async agent launched successfully" and were continued with `SendMessage`, while the CLI sessions answered "Spawned successfully" with delivery by mailbox. In Stage 1 the lead called finished consultants idle and proposed a team shutdown. The explicit human guidance of Stage 2 prevented that for the remaining stages, so those stages do not verify the unchanged default text.

The decision above is unchanged for actual coordinated-team teammates: the structured request, the separation of dispatch, approval and termination, and the immediate and stable Completion report. It is now scoped. The native lead selects the branch from the host's own launch results, never from the variable. For ordinary subagents a finished turn and the worker's report are the completion evidence: the lead sends no `shutdown_request`, waits for no approval or `teammate_terminated` notice, wakes no finished worker for a lifecycle event, lists each worker's report status in place of the shutdown table and delivers at once. A late notice leaves delivery complete in both mechanisms. An unestablished mechanism is reported and gets no protocol frame. Specialists report through `SubagentHandback` only when that tool is actually available, otherwise in the ordinary final response, and a coordinated teammate keeps the host-delivered final answer.

**Status.** The authored-contract tests (`tests/native-claude-worker-lifecycle.test.ts` and the updated lead and completion regressions) pass offline. They show that the text exists, not that a model follows it. The changed default behaviour is **unverified live**: the guided Desktop run is observed, and no run has used the new text. A targeted run needs its own candidate, hypothesis, human launch and accepted spending ceiling; no model starts one automatically. Physical exit, cost and quota, the naturally late notice, a failed or declined request and the nine-specialist team flow stay unverified. ListAgents and SendMessage grants, the user-intent boundary of ADR 0054, the mode-line wait and the absence of a production Stop hook, forced kill or polling are unchanged.

## Live verification amendment, 2026-10-19

The maintainer ran the two H12 cases of the [live-test protocol](../live-test-protocol.md) on the candidate of the applicability amendment above: four prompts that say nothing about workers, teams or shutdown, once in the Desktop Code tab (embedded Code 2.1.299) and once in the interactive CLI (2.1.301), with the teams variable at `1` in both. [The observation](../../host-library/claude/observations/2026-10-19-claude-2.1.301-worker-lifecycle-live.md) and its [compact evidence](../../host-library/claude/observations/2026-10-19-worker-lifecycle-live-evidence.json) hold the result.

On Desktop the lead named the mechanism from its launch results (ordinary subagents, relay mode), sent no `shutdown_request` or other protocol frame, never called a finished worker idle or waited for a lifecycle event, and delivered each report 6 to 8 seconds after the last worker activity with a line that no team shutdown applies. In the CLI the lead named the mechanism from the launch result ("instructions by mailbox"), sent a structured request to each teammate, the consultant included, in two rounds, and gave its report 6.8 and 5.9 seconds after the last accepted request with no tool call in between, dispatch, approval and termination in separate columns and missing events marked "not observed". Stage 4 held zero tool calls by every actor on both surfaces.

**The naturally late notice is now observed.** Two approvals and two terminations reached the lead only at the start of its next turn, 377 seconds after the first round; the lead recorded them as evidence and went on with the user's revision. For the second round none arrived before the end of the session, and the lead said it did not know whether the teammates were still running, as decision 2 asks.

**Findings.** (1) A foreground Desktop launch returns the worker's report inline in a "[Subagent hand-back]" frame with an agent-id footer; the lead's Step 0 names only the background form ("Async agent launched"), and in its first answer the lead quoted words the result did not contain, with the right conclusion. (2) On 2.1.301 a message to a stopped in-process teammate resumes it with its earlier context, so shutting teammates down after a delivery and revising later lost nothing; the lead's remark that a resume restores no teammate concerns resuming a session. (3) The first collector misread three things, found by these runs and fixed with tests.

**Status.** The decision of this ADR and the applicability amendment are verified live once on each surface, within the limits of the observation: one session per surface, two workers, no control run of the previous text. **Still unverified:** a failed or declined shutdown request, the nine-specialist flow, a Desktop run in which `SubagentHandback` is provided and used under the new wording, process exit, cost and quota. No instruction changed after the runs; the foreground wording of finding 1 is a possible one-sentence follow-up.
