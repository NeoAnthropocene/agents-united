# ADR 0035: The Native Claude Guards Ship as Script Files in `.claude/hooks/`, and a Global Install Keeps Them Inline

- **Status**: Accepted — 2026-10-04 (maintainer, in chat, after a grilling: "file plus a doctor check" for a missing script, and "keep inline `node -e` there" for a global install). Follow-up (6) of the plan 032 close-out. Builds on ADR 0018 and 0025 (native Claude agents), Plan 022 H5 and Plan 023 A0 (the managed guard and its exec form), and ADR 0031 (the Antigravity guard as a tracked script).
- **Context**: The first real Claude session of the close-out (`host-library/claude/observations/2026-10-03-claude-2.1.288-pilot.md`, defect 3) showed that Claude prints the whole `node -e <script>` of a blocking hook in its block message: about 600 characters of regular expressions per block, which also reach the model. Cline and Antigravity already ship their guard as a file. Prior art searched first: `src/core/guard.ts` and `src/core/readonly-guard.ts` (the two inline scripts, exec form), `src/core/antigravity-projector.ts` and `src/core/cline-projector.ts` (a guard as a tracked projection with `ownedByBundle`), `host-library/claude/guide/hook.md` (path placeholders; "a gate that cannot start fails open"), and the open and closed pull requests for the term "guard" (none for a Claude script file). Three facts shaped the decision. (1) `${CLAUDE_PROJECT_DIR}` is the only placeholder a user-owned script can use; a user-level agent has none. (2) A hook whose script path does not exist exits non-zero without blocking, so a missing file is the guard gone, silently. (3) A plugin agent's `hooks:` are ignored by the host, so the plugin lane is unaffected whichever form it carries.
- **Decision**:
  1. **Two script files, one author.** `registry/hosts/claude/hooks/agents-united-guard.js` (destructive-command guard) and `agents-united-readonly-guard.js` (read-only guard) are the existing `GUARD_SCRIPT` and `READ_ONLY_GUARD_SCRIPT` written out unchanged, by the same `UPDATE_NATIVE=1` regeneration that writes the hooks block; a test ties each file to its constant, so the logic is not authored twice. The inline constants stay: the legacy lane, the plain-session settings guard and the global install still use them.
  2. **The role names the file.** The committed native agents carry `{"type":"command","command":"node","args":["${CLAUDE_PROJECT_DIR}/.claude/hooks/<name>.js"]}` (exec form, no shell), with the matchers the inline guards always had. The block message the host prints drops from about 600 characters to under 90.
  3. **A tracked projection.** The lane installs the script as kind `hook`, host `claude`, with the marker as a trailing comment (code the host runs is copied unchanged), owned by the bundle that installs a role naming it and refcounted like the roles. A script is removed with the last role that needs it, with `--no-native`, and with the bundle; an emptied `.claude/hooks/` goes with it and a hook of the user's own stays.
  4. **A missing script is a doctor warning, not a silent state.** Doctor names the script and the roles that depend on it, says that the host lets the call through when a hook script cannot start, and gives `agents update <bundle> --fanout claude`. An edited script is the ordinary content-drift warning.
  5. **A global install keeps the inline guard.** Roles in `~/.claude/agents` cannot name a script portably (the placeholder is whichever project is open), so with `--global` the same committed role is rendered with the inline `node -e` hooks block and no script is installed. The marker hashes the committed source either way, so freshness is judged the same in both scopes. The noisy block message stays for global installs only; that is the known limit of this decision.
  6. **Install carries an older install forward.** An install made before this change (inline guards, recorded hashes) is upgraded by the next install or `agents update` without `--force`, because the recorded hash still matches what was written.
- **Consequences**:
  - Positive: a short, readable block message; the guard logic reviewable as a file; a tracked, hash-checked, refcounted script; the doctor can say why a guard is not in effect.
  - Negative: the guard is now a file that can be deleted, so a deleted script fails open until the doctor or an update runs (the inline form could not go missing); two shapes of the same role exist (project and global), and the doctor reads both.
  - Not verified in a real session when this was written: that Claude resolves `${CLAUDE_PROJECT_DIR}` in a role's own `args` (the docs say it does for any hook defined anywhere, in exec form), the length of the real block message, and the behaviour of a deleted script. See the observations file of the slice for what a session showed.
  - Open: the plain-session guard in `.claude/settings.json` (`--session-guard`) still writes the inline form, because the legacy goldens pin it; whether it should follow is a separate decision.
