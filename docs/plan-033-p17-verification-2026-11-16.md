## What the Host documentation says and why two switches are used

- [agent-teams.md](../host-library/claude/pages/orchestration/agent-teams.md), section "Claude spawns teammates instead of subagents": the way to turn agent teams off is the value `0`; "Setting the variable to `0` in your user `settings.json` overrides a shell export"; "project settings, local settings, and a `--settings` payload apply after user settings, so an `env` entry that sets the variable to `1` in any of them wins"; managed settings `"apply after every other source"`. Section "Enable agent teams": while agent teams are enabled, a subagent that Claude names launches as a teammate.
- [settings.md](../host-library/claude/pages/settings/settings.md), section "Settings precedence": command line (`--settings <file-or-json>`, `"for that session only"`) sits above project local, shared project and user settings and below managed settings; `"a key you leave out keeps its value from those files"`; "An `env` block inside a settings file is an ordinary key and follows the levels above."
- Consequence drawn by the lead: removing the variable from the process the launcher starts would change nothing where a settings file sets it to `1`, which is the maintainer's machine. The launcher therefore uses two switches for `agent-factory`: setting `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` to `0` in `plan.env` (dropping any differently-cased parent key at spawn) and passing `--settings={"env":{"CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS":"0"}}` in `argv`.

## Known and left

- Managed settings apply after the `--settings` payload and can still enable agent teams; the dry-run line and the real-start note state this limit.
- A session started directly with `claude --agent orchestrator-agent-factory` does not get either switch; the runbook sentence says so and keeps the rule that a worker that starts as a teammate is refused and reported.
- The Host documentation in the library does not say whether a `--settings` `env` block replaces the `env` block of lower settings files as a whole or is merged with it key by key. If it replaces, other variables a user sets in a settings file's `env` block would not reach the factory session. The maintainer's user settings `env` block holds only the agent-teams variable, so nothing of his can be dropped; unverified for other users.
- Pre-existing, found while checking the review's point about `cmd /c`, not changed here, all bundles: when Claude is installed as a `.cmd` shim with no Node wrapper beside it, the launcher starts it as `cmd.exe /c <shim>`; in the lead's scratch trial a first message with line breaks was cut at its first line break on that route, and a shim path that contains a space failed to start. The maintainer's machine resolves `claude.exe`, which does not use that route.
- A single-dash option in an executable prefix is not refused (the prefix rule checks `startsWith('--')`); the prefix comes from the capability probe, not from user input.
- Process-budget counting (noted in S1) is still not addressed.
- The scripts' clean-environment helpers still remove the variable before they run the launcher's dry run; harmless, left.
