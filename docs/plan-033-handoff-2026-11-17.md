## The factory: how to install and start it, and what it can do today

- Install it into a workspace (Claude Code CLI, workspace scope, native lane only): `agents add agent-factory -t claude --native --allow-under-construction --copy -y`.
- Start its coordinator: `agents start agent-factory --host claude`. Run the entry dry run (`... --dry-run`) from the workspace root.
- Use the CLI of a built checkout of `dev` after the merge (`npm ci`, `npm run build`, then `node <checkout>/dist/cli.js add ...` and `node <checkout>/dist/cli.js start ...`), not a bare `agents`: on the machine of this session the bare command resolved to an older published version that knows nothing of the factory ([P16](plan-033-p16-verification-2026-11-16.md)). The launcher refuses while `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` is set; clear it for that process.
  - Correction, 2026-11-17, by the lead of the next session: the last sentence is out of date. Since [P17](plan-033-p17-verification-2026-11-16.md) the launcher does not refuse; it turns agent teams off for the factory's own session, so nothing has to be cleared. A case the maintainer can sit to see this himself is in [the sitting case](plan-033-teams-variable-sitting-case-2026-11-17.md) (prepared, not run).
- What it does today, each with caller-checked records: it realizes ONE Claude agent from a supplied shared pair (coordinator, `factory-realizer`, `factory-evaluator`); it authors a Skill, a shared pair and a Bundle proposal through three commands the human types (`/author-skill`, `/author-contract`, `/author-bundle`, each with the absolute path of a task record the coordinator has prepared); it reviews candidates of the kinds `skill`, `shared-pair` and `claude-agent`; it plans a host-update sync for the host `claude`; it prepares a pull-request body and sends nothing.
- What it cannot do: it has no target and no review kind for a Codex, Antigravity or Cline native artifact. The remaining stages build exactly that, so in those stages the factory can author and review the host-neutral parts (shared pairs, Skills, Bundle proposals) and the maintainer skill `realize-for-host` with the Host's own library stays the way to write the native parts until a stage's own realizer exists.
- Limits that matter in use: the coordinator reads its entry itself (no preload for an `--agent` main); the three authoring commands are typed by the human; the waiting rule for background workers, the rule for a refused review result and the rule that a fork stops on a wrong task path are prose, not mechanisms; a worker that never reports and the stop-waiting exit were never observed.

## Working rules that proved necessary

- Pull requests target `dev`, never `main`. The lead never merges.
- The gate before a push, from inside a Claude Code session on Windows: `npm run hostlib:verify`, `npm run typecheck`, `env -u CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS npm test -- --maxWorkers=1 --fileParallelism=false`, and for changes to bundles or installs `AGENTS_CI_FULL=1 env -u CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS npx vitest run tests/e2e-domain-conformance.test.ts --maxWorkers=1 --fileParallelism=false`. Run nothing else on the machine meanwhile, and start it only after the reviews are in.
- Focused test runs need the limits `npm test` uses: add `--testTimeout=30000 --hookTimeout=30000`. Without them several install and package tests look like timeouts.
- Linux CI is the second platform: tests that depend on a case-sensitive volume run only there, tests that need Windows short names only on Windows.
- Records come from one facts file per slice or sitting; a record says what was shown once, what was not shown and what is not determinable, and who ran a session.
- Every slice had an independent review by a second Host before its gate; the reviews found real defects in each of the last four slices.
- Live sessions on the Host run on the maintainer's subscription; a headless test run carries the Host's budget cap flag; an interactive sitting can be sat by the lead through a terminal bridge only when the maintainer delegates it, and the record then says so.
- The working notes of the session that wrote this (plans, decisions, facts files, briefs, reviews) are under `scratch/plan-033-implementation/` in that session's checkout; `scratch/` is ignored by git, so they are not on the branch.
