## What the maintainer saw that the records do not show (F1)

The maintainer ran the lead's printed block in the terminal they use every day, which opens in their **home folder**. `claude mcp add --scope local` stores the server under the entry of the folder it is run from, so it went to the home folder's entry and the session started in `e2e-gemini` did not have it. After a second run with a `cd` into `e2e-gemini`, `claude mcp list` showed `image-gen: npx -y mcp-image@0.18.0 - ✔ Connected`, and the restart then listed the tool. The first run's entry, with the key, is still in the home folder's entry unless the maintainer removed it (`claude mcp remove image-gen --scope local` from that folder). This is the maintainer's report; the session record cannot show it, and it is the reason the chain needed two runs of the command. The H10n protocol already said "a second terminal opened in the project folder (the local scope is keyed by the folder)", but the lead's printed block did not, and a user reads the block, not the protocol.

**Fixed in this PR, test first:** every command block of the `mcp-setup` reference's section "Photographic images" starts with `cd <absolute path of the project>`, a paragraph "Run it in the project folder" says why and what to do after a run in the wrong folder, and the lead's paragraph says the same and has the user check with `claude mcp list` from that folder (`tests/mcp-setup-image-route.test.ts`, `tests/native-claude-image-route.test.ts`). The fix was written after this sitting and has not been run live.

## What this says

The `mcp-setup` route does install the image-generation server for a Gemini-only pilot, in the only way the skills allow for a credentialed server: the lead offers it with the figures, **prints** the command with a placeholder and never runs it, the user runs it in their own terminal, and a restart loads it. Every link was seen to work in one session with one image, no key outside the maintainer's terminal, and the host cut the lead's pool as ADR 0054 expects. What failed was the printed block: it did not tell the user which folder to run it in, which cost a second run and left a key in a stray entry (F1, fixed here, not yet run live).
