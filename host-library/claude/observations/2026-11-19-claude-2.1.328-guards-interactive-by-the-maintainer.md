# Claude Code 2.1.325 and 2.1.328: the guards in interactive sessions, sat by the maintainer (2026-11-19)

**These are observations of one installed build, not documentation.** The guides in `../guide/` cite the vendor's docs snapshots; where this file disagrees with a guide, the guide's authoring notes say so. Nothing here is a vendor promise, and it may change in any release.

The headless observations of 2026-11-18 ([record](2026-11-18-claude-2.1.325-guard-failure-mode-headless.md)) left two things that only an interactive session can show: what a user sees for a blocked call, and the inline guard as an agent's own frontmatter hook (a headless run skips those). The maintainer sat both himself on 2026-11-19, with the session guard in its file form (pull request 229, on `dev` at `7f13f3b`). ## How the sessions were run

- Interactive `claude` in PowerShell, on the maintainer's subscription, permission mode `auto`. The first session ran on Claude Code 2.1.325, the other three on 2.1.328: the Host updated itself between them.
- Folder S: a new git folder with `agents add agent-factory -t claude --native --allow-under-construction --copy -y --session-guard project`, from a build of `dev` at `7f13f3b`. The session guard is `node ${CLAUDE_PROJECT_DIR}/.claude/hooks/agents-united-session-guard.js` with `onFailure: block`.

The sessions there were started with `claude --agent backend-architect`, so the guard is the main agent's own frontmatter hook, with nothing registered at settings level.

## What this shows and what it does not

Shown once each, typed by a human: the session guard in its file form and the inline role guard as an agent's own hook block a forced push, and both block when they cannot run, with the Host's notice `failed; blocking because onFailure is "block"`. This closes two limits the "Factory hooks" row was closed with on 2026-11-18: the inline guard as an agent's own frontmatter hook (for a main agent), and what a user sees for a blocked call.

It also corrects the weight of finding G6 of the headless record. That finding (the Host puts the hook's whole command line in front of every refusal, so an ordinary block begins with the words of the failure message) was the reason the session guard's script was moved into a file. In interactive sessions the notice says `[command hook]` and never showed the script, with the inline form as well (2A). So the long notice is, on what these sessions show, a property of the headless run that printed it and not of what a user at the terminal sees. The file form still shortens what a headless or scripted run prints and reads; it was not needed for the interactive notice.
