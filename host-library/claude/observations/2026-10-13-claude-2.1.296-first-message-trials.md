# Claude Code 2.1.296: the first-message trials, welcome out and the Operation Mode information first (headless; Plan 036 S19, run and read 2026-10-13)

**These are observations of installed builds, not documentation.** The guides in `../guide/` cite the vendor's docs snapshots; where this file disagrees with a guide, the guide's authoring notes say so. Nothing here is a vendor statement. The maintainer asked, after Sitting U, to remove the welcome message of the Tier-2 orchestrators and to make the Operation Mode information the first message, and to "test if this works without the hook errors as we expect, and then implement". This is the test. **Its limit is stated first: the sessions are headless, and a headless session saves its transcript promptly, which is the opposite of the interactive sessions where the red errors were seen. The trials show what the lead writes and in which message; whether an interactive session shows a red error is what Sitting V (H11) has to show.** The decision and the implementation are ADR 0053.

- **Build and method:** Windows 11, `claude-sonnet-5-5` (`--model sonnet --effort low`), Claude Code `2.1.296`, `claude -p --agent orchestrator-digital-agency` on the subscription (no API key in the environment, the two team variables set, `--max-budget-usd 0.35`), the lead alone (the prompts never reach a teammate). Six fresh folders built from the clone at `1bf058c` (the tip of PR 198, which merged at 07:10 UTC that morning) with `scripts/new-first-message-folders.ps1`, each the digital-agency native install (`doctor` healthy), no image server, `docs/pilot/hero.ts` as the file to read: `fm\base` is the lead as the clone has it, and `fm\a` to `fm\e` differ from it in the lead's section "The first message" only (`variants.txt`, checked by `patch-first-message.mjs`, which stops if a replacement does not match exactly once). **29 runs**: prompt `p1` (a task, "Read docs/pilot/hero.ts and tell me what its first line is, in one sentence", whose first call, `Read`, is gated) and `p2` (a bare "Hi"), `prompts.txt`. Each run's session record was read with `first-message.mjs` and the table is `trials-summary.txt`; the lead's words are in `trials-detail.txt`.
- **The gate in a headless run.** `claude -p` skips the frontmatter hooks of a project agent (ADR 0042), so the first three runs (`fm-base-p1-1`, `fm-a-p1-1`, `fm-b-p1-1`) met no gate: they show what the lead writes and no hold. For the other **26 runs** the same script (the installed `agents-united-mode-line-gate.js`) was registered as a **settings-level hook** in the folder's `.claude/settings.local.json` (`add-settings-gate.mjs`), which `-p` trusts; the script exempts every call that carries an agent id, so only the lead is gated, as with the frontmatter hook. Variant `e` ran a copy of the script that waits for the saved transcript and logs each decision (`spike-wait-hook.mjs`, `gate-log-variant-e.txt`); the repository's script is the implementation of ADR 0053, written test-first afterwards.

## Results (`trials-summary.txt`)

| Variant | Gated runs | Holds, gate on | Line in an earlier message than the first gated call | Words on "Hi" |
| --- | --- | --- | --- | --- |
| `base` | 3 | 2 and 2 (the line came with the first repeat, and was held again) | **0 of 3** | the line, "I'm Chris", the roster of nine, a question |
| `a` | 4 | 0, 1, 0 (the one hold: the line came in the same message as the call) | 3 of 4 | the line, then "Hi, I'm Chris, the lead for this digital agency team" |
| `b` | 4 | 0, 0, 0 | 4 of 4 (message 1) | the line, then "Hi! I'm Chris, the lead for your digital agency team ..." |
| `c` | 3 | 0, 0, 0 | 3 of 3 (message 1) | "Hi! What would you like to work on?" (no roster) |
| `d` | 3 | 0, 0, 0 | 3 of 3 (message 1) | "Hi! What would you like to work on?" |

1. **Your guess about the welcome holds in the data.** With the welcome in the lead's text, none of 3 task runs wrote the line before its first gated call; with it taken out and the order kept (`a` and `e`), 7 of 8 did, and the eighth wrote it in the same message as the call and was held. The welcome rule gave the second message a second job (the introduction), and the model did the work the hook cannot see.
2. **Taking out "the introduction" is not enough on a greeting.** `a` and `b` still answered "Hi" with "I'm Chris, the lead for ...". The paragraph that names what to leave out and says what a hello gets (`c`, `d`, `e`: 5 of 5 runs, none of the welcome words) is what removed it.
3. **The line as the very first message works for the hook and fails for accuracy.** `b`, `c` and `d` (15 runs) wrote the line first in 15 of 15, and none of their 9 gated runs with the gate on was held. But the line, written from the list the session gives at its start, **disagreed with the lead's own searches in 4 of 15** runs: it put Firecrawl under Missing because the claude.ai connector (`mcp__claude_ai_Firecrawl__...`) was not in the list yet (each time the lead corrected it in its next message, "Correction: Firecrawl turned out to be callable ..."), and in a fifth run the lead named Context7 without having searched for it. An Operation Mode line is the one thing the lead must not get wrong, so it is written after the searches (`e`: 5 of 5 runs, in agreement with the lead's searches each time).
4. **A connector can really be missing.** In `fm-e-p1-1` the claude.ai Firecrawl connector failed to connect with a 503 ("Firecrawl credential validation is temporarily unavailable"; the note is in the `ToolSearch` result), and in `fm-d-p1-3` the search for it found nothing at +5 s, with no note; in both the lead's line said Missing, and that was right as to what the searches returned. The first scoring, against a fixed answer, called them wrong; the table scores each line against that run's own `ToolSearch` results, and counts an integration the lead never searched for as unchecked (`fm-b-p1-1`).
5. **The call being judged is not in the file when the hook runs.** In the four gated runs of `e` the log's first look (`firstOwn: false`) found the text of the line, written 2 to 3 s earlier, and not the `tool_use` block of the call under judgment. So the hook cannot tell "the file has caught up to this call" from "the file is behind": its wait ends on the line or at the cap, nothing else. In these four runs the line was already in the file at the first look (`released`, `by: line`, 1 ms): **headless saves promptly, and the lag of the interactive sessions cannot be reproduced here.**
6. **No hold in `b` to `e`: 0 of 13 gated runs with the gate on** (`b` 3, `c` 3, `d` 3, `e` 4), against 2 of 2 for `base` and 1 of 3 for `a`. With a prompt writer, the order of ADR 0051 plus the welcome out is enough; with the interactive writer, the wait of ADR 0053 is what is meant to cover the lag.

## What the trials say for the decision

- Remove the welcome in the four places it lived and name what is left out (ADR 0053, decisions 1 and 2).
- Keep the order of ADR 0051 (line after the searches), because the line must be accurate (decision 3).
- Add the wait to the hook, because the trials cannot show it is unnecessary: the interactive sessions showed the line missing from the file 2.7 to 6.0 s after it was written, and a lead that follows the new text writes its line only one model round trip (2 to 3 s) before its first gated call (decision 4).

## Not established

- That an interactive session shows no red error. Sitting V (H11) runs G1 and a bare "Hi" and reads the hook's log.
- That the host saves its transcript while the hook polls (the evidence of Sittings T and U suggests it does: two hooks of one message answered differently 0.1 s apart).
- Whether an interactive lead follows the second-message order as the headless lead did (7 of 8, then 5 of 5).
- Runs of the whole roster (R2, R3) were not made.
