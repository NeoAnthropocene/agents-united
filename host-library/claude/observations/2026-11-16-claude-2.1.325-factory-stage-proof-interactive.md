### S4-A1: workers started in the background in an interactive session

In S4 part A (`51a0014c-723f-49d0-9f01-e48220864a36`), the Host started `factory-realizer` in the background (`status: "async_launched"`, main record line 106; `.meta.json` `requestShape: "background"`, `launchedWithDefaults: true`) even though `.claude/agents/factory-realizer.md` sets `background: false` and the prompt requested foreground (line 101). The `Agent` call (line 105) carried only `subagent_type`, `description` and `prompt`, and the coordinator's tool schema (line 19) had no `run_in_background` parameter. The coordinator wrote at line 117: `"The realizer did not start in the foreground: the Host launched it as a background agent, and I have no result from it yet."` and `"My Agent tool has no foreground setting in this session, so I could not request it."` It stopped as its rule requires and asked whether to start `factory-evaluator` anyway; because the instructions gave no answer for that, `factory-evaluator` was never started.

S3 (`17cd59b1-d41d-4dec-be8a-f3a0d54bb0f5`) showed S4-A1 a second time for `factory-evaluator`: one `Agent` call (`M:L412`) with only `description`, `subagent_type` and `prompt` (schema `M:L36` had no `run_in_background`) returned `status: "async_launched"` (`M:L413`), and the worker `.meta.json` recorded `requestShape: "background"`, `launchedWithDefaults: true`, despite `factory-evaluator.md` setting `background: false`. The coordinator stopped (`M:L426`, `M:L430`), did not start the Skill evaluator, and left the returned background review unsaved and unchecked (`M:L446`/`L447`).

The Host documentation in [sub-agents.md](../pages/agent/sub-agents.md) explains this behaviour across three sections:

- Section `"Which subagents run in the background"`: `"With nothing configured, a subagent that Claude spawns from your main conversation starts in the background."` For `claude -p` and the Agent SDK, `"Claude can wait, on its own judgment or when you ask."` For interactive terminal sessions, VS Code, and desktop app sessions, `"to let Claude wait for a subagent, turn off fork mode, which is on by default."`
- Section `"Let Claude wait for a subagent"`: directs turning fork mode off by setting `CLAUDE_CODE_FORK_SUBAGENT` to `0` (for example in `settings.json`), restarting Claude Code, and asking Claude to wait when a result is needed first.
- Section `"Turn fork mode off"`: `"While fork mode is on, Claude also can't wait for a subagent in interactive terminal, VS Code, or desktop sessions on your machine. Fork mode is on by default from Claude Code v2.1.302, and in an interactive terminal session from v2.1.232."`

This explains why the headless `claude -p` runs in [the 2026-11-15 headless record](2026-11-15-claude-2.1.323-factory-stage-proof-headless.md) ran workers in the foreground while the interactive sittings on `2.1.325` launched them in the background.

### S4-A2: the guard fails open when its script is missing

In Step 5 of S4 part A (`51a0014c-723f-49d0-9f01-e48220864a36`), after `.claude\hooks\agents-united-guard.js` was moved away outside the session, `PowerShell` `echo git push --force` (main record line 136) triggered Node failure `MODULE_NOT_FOUND` (`"Error: Cannot find module '<workspace>\s4a-factory-guards\.claude\hooks\agents-united-guard.js'"`, exit code `1`). The Host logged `hook_non_blocking_error` (`"Failed with non-blocking status code:"`, main record line 137) for `PreToolUse:PowerShell` and ran the command (line 138, printing `git`, `push`, `--force`). By design `agents-united-guard.js` blocks by writing to `stderr` and exiting with code `2`; a crashed hook process exits `1`, which the Host treats as non-blocking, so the guard fails open when its script is missing. This was shown for `PowerShell` once; behaviour for `Bash` or other hook failures is not shown. (Disk inspection after the sitting showed `agents-united-guard.js` restored and `agents-united-guard.js.off` absent.)
