# `mcp-image@0.18.0`: the wiring of the three providers, checked with made-up keys (Plan 036 S19, run and read 2026-10-13)

**These are observations of installed builds, not documentation.** Nothing here is a vendor statement; the package is the one pinned in the `mcp-setup` reference. The maintainer holds a Gemini key only. On 2026-10-13 they asked that a user be able to choose the other providers of the image server, that "basic tests" show whether the MCP calls of OpenAI and Seedream work, and that the real generation tests for the providers that were never tested go on the ROADMAP. This is the basic test; Milestone 4 of `ROADMAP.md` holds the rest. **No image was made**, and no real key was used or needed: every key below is a made-up string that names itself.

- **Method:** `mcp-smoke.mjs` (kept in `2026-10-13-provider-wiring-smoke-records/`) starts the server over stdio as a host does (`cmd /c npx -y mcp-image@0.18.0` on Windows, `npx -y mcp-image@0.18.0` elsewhere; protocol 2024-11-05), in a fresh empty folder with `IMAGE_OUTPUT_DIR` inside it and `SKIP_PROMPT_ENHANCEMENT=true`, with a **whitelist of the environment** (the path and the system variables that `npx` needs, and none of the maintainer's: no key variable can reach the server) plus the made-up keys of the case. It sends `initialize`, then `tools/list` or `tools/call` for `generate_image` with the prompt "A plain grey square. Wiring test only; no key is real." and the provider named or not. Windows 11, Node v24.19.0 (from the server's own log). The made-up keys do reach Google, OpenAI and BytePlus, whose APIs refuse them: two or three outgoing requests per provider in a run of the script (it was run twice), none with a real key.
- **Output:** `results.txt` holds the output of all eight cases as the script printed it (the server's replies and the first lines of its own log), and the line "images written: 0".

## The eight cases

| Case | The server's environment | The call | What the server answered |
| --- | --- | --- | --- |
| `list` | a made-up Gemini key, `IMAGE_PROVIDER=gemini` | `tools/list` | server `mcp-image-server` 0.18.0 with one tool, `generate_image`, whose `provider` field takes `gemini`, `openai` or `seedream` ("The provider must have its API key configured on the server") |
| `openai-nokey` | a made-up Gemini key only | `provider: openai` | `CONFIG_ERROR`, "The selected image provider "openai" is not configured on this server."; the suggestion asks to configure `OPENAI_API_KEY`, restart the server and retry with provider "openai"; nothing was sent to OpenAI, and the call did not fall back to Gemini |
| `seedream-nokey` | a made-up Gemini key only | `provider: seedream` | the same `CONFIG_ERROR` for `seedream`, asking for `ARK_API_KEY` |
| `openai-fake` | a made-up OpenAI key only, `IMAGE_PROVIDER=openai` | `provider: openai` | `IMAGE_API_ERROR`, "Failed to generate image with OpenAI", status 401 from OpenAI ("Incorrect API key provided: FAKE_OPE*********************TEST") |
| `seedream-fake` | a made-up `ARK_API_KEY` only, `IMAGE_PROVIDER=seedream` | `provider: seedream` | `IMAGE_API_ERROR`, "Seedream image request was rejected", stage `image_request`, status 401 |
| `gemini-fake` | a made-up Gemini key, `IMAGE_PROVIDER=gemini` | `provider: gemini` | `GEMINI_API_ERROR`, status 400, "API key not valid" |
| `default-openai` | a made-up OpenAI key only, `IMAGE_PROVIDER=openai` | no provider | the same OpenAI 401: the default provider comes from `IMAGE_PROVIDER` |
| `multi-keys` | the three made-up keys, `IMAGE_PROVIDER=gemini` | `provider: openai`, then `seedream`, then none | OpenAI 401, then Seedream 401, then Gemini 400: the provider named in a call answers, and a call that names none goes to the default |

## What this shows

1. **The pinned version starts, lists its tool and takes the provider per call.** The three provider names are an enum of the tool's schema, as the `image-generation` skill assumes.
2. **The calls of OpenAI and Seedream are wired.** The variables that the `mcp-setup` reference names, `OPENAI_API_KEY` and `ARK_API_KEY`, are the ones the server reads, and `IMAGE_PROVIDER=openai` and `IMAGE_PROVIDER=seedream` are accepted. A server with one of these keys and no Gemini key starts, so the two single-provider commands that the reference now prints (OpenAI only, Seedream only) are the shapes that were run. With a made-up key each provider answers 401 from its own API, which is the answer a bad key should get.
3. **The refusals are the ones the skills tell the lead to expect**: a provider named without its key is refused by the server itself ("not configured", the key to configure, a restart), with no call to the provider and no silent fall-back to the default.
4. **Choosing a provider is the user's, and it is already offered**: the digital-agency lead asks one `AskUserQuestion` with an option for each of Gemini, Seedream and OpenAI, and prints the command with the key pair of each provider the user named. What this change adds is a ready command for the user who has one other provider's key and none of Gemini's, so the lead prints it instead of editing the Gemini one.

## A flag, not changed here

OpenAI's refusal echoes the first eight and the last four characters of the key in `details.upstreamMessage` ("FAKE_OPE" and "TEST" above). With a real key this puts `sk-proj-` and the last four characters of the key in a tool result that the designer, and the lead, would see; the skills say never to print a key, and a report that copies the message copies part of one. It is left to the maintainer; the ROADMAP task says what to decide.
