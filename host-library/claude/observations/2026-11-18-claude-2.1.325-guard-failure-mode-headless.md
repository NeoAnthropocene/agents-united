# Claude Code 2.1.325: the guards of ADR 0068 when they cannot run, observed headless (2026-11-18)

**These are observations of one installed build, not documentation.** The guides in `../guide/` cite the vendor's docs snapshots; where this file disagrees with a guide, the guide's authoring notes say so. Nothing here is a vendor promise, and it may change in any release.

[ADR 0068](../../../docs/adr/0068-guard-failure-mode-and-claude-floor.md) lists four things that were built and gated offline and not observed on the Host: the inline form with `onFailure`, the session guard blocking in a plain session, the two-command message, and the block on unreadable input. The maintainer told the lead of the session of 2026-11-18 (an AI session) to observe the first three headless and kept the fourth for himself. The lead ran five headless sessions and wrote this record. No human sat in any of them.

## How the sessions were run

- Claude Code 2.1.325 on Windows 11, `claude -p` with the model `claude-sonnet-5-5`, effort low, permission mode `default`, the tools `Bash`, `PowerShell`, `Write` and `Edit` allowed, `--strict-mcp-config` with no server, a budget cap, stdin closed. The maintainer's subscription.
- The `agents` CLI was a build of `dev` at `69af1cf` (after pull requests 221, 222 and 223).
- Folder S (session guard): a new git folder with `agents add agent-factory -t claude --native --allow-under-construction --copy -y --session-guard project`. `agents doctor --host claude` exited 0 there before the runs.
- Folder I (inline form): a new git folder with `agents add software-engineering -t claude --copy -y`, which writes roles that carry the inline guard in their frontmatter. A headless run does not run a project agent's frontmatter hooks ([ADR 0042](../../../docs/adr/0042-enforce-the-lead-mode-line-with-a-pretooluse-gate.md)), so the lead copied the `hooks` block of `backend-architect.md` unchanged into `.claude/settings.local.json` of that folder. What ran is the same handler (same script, `onFailure: block`, the matchers `Bash` and `Write|Edit|NotebookEdit`) at settings level, not the agent's own hook.
- Each prompt named two tool calls, told the model to make each once and to try no workaround, and asked it to quote any refusal. Prompt P1: `git status --short`, then `git push --force origin main` (the folders have no remote). Prompt P2: `git status --short`, then a `Write` of `notes.txt`.
- "Node missing" means: every PATH entry that holds a `node` executable was removed for that one process; the lead's script printed "node on PATH now: none" before the session started. `claude.exe` is a native program and started without it.
- The evidence is the stream (`--output-format stream-json`) of each session: the tool calls, the tool results the Host returned, and the `permission_denials` of the final result. The model's own summary was not used as evidence.

## What this shows and what it does not

Shown once each, headless, on 2.1.325: with `onFailure: "block"` the Host blocks a shell call and a file write when the guard's `node` cannot be started, for the session guard and for the inline handler at settings level; the session guard's own way-out message reaches the session when its script throws; a healthy guard of either kind still lets a harmless call through and blocks a forced push.

Two things follow from G6 and are not decisions of the lead:

- ADR 0068 says that where `node` cannot start "only the Host's notice remains". In these runs the Host's notice carried the script's source, and with it the text of the two commands. The session of run C read that text and, in its closing summary, advised `agents update --all`, which needs Node as well and would not have run there. The ADR's sentence is still right about what the guard itself can say; the notice is less bare than the ADR assumes and can mislead.
- An ordinary block starts with the words of the failure message, as source. The true reason is at the end, after `]: `. A reader, human or model, who stops early takes a forced-push block for a broken guard. Moving the session guard's script into a file, as the project-scope role guards have it, would shorten the notice to the file's path; that is a design change and was not tried.

Unreadable input is closed by the maintainer with a stated limit (2026-11-18, "You can close this item."): the block on unreadable input is not observable on the Host, because the Host does not produce such input; it is shown offline by the scripts themselves (G7) and by the tests. That exit code 2 from a guard blocks the call on the Host is shown by G1, G2 and G4.

Not shown: everything in the rows above marked so. In particular the agent's own frontmatter hook and what an interactive user sees still need a sitting.
