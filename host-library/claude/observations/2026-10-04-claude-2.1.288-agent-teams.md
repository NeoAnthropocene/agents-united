## What was established

- **A definition's frontmatter hook does not fire for an in-process teammate (probe 1).** The teammate called `Write` on `pwned.txt` and it succeeded; the teammate's transcript has no hook record of any kind. Its metadata reads `taskKind: in_process_teammate`, `customAgentType: probe-neutral`, `permissionMode: auto`. This matches the docs' list of what the host applies to a teammate (tools, model, body; not hooks, not permission mode, not skills), but the docs do not say it, and no guide rule rested on it before.
- **A settings-level guard does fire for a teammate (probe 2).** `writer`'s `echo git push --force` and its `Write` of `.env.test` were both refused with `Blocked by agents-united guard: …`; neither file exists. The block message carried the inline `node -e` script (about 785 characters, the settings-level guard is still the inline form).
- **A teammate's `tools:` list holds (probe 2).** `reviewer`, spawned from the shipped `code-reviewer`, made no `Write` call and said it has no `Write` tool: the allowlist is the least privilege a teammate has.
- **The bundle-scoped role names resolve in a live team (team run).** The lead spawned `ava`, `kaan` and `jamileh` with `Agent {name, subagent_type}`; the three metadata files read `customAgentType: agency-growth-strategist`, `agency-conversion-specialist`, `agency-creative-designer`, all `in_process_teammate`.
- **The lead followed its plan.** First turn: Limited Operational, none of the eight integrations callable, the team named. It checked the team switch with `printenv`, waived the consultation as the user told it, ran Ava first and launched Kaan and Jamileh in the same turn about 20 seconds later, both starting from `strategy.md`; each brief carried objective, scope, acceptance evidence, peers (mode, the peer, the exchange budget) and report format; it verified the files itself at the end. `hero.ts` and `design-tokens.json` agree on `color.cta.primary`.
- **A message to a working teammate is not read mid-turn; it arrives after the turn ends, as a new turn.** Kaan sent his proposal at 11:32:17.8; Jamileh read, wrote and edited through 11:32:48 and never saw it, replied at 11:32:25.8 as if none had been sent, and received Kaan's messages only afterwards, as a new turn. Both teammates' first reports said `Peer messages received: none` (true when written); the late messages arrived, and each teammate reported again as an update. An idle teammate is woken by a message (Jamileh was brought back by Kaan's).
- **The exchange count is ambiguous.** Three messages passed between the pair (Kaan proposed, Jamileh answered, Kaan agreed). Counted as a message and its reply that is two exchanges; the teammates counted messages sent. The wording now defines it.
- **Teammates hold editors and no shell and said so.** Kaan and Jamileh listed "run `tsc`" under `Open items` instead of trying; the lead noted the type-check was not run because TypeScript is not installed.

## Read against the live documentation (2026-10-04, after the runs)

The live page (`code.claude.com/docs/en/agent-teams.md`) was read in full against the package and against the library snapshot (reviewed against 2.1.285). The mechanics the package rests on hold: an `Agent` call with a `name` starts an in-process teammate while the variable is on (and only in an interactive session), a definition gives a teammate its tools, model, body, and now also `effort` and `disallowedTools`, never its skills, hooks or permission mode, and teams are one per session with no nested teams and no resume. The page is newer than the snapshot: it adds `disallowedTools`, `effort`, plugin scope, the wake of a teammate waiting to retry a failed request, `settings.json` `env` as a way to switch teams on or off at run time, and says the team directories are cleaned up when the session ends (there is no cleanup step for the lead). One fact changed the package: **the Task tools are provided by default only on Sonnet 4 to 4.6, Opus 4 to 4.7 and Haiku 4.5**, and on any other model need `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` or an `--allowedTools` entry; the sessions above ran `claude-sonnet-5-5`, the lead never created a task, and the Task tool names appear in its transcript only inside its own definition, which is consistent with the tools being absent but does not prove it. A stand-alone check of whether a `claude-sonnet-5-5` session holds the Task tools has not been run. The lead and the teammates now say how to use the shared task list with and without those tools, how many teammates to start (three to five), to wait for them, to check a stuck task and to shut a teammate down by name.

## The Task tools, and the relay mode run (added the same day)

- **The Task tools are absent by default on `claude-sonnet-5-5` and deferred when switched on (probes A and B, read from the host's `deferred_tools_delta`).** With the variable unset the deferred list has no `TaskCreate`, `TaskGet`, `TaskList` or `TaskUpdate`, and the lead called nothing and said it had no `TaskList`. With `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` all four are listed as deferred tools; the lead loaded `TaskList` through `ToolSearch`, called it, and it returned `No tasks found`. So the lead must check and load them with `ToolSearch`, which its body now says.
- **Relay mode works headless, with teams off (the relay run, Claude Code 2.1.289, run by the authoring session at the maintainer's request).** `claude -p` cannot start a team (the docs say so), so this exercised the default mode of the law. The lead named the mode (relay), ran Ava first in the foreground, then Kaan and Jamileh in the background together; the `Agent` calls carried `name` and the agency-only `subagent_type`, and the three subagent records have no `in_process_teammate` kind: they are ordinary subagents resolved by the scoped role names. **Contract first held:** instead of a peer exchange the lead fixed the colour-token name in both briefs ("CONTRACT, fixed, do not change"), so the two ran in parallel without talking. Every brief carried the five fields with `Peers: relay mode`. The subagents used only `Read` and `Write`: none loaded or called `SendMessage`. Each reported `Peer messages received: none` and its `Open items`; the lead relayed them, said plainly that it had not parsed the JSON or compiled `hero.ts` (its `node` check was denied in headless mode), and reported the files consistent. Noted: the lead declared relay mode without running the environment check its body asks for, and a claude.ai connector notice (Gmail, Calendar) leaked into its summary from the account, unrelated to the package.
- **A live team still needs an interactive session** (the docs: `-p` never spawns teammates). The re-run of the PetPal team with the corrected wording and the task list is the one check left that cannot be done headless. (Done by the maintainer the same evening: see the next section.)

## Defects found, and what became of them

1. **The comms law told teammates to read their inbox between steps.** For an in-process teammate there is no such moment (see above). Fixed test first (`tests/helpers/comms-law.ts`, then the four teammate bodies and the lead): a late message is a new turn, do not wait for a reply, report again with `Peer messages received (update)`, an exchange is one message and its reply, and the old "a finished peer reads nothing until the lead wakes it" is gone.
2. **A role's own frontmatter guard does not protect a teammate** (probe 1). Not a defect of a file but a gap the package must say plainly: the install note, the consent prompt and the doctor warning now do (ADR 0036 decision 4).
3. **The teammates never loaded the Task tools** (the live re-run above). Fixed test first in ADR 0038: the four teammate bodies say the tools arrive deferred and name the `ToolSearch` call, and say what to do without them; `agents start` now sets `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` with the teams variable so the lead's check finds them.

## Defects the full-roster run showed, and what became of them

4. **A task owner set on a running teammate lifted its read-only consultation.** The lead spawned Ava with "READ-ONLY CONSULTATION, write NO files", then set her task's owner at 19:17:26. The host announced it to her as a `task_assignment` message at 19:17:29.575, right after her scope statement, and she wrote `strategy.md` in that turn, before the lead's own "deliver" message arrived at 19:17:44. Owners set before a teammate existed (all the others) announced nothing. Fixed test first in the lead's body (set an owner when the work should start, leave a consulted teammate's task unowned until the consultation is accepted) and in every teammate's body ("a task assignment is not a go-ahead").
5. **A plain-text shutdown request was refused.** Ava answered that it carried no `request_id`; the lead's structured request a moment later was approved, and every later request was structured. The lead's body now says how to ask.

The five roles without a shell now re-read what they wrote and label what they did not check.
