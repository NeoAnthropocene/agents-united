## What happened that the protocol does not ask for, or that differs from it

- **The lead wrote a file itself after the declined schedule.** After "Don't schedule" it ran a `Bash` heredoc (`main` 450), first line `cd "<workspace>"; cat > docs/research/node-sqlite-recheck.md <<'EOF'`, creating `docs/research/node-sqlite-recheck.md`: a manual re-check file with a status line ("there is no schedule", "the user chose "Don't schedule" (R4 declined)"), what a run cannot do, and the specialist's run prompt copied from its R4 entry. It then told the specialist (`main` 451). The dialog's third option had said "Keep the run prompt in the note's handoff", while the lead wrote a separate file. The file is not a schedule; no schedule tool was called. The block does not say what the lead does after a declined `schedule` entry.
- **The form of the declined line.** `R4: declined. The user chose not to schedule anything.` names who (the user) but gives no reason, and not as `declined (who, why)`. The lines `R1: answered`, `R2: answered` and `R3: answered` match the form.
- **Request numbers ran on across the three prompts** (R1 in P1, R2 and R3 in P2, R4 in P3), because the lead continued the one agent for each prompt. The block says numbers are never reused within one piece of work and counts on; it does not say whether a new prompt is a new piece of work. A new piece of work was started with a new instruction, "New task from the user" (`main` 205 and 402), to the same agent, not with a new launch.
- **The lead's own briefs named the section.** The launch brief (`main` 58) said to return "a blocking `ask-user` entry under `Requests for the lead`", gave "2-3 options" and listed the entry's fields (`R<n>`, type, blocking, reason, options, the assumption, what it will do). The lead's definition says to ask for the section in every brief, so this is the lead following its own text, but the run does not separate the effect of the role text from the effect of the brief.
- **The lead did more than relay.** It ran its own searches (four `firecrawl_search` calls, `main` 137, 138, 185, 303), read the finished note (`main` 170), spot-checked the specialist's claims by running its own commands (`main` 262 and 342) and sent corrections (E10). - **R4's entry lacked two fields** the block requires, "If declined or unanswered" and "With the result I will"; the specialist's first schedule entry also said "No ask-user option is needed", yet the lead built a three-option consent question of its own (a session schedule, a cloud routine, no schedule), with "Session schedule (Recommended)" first.
- **The lead announced the consent step before the report arrived** (`main` 425: "I'll ask you before anything is scheduled") and asked it after the report (`main` 443); it did not call any schedule tool.
- **A start dialog the plan for the run did not list:** "Claude in Chrome extension detected ..." with "No, keep browser tools off" as the default; Enter was pressed on it. It is not in the session records.
