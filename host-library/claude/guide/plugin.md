# Claude Code — authoring guide: plugins

Distilled from the snapshots in `host-library/claude/pages/`. Primary sources: [plugins-overview](../pages/plugin/plugins-overview.md), [plugins-components](../pages/plugin/plugins-components.md), [plugins-manifest-reference](../pages/plugin/plugins-manifest-reference.md). Supporting sources: [sub-agents](../pages/agent/sub-agents.md), [mcp](../pages/mcp/mcp.md), [hooks](../pages/hook/hooks.md), [workflows](../pages/orchestration/workflows.md).

A plugin is the unit the native install lane (Plan 032 Phase 7) hands to Claude Code: one directory of skills, agents, hooks, workflows, MCP servers and settings that loads as one unit. Plugin components are more restricted than the same files placed in a project's `.claude/`, so this guide lists what a plugin cannot carry.

## Rules

### Layout and manifest

- **A plugin is a directory of components, usually with a manifest at `.claude-plugin/plugin.json`; every other file sits at the plugin root, not inside `.claude-plugin/`.** The manifest is optional for loading (the name then comes from the marketplace entry or the directory name) but is required by Anthropic's directory; only `name` is required inside it. [Understand what a plugin is](../pages/plugin/plugins-overview.md#understand-what-a-plugin-is), [Manifest file](../pages/plugin/plugins-manifest-reference.md#manifest-file)
- **Standard layout**: `skills/<name>/SKILL.md`, `commands/`, `agents/`, `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `output-styles/`, `workflows/`, `themes/`, `monitors/monitors.json`, `bin/`, `settings.json`. A plugin with a root `SKILL.md`, no `skills/` and no `skills` key loads as a single skill. [Standard layout](../pages/plugin/plugins-manifest-reference.md#standard-layout)
- **`name` is kebab-case with no spaces, `@`, `:` or path separators, and namespaces every component** (`deploy-tools:reviewer`). `version` pins users to that version until you change it; `dependencies` lists plugins that must be enabled. [name](../pages/plugin/plugins-manifest-reference.md#name), [version](../pages/plugin/plugins-manifest-reference.md#version), [dependencies](../pages/plugin/plugins-manifest-reference.md#dependencies)
- **Unknown top-level manifest keys are stripped with a validator warning; unknown keys inside `userConfig`, `channels`, `lspServers` or `monitors` entries are errors and the plugin does not load.** [Unrecognized fields](../pages/plugin/plugins-manifest-reference.md#unrecognized-fields)
- **Every component path in the manifest starts with `./`, resolves inside the plugin root and must exist** (`skills` also accepts `.`, `mcpServers` an `https://` bundle URL). A `..` path is rejected as traversal. [Path rules](../pages/plugin/plugins-manifest-reference.md#path-rules), [Containment and existence](../pages/plugin/plugins-manifest-reference.md#containment-and-existence)
- **Manifest keys either replace, add to, or merge with their default folder.** `commands`, `agents`, `outputStyles`, `workflows`, `experimental.themes` and `experimental.monitors` replace the default scan; `skills` adds to it; `hooks`, `mcpServers` and `lspServers` merge into the default file. Setting a replacing key while the default folder exists produces a warning. [How each key combines with its default location](../pages/plugin/plugins-manifest-reference.md#how-each-key-combines-with-its-default-location)
- **`claude plugin validate <dir>` is the authoritative manifest check**; `--strict` turns warnings into failures for CI, and the MCP checks need v2.1.281+. It does not read `.lsp.json`, so a bad LSP entry is only reported at load in the `/plugin` Errors tab. [Validate the manifest](../pages/plugin/plugins-manifest-reference.md#validate-the-manifest), [LSP servers](../pages/plugin/plugins-components.md#lsp-servers)
- **Instructions in a plugin must be a skill.** A `CLAUDE.md` at the plugin root is not loaded (the validator warns). A rule that must hold every time belongs in a hook, not a skill. [Skills](../pages/plugin/plugins-components.md#skills)

### Components and their plugin-specific limits

- **Skills**: add to `skills/`; invoked as `/<plugin>:<dir>`; the manifest `skills` key adds more directories without replacing the default. **Commands** are the older format; write new ones as skills. [Skills](../pages/plugin/plugins-components.md#skills), [Commands](../pages/plugin/plugins-components.md#commands)
- **Agents**: Markdown files under `agents/`, named `<plugin>:<name>` (subfolders join the scoped name); the supported frontmatter is `name`, `description`, `model`, `effort`, `maxTurns`, `tools`, `disallowedTools`, `skills`, `memory`, `background`, `omitClaudeMd`, `isolation` and the `experimental.cacheTtl` key, and `permissionMode`, `hooks`, `mcpServers` and `initialPrompt` are ignored. An agent whose frontmatter does not parse still loads with every field ignored. [Agents](../pages/plugin/plugins-components.md#agents), [Frontmatter fields in plugin agents](../pages/plugin/plugins-components.md#frontmatter-fields-in-plugin-agents)
- **Hooks**: `hooks/hooks.json` under a top-level `"hooks"` key, same shape as `settings.json`; they register at plugin load and fire for the whole session. Add the hook and MCP server the agent cannot declare at plugin level. [Hooks](../pages/plugin/plugins-components.md#hooks), [When plugin hooks fire](../pages/plugin/plugins-components.md#when-plugin-hooks-fire)
- **Workflows**: `.js` files in `workflows/`, namespaced `/<plugin>:<meta.name>`. [Distribute a workflow in a plugin](../pages/orchestration/workflows.md#distribute-a-workflow-in-a-plugin)
- **MCP servers**: `.mcp.json` at the plugin root (with or without the `mcpServers` wrapper) or inline/`.mcpb` in the manifest; the server registers as `plugin:<plugin>:<server>` and its tools are `mcp__plugin_<plugin>_<server>__<tool>`, the name to use in permission rules, a skill's `allowed-tools`, a subagent's `tools` and a hook matcher. [MCP servers](../pages/plugin/plugins-components.md#mcp-servers), [Server names, tool names, and reloads](../pages/plugin/plugins-components.md#server-names-tool-names-and-reloads), [Plugin-provided MCP servers](../pages/mcp/mcp.md#plugin-provided-mcp-servers)
- **`bin/` executables go on the Bash tool's PATH while the plugin is enabled, after the user's own PATH entries, so a plugin cannot shadow `git` or `ls`.** claude.ai and Cowork do not install a plugin that has a top-level `bin/`. [Executables](../pages/plugin/plugins-components.md#executables)
- **A plugin `settings.json` can set only `agent` and `subagentStatusLine`; every other key is dropped.** `agent` runs one of the plugin's own agents as the session's main thread. `settings.json` beats the manifest `settings` key, and the user's own `agent` setting beats the plugin's. [Default settings](../pages/plugin/plugins-components.md#default-settings), [settings](../pages/plugin/plugins-manifest-reference.md#settings)
- **Monitors** start in interactive sessions only, never with `-p`, only where the Monitor tool exists, cannot reference `${user_config.*}`, and keep running after the plugin is disabled mid-session. [Monitors](../pages/plugin/plugins-components.md#monitors)
- **LSP servers are configuration only**: the plugin declares `command` and `extensionToLanguage`; the user installs the binary, each extension gets one server, and a server must write logs to stderr because stdout is protocol. [LSP servers](../pages/plugin/plugins-components.md#lsp-servers)

### Paths, configuration and runtime

- **Reference plugin files through `${CLAUDE_PLUGIN_ROOT}` (changes on every update, so never write state there), `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/<id>/`, survives updates) and `${CLAUDE_PROJECT_DIR}`.** Substitution applies in hook and monitor commands, MCP `command`, `args`, `env`, `url`, `headers`, LSP fields, and in skill, command and agent bodies. The variables are not present in the environment of commands Claude runs through Bash. [Environment variables](../pages/plugin/plugins-manifest-reference.md#environment-variables), [Reference plugin paths and store data](../pages/plugin/plugins-components.md#path-variables-and-persistent-data)
- **`userConfig` prompts the user for values** (types `string`, `number`, `boolean`, `directory`, `file`; `sensitive: true` masks and stores in secure storage). The dialog appears only in interactive `/plugin` flows; `claude plugin install` never prompts, and values are passed with `--config KEY=VALUE`. Exec-form hooks may use `${user_config.*}`; shell-form hooks must read `$CLAUDE_PLUGIN_OPTION_<KEY>` instead. [Ask the user for configuration values](../pages/plugin/plugins-components.md#user-configuration), [User configuration](../pages/plugin/plugins-manifest-reference.md#user-configuration), [Exec form and shell form](../pages/hook/hooks.md#exec-form-and-shell-form)
- **Load and test without a marketplace**: `claude --plugin-dir <dir>`, then `/reload-plugins` after adding a component; a reload keeps MCP connections of unchanged servers. Skill text edits are live, but `hooks/`, `.mcp.json`, `agents/` and `output-styles/` need the reload. [Add components to a plugin](../pages/plugin/plugins-components.md#add-components-to-a-plugin), [Server names, tool names, and reloads](../pages/plugin/plugins-components.md#server-names-tool-names-and-reloads), [Make an installed plugin available in your session](../pages/plugin/plugins-overview.md#make-an-installed-plugin-available-in-your-session)
- **An enabled plugin costs context in every session.** The name and description of each model-invocable skill, agent and command load every turn even when nothing from the plugin runs; its MCP servers run alongside each session and its hooks fire on their events. Keep descriptions short. [What an enabled plugin adds to your sessions](../pages/plugin/plugins-overview.md#what-an-enabled-plugin-adds-to-your-sessions)
- **A plugin runs as the user.** What its hooks, MCP servers and scripts run, they run as the user, so review them like any code. Administrators can block plugin hooks with `allowManagedHooksOnly`. [What an enabled plugin adds to your sessions](../pages/plugin/plugins-overview.md#what-an-enabled-plugin-adds-to-your-sessions), [Hook locations](../pages/hook/hooks.md#hook-locations)

## Authoring notes (agents-united, not host behaviour)

- The native install lane copies committed files and records marker plus hash. If the agents-united package is delivered as a Claude Code plugin, the reviewer's read-only hook must be registered at plugin level (`hooks/hooks.json`, matcher on the tool names), because the agent file cannot carry `hooks`.
- If the same role must keep frontmatter `hooks` or `mcpServers`, deliver it as a project or user agent file instead, and say so in the profile.
- Not snapshotted: plugin install, marketplace, CLI reference and troubleshooting pages. Add them to `sources.json` before authoring marketplace publishing steps.
