# Claude Code — authoring guide: permissions, modes and enforcement

Distilled from the snapshots in `host-library/claude/pages/`. Primary sources: [permissions](../pages/permissions/permissions.md), [permission-modes](../pages/permissions/permission-modes.md). Supporting sources: [tools-reference](../pages/tools/tools-reference.md), [sub-agents](../pages/agent/sub-agents.md), [hooks](../pages/hook/hooks.md).

This guide is the input for the `permissions` block of `registry/hosts/claude/profile.json` and for the guard design of each role: what the host enforces itself (rules, modes, protected paths), what only a hook can enforce, and what no mechanism guarantees. Permission rules are enforced by Claude Code, not by the model; instructions in a prompt or `CLAUDE.md` shape what Claude tries but change nothing about what is allowed. [Manage permissions](../pages/permissions/permissions.md#manage-permissions)

## Rules

### Rule evaluation

- **Evaluation order is deny, then ask, then allow; the first match decides and specificity never changes the order.** A broad `Bash(aws *)` deny blocks a call that a narrower `Bash(aws s3 ls)` allow also matches; a matching ask rule prompts even when a more specific allow rule matches. [Manage permissions](../pages/permissions/permissions.md#manage-permissions)
- **A deny at any level cannot be allowed by any other level.** Managed settings sit highest and no command-line argument overrides a managed rule; a user-level deny beats a project-level allow. `--disallowedTools` can add restrictions beyond managed settings. [Settings precedence](../pages/permissions/permissions.md#settings-precedence)
- **Syntax is `Tool` or `Tool(specifier)`.** A bare name matches every use and, as a deny, removes the tool from Claude's context; a scoped rule leaves the tool and blocks matching calls. `Bash(*)` equals `Bash`. Deny and ask (not allow) can also match a scalar input parameter with `Tool(param:value)`, for example `Agent(model:opus)`. [Match all uses of a tool](../pages/permissions/permissions.md#match-all-uses-of-a-tool), [Match by input parameter](../pages/permissions/permissions.md#match-by-input-parameter)
- **Put the `*` after the subcommand in Bash rules.** `Bash(git log *)` allows only `git log`, `Bash(git *)` allows every git command (including `git -c core.fsmonitor=... diff`), and a trailing ` *` also matches the bare command. `Bash(git * main)` triggers a startup warning. [Wildcard patterns](../pages/permissions/permissions.md#wildcard-patterns)
- **A Bash rule matches command text, not intent, so it is not a security boundary.** `Bash(curl *)` misses `/usr/bin/curl` and `sh -c 'curl ...'`; `Bash(git push *)` misses `git -C . push`. A fixed list of wrappers (`timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, `noglob`, bare `xargs`) is stripped before matching, environment runners such as `npx` or `docker exec` are not. Compound commands are split at `&&`, `||`, `;`, `|` and newlines and every part must match. [Compound commands](../pages/permissions/permissions.md#compound-commands), [Wrappers](../pages/permissions/permissions.md#process-wrappers), [What a Bash rule doesn't match](../pages/permissions/permissions.md#bash-rule-limits)
- **Use sandboxing or a hook when a restriction must hold.** Sandboxing is OS-level enforcement for Bash, PowerShell and Monitor commands and complements permissions; a `PreToolUse` hook can inspect the whole command text. Constraining `curl` by URL in a Bash rule is fragile, so deny the network tools and allow `WebFetch(domain:...)`. [What a Bash rule doesn't match](../pages/permissions/permissions.md#bash-rule-limits), [How permissions interact with sandboxing](../pages/permissions/permissions.md#how-permissions-interact-with-sandboxing)
- **File rules**: `Edit(...)` rules cover every built-in file-editing tool; `Read(...)` rules are best effort across Grep, Glob, `@` mentions and IDE context; a `Read` deny also blocks Edit and Write on that path, but not `NotebookEdit`, which needs its own `Edit` deny. Bash redirects (`>`, `>>`, `<`, `tee`) are checked against these rules. [Read and Edit](../pages/permissions/permissions.md#read-and-edit), [Redirections](../pages/permissions/permissions.md#redirections)
- **A built-in, non-configurable set of read-only Bash commands runs without a prompt in every mode** (`ls`, `cat`, `grep`, `find`, `git` read forms, and so on), with listed exceptions such as unquoted globs on write-capable flags and unparseable commands. A "read-only" role that keeps Bash is therefore only as read-only as its hook. [Read-only commands](../pages/permissions/permissions.md#read-only-commands)
- **MCP, subagent and skill rules**: `mcp__server`, `mcp__server__*`, `mcp__server__tool`; `Agent(Explore)`, `Agent(my-agent)` to disable a subagent; `Skill(name)` and `Skill(name *)`. `--disallowedTools "Agent(Explore)"` does the same on the command line. [MCP](../pages/permissions/permissions.md#mcp), [Agent (subagents)](../pages/permissions/permissions.md#agent-subagents), [Disable specific subagents](../pages/agent/sub-agents.md#disable-specific-subagents)

### Modes

- **Six modes**: `default` (Manual; reads only), `acceptEdits` (reads, edits and common filesystem commands in the working directories), `plan` (read-only exploration), `auto` (everything, with a background classifier), `dontAsk` (pre-approved tools only; anything that would prompt is denied) and `bypassPermissions`. `manual` is an alias for `default` from v2.1.200; hooks always receive `"default"`. [Available modes](../pages/permissions/permission-modes.md#available-modes), [Permission modes](../pages/permissions/permissions.md#permission-modes)
- **Deny rules block in every mode, `bypassPermissions` included; allow rules have no effect there.** Some actions are never auto-approved in any mode: tools matched by an ask rule, tools that need user interaction (`AskUserQuestion`, MCP tools flagged `requiresUserInteraction`), organization connector tools set to `ask`, `rm`/`rmdir` on a critical path, and reads outside the working directories when `blockReadsOutsideWorkingDirectories` is on. [Actions no mode auto-approves](../pages/permissions/permission-modes.md#actions-no-mode-auto-approves)
- **`dontAsk` is the mode for unattended runs**: prompts become denials, explicit ask rules are denied, and `AskUserQuestion` is denied even if allowed. Cloud sessions ignore `defaultMode: "dontAsk"` and `"bypassPermissions"` from settings files. [Allow only pre-approved tools with dontAsk mode](../pages/permissions/permission-modes.md#allow-only-pre-approved-tools-with-dontask-mode), [Skip all checks with bypassPermissions mode](../pages/permissions/permission-modes.md#skip-all-checks-with-bypasspermissions-mode)
- **`bypassPermissions` offers no protection against prompt injection.** It cannot be entered from a session started without it, is refused as root or under `--restricted`, and can be disabled with `permissions.disableBypassPermissionsMode: "disable"` (and `disableAutoMode` for auto) in any settings file, typically managed. [Skip all checks with bypassPermissions mode](../pages/permissions/permission-modes.md#skip-all-checks-with-bypasspermissions-mode), [Permission modes](../pages/permissions/permissions.md#permission-modes)
- **Protected paths are never auto-approved** except in `bypassPermissions`: `.git`, `.vscode`, `.idea`, `.husky`, `.devcontainer`, `.claude` (except `.claude/worktrees`), shell rc files, `.gitconfig`, `.npmrc`, `.mcp.json`, `.claude.json` and similar. `permissions.allow` rules in settings do not pre-approve them; `dontAsk` denies them and `auto` routes them to the classifier. [Protected paths](../pages/permissions/permission-modes.md#protected-paths)
- **`rm` and `rmdir` on a critical path (root, home, working directory) are never approved by an allow rule or a hook `allow`**, even in modes that skip other prompts; only a deny rule blocks them outright. [Critical paths](../pages/permissions/permission-modes.md#critical-paths)
- **Plan mode is read-only exploration but is not enforced in an interactive terminal session where `bypassPermissions` is available**; it is enforced in `-p`, SDK and VS Code chat sessions. [Skip all checks with bypassPermissions mode](../pages/permissions/permission-modes.md#skip-all-checks-with-bypasspermissions-mode)
- **A subagent's mode is the parent's unless the parent is `default`, `dontAsk` or `plan`.** Under `bypassPermissions`, `acceptEdits` or auto the parent's mode wins and the agent's `permissionMode` is ignored; teammates start in the lead's mode (except `dontAsk`). [Permission modes](../pages/agent/sub-agents.md#permission-modes), [Permissions](../pages/orchestration/agent-teams.md#permissions)

### Hooks, working directories and trust

- **A `PreToolUse` hook runs before the permission prompt for every tool except `EndConversation`, but it cannot override rules.** Deny and ask rules still apply after a hook `allow`, and a hook that exits 2 blocks even when an allow rule matches. [Extend permissions with hooks](../pages/permissions/permissions.md#extend-permissions-with-hooks), [PreToolUse decision control](../pages/hook/hooks.md#pretooluse-decision-control)
- **Working directories**: Claude can read the launch directory freely; extend it with `--add-dir`, `/add-dir` or `permissions.additionalDirectories`. `additionalDirectories` in a settings file grants file access only and loads no configuration; `--add-dir` additionally loads skills, commands and subagents (and `enabledPlugins`). [Working directories](../pages/permissions/permissions.md#working-directories), [Additional directories grant file access, not configuration](../pages/permissions/permissions.md#additional-directories-grant-file-access-not-configuration)
- **Project `permissions.allow` rules and `additionalDirectories` apply only after the user accepts the workspace trust dialog** (`deny` and `ask` are unaffected because they only restrict). `-p` and SDK sessions never show the dialog and treat the folder as trusted for hooks, so a package must not assume a prompt guarded its own allow rules. [Project allow rules and workspace trust](../pages/permissions/permissions.md#project-allow-rules-and-workspace-trust), [What runs before you trust a folder](../pages/permissions/permissions.md#what-runs-before-you-trust-a-folder)
- **"Yes, and don't ask again" saves rules to `.claude/settings.local.json` at the repository root** (resolved through worktrees) for Bash commands and WebFetch domains; file-edit approvals last only until the session ends. Ship pre-approved rules in a committed settings file or a plugin instead of relying on that. [Permission system](../pages/permissions/permissions.md#permission-system)
- **Managed settings can lock the policy**: `allowManagedPermissionRulesOnly` makes managed rules the only source, and the `disable*Mode` keys and `allowManagedHooksOnly` are typically set there. A native package must expect its own allow rules and hooks to be ignored under those locks. [Managed settings](../pages/permissions/permissions.md#managed-settings), [Hook locations](../pages/hook/hooks.md#hook-locations)
- **`Cd(...)` rules govern only the user's `/cd`**; Claude cannot call it. Adding any `Cd` allow rule switches `/cd` to allowlist mode. [Cd](../pages/permissions/permissions.md#cd)

## Authoring notes (agents-united, not host behaviour)

- Recommended posture for a read-only reviewer package: allowlist `Read`, `Grep`, `Glob`, `LSP`, `WebFetch`, `WebSearch`, `ReportFindings` (no `Bash` unless required), a `PreToolUse` hook for anything that mutates, and no `memory` key; do not put the guarantee in `permissionMode` or in prose.
- Destructive-command guard for implementers: a `PreToolUse` hook on `Bash|PowerShell` plus deny rules for the commands that must never run, tested against the wrapper and `sh -c` bypass forms listed above.
- Not snapshotted: the settings reference, the managed-settings page, sandboxing and the auto-mode classifier configuration page. Add them before authoring org policy, sandbox settings or classifier rules.
