# Claude Code — authoring guide: orchestration (subagents, agent teams, dynamic workflows)

Distilled from the snapshots in `host-library/claude/pages/`. Primary sources: [workflows](../pages/orchestration/workflows.md), [workflow-authoring](../pages/orchestration/workflow-authoring.md) (the reference bundled inside Claude Code since 2.1.248, captured through a session; see `sources.json`), [agent-teams](../pages/orchestration/agent-teams.md), [features-overview](../pages/orchestration/features-overview.md). Supporting sources: [sub-agents](../pages/agent/sub-agents.md), [tools-reference](../pages/tools/tools-reference.md), [plugins-components](../pages/plugin/plugins-components.md).

Native orchestration output lands in `registry/hosts/claude/workflows/*.js` (installed to `.claude/workflows/`) and in the orchestrator agent files. The core invariants "parallel slices fan out in one turn, with one synthesis point" and "never busy-poll" bind to the mechanisms below. Note the vocabulary clash: a *workflow skill* is ours (`registry/skills/workflow-*`), a *dynamic workflow* is Claude Code's JavaScript orchestration; see `CONTEXT.md`.

## Rules

### Choosing the mechanism

- **Decide by who holds the plan.** With subagents, skills and agent teams Claude (or the lead) decides turn by turn and results land in a context window; in a workflow the script holds the loop, the branching and the intermediate results, so Claude's context receives only the final answer. Scale: subagents a few delegated tasks per turn, teams a handful of long-running peers, workflows dozens to hundreds of agents per run. [When to use a workflow](../pages/orchestration/workflows.md#when-to-use-a-workflow), [Subagent vs Dynamic workflow](../pages/orchestration/features-overview.md#compare-similar-features)
- **Use `Agent` subagents for a quick, focused worker (research a question, verify a claim, review a file) and a workflow when the job outgrows a handful of subagents** or the findings must be cross-checked before you see them (codebase-wide audit, large migration, a plan drafted from several angles). [Subagent vs Dynamic workflow](../pages/orchestration/features-overview.md#compare-similar-features), [When to use a workflow](../pages/orchestration/workflows.md#when-to-use-a-workflow)
- **Parallel subagents return their results into the caller's context**, so many detailed reports cost context and each subagent spends tokens of its own. Fan out only independent paths, and expect at most 20 concurrent subagents by default (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, v2.1.217+). [Run parallel research](../pages/agent/sub-agents.md#run-parallel-research), [Concurrent subagent limit](../pages/agent/sub-agents.md#concurrent-subagent-limit)
- **Use agent teams only when teammates must share findings, challenge each other or coordinate on their own.** They add overhead and cost significantly more tokens; sequential work and same-file edits fit a single session or subagents better. [When to use agent teams](../pages/orchestration/agent-teams.md#when-to-use-agent-teams), [Compare with subagents](../pages/orchestration/agent-teams.md#compare-with-subagents)
- **A skill that fans work out is still just instructions**; it becomes a repeatable orchestration only when written as a workflow script. Claude can be pointed at an existing folder of subagent prompts or a fan-out skill and asked to produce the equivalent workflow. [Ask for a workflow in your prompt](../pages/orchestration/workflows.md#ask-for-a-workflow-in-your-prompt), [When to use a workflow](../pages/orchestration/workflows.md#when-to-use-a-workflow)

### Who can launch a workflow

- **`Workflow` is never available to subagents**, even when listed in `tools`. The orchestrator that launches workflows must therefore run as the main thread (`claude --agent <name>`, or a plugin `settings.json` with `"agent": "<name>"`), not as a delegated subagent. [Available tools](../pages/agent/sub-agents.md#available-tools), [Default settings](../pages/plugin/plugins-components.md#default-settings)
- **Workflows are on paid plans, the API and Bedrock, Vertex and Foundry; Pro needs the Dynamic workflows row in `/config`.** `disableWorkflows`, `CLAUDE_CODE_DISABLE_WORKFLOWS=1` or a managed setting removes the bundled workflow commands, the `/workflow-authoring` skill and the `ultracode` keyword; a run already in progress keeps going. [Run a bundled workflow](../pages/orchestration/workflows.md#run-a-bundled-workflow), [Turn workflows off](../pages/orchestration/workflows.md#turn-workflows-off)
- **The `ultracode` keyword only opts in from a prompt the user types** (interactive prompt, IDE panel, Remote Control, or an SDK app that stamps human input). It does not start a workflow from `-p`, unstamped SDK input, a scheduled prompt or a relayed webhook or PR comment (v2.1.210+), so automation must call the saved workflow by name instead. [Where the keyword works](../pages/orchestration/workflows.md#where-the-keyword-works)
- **Launch approval depends on permission mode.** Auto asks on first launch only (skipped with ultracode), Manual and acceptEdits ask every run unless "don't ask again" was chosen for a named workflow, bypass never asks. In `-p` and the SDK there is no prompt: allow `Workflow` or `Workflow(<name>)`, use auto or bypass mode, or a `PreToolUse` hook that returns `allow`. [Approve the plan before it runs](../pages/orchestration/workflows.md#approve-the-plan-before-it-runs)

### Writing the script

- **A saved workflow is a `.js` file: `export const meta = { name, description, phases? }` first, then a plain-JavaScript body with top-level `await`.** `meta` must be a pure object literal (a variable, call or spread makes Claude Code drop `/<name>` from autocomplete); each `phases` entry must equal the title passed to `phase()`. [What the saved script looks like](../pages/orchestration/workflows.md#what-the-saved-script-looks-like), [Edit a saved script](../pages/orchestration/workflows.md#edit-a-saved-script)
- **The runtime API is `agent()`, `pipeline()`, `parallel()`, `phase()`, `log()` and the `args` global.** There is no module loading (a script containing `import()` fails before the run starts), no direct filesystem or shell access from the script itself (agents do the work), and no user input mid-run (split stages into separate workflows when sign-off is needed). [Behavior and limits](../pages/orchestration/workflows.md#behavior-and-limits), [Edit a saved script](../pages/orchestration/workflows.md#edit-a-saved-script)
- **`Date.now()`, `Math.random()` and a no-argument `new Date()` throw inside a script**, so a relaunched run repeats the same `agent()` calls. Pass a timestamp or seed in through `args`. [Edit a saved script](../pages/orchestration/workflows.md#edit-a-saved-script)
- **`agent()` resolves to `null` if the agent is stopped or hits an unrecoverable API error, and `pipeline()` keeps each `null`** in its result array, so end with `.filter(Boolean)`. [What the saved script looks like](../pages/orchestration/workflows.md#what-the-saved-script-looks-like)
- **Pass a `schema` to an `agent()` call to get JSON instead of prose.** Claude Code rejects a schema it can prove contradictory before the subagent starts (for example a `required` key that `additionalProperties: false` rules out) and fails the call after five invalid outputs (`MAX_STRUCTURED_OUTPUT_RETRIES`). [What the saved script looks like](../pages/orchestration/workflows.md#what-the-saved-script-looks-like)
- **Hard limits**: 16 concurrent agents by default (fewer on few CPUs; `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` 1 to 256, v2.1.269+), 4,096 items in one `parallel()` or `pipeline()`, 1,000 agents per run. [Behavior and limits](../pages/orchestration/workflows.md#behavior-and-limits)
- **Use the quality patterns the runtime is built for**: independent agents that adversarially verify each other's findings, a checker loop that stops when two rounds make no progress, per-file isolated copies for migrations, and one agent that ranks and deduplicates per-file findings. [Example workflow prompts](../pages/orchestration/workflows.md#example-workflow-prompts), [When to use a workflow](../pages/orchestration/workflows.md#when-to-use-a-workflow)

- **`agent()` takes more options than the public page documents: `agent(prompt, {label, phase, schema, model, effort, isolation, agentType})`.** `agentType` runs a named custom subagent type (for example `'code-reviewer'`, resolved from the same registry as the `Agent` tool) instead of the default workflow subagent and composes with `schema`; `isolation: 'worktree'` runs the agent in a fresh git worktree and costs setup per agent, so use it only when parallel agents mutate files that would otherwise conflict; `model` and `effort` override one call (omit them to inherit the session; use `'low'` effort for mechanical stages and higher tiers only for verify and judge stages); `phase` assigns the agent to a progress group inside `pipeline()`/`parallel()` stages. [Workflow authoring reference](../pages/orchestration/workflow-authoring.md)
- **Default to `pipeline()`; use `parallel()` only as a barrier.** `pipeline(items, stage1, stage2, ...)` has no barrier between stages and passes each stage `(prevResult, originalItem, index)`; a stage that throws drops that item to `null`. A barrier is right only when a stage needs cross-item context: dedup or merge before expensive verification, an early exit on zero findings, or a prompt that compares against the other findings. Flattening, mapping or filtering is not a reason for a barrier. [Workflow authoring reference](../pages/orchestration/workflow-authoring.md)
- **A saved workflow can call another with `workflow(nameOrRef, args)`, one level deep.** The child shares the run's concurrency cap, agent counter, abort signal and token budget, and `workflow()` inside a child throws. Throws on an unknown name or a child syntax error, so catch it. [Workflow authoring reference](../pages/orchestration/workflow-authoring.md)
- **`budget` is the turn's token target (the `+500k` directive), shared across the main loop and every workflow, and a hard ceiling.** `budget.total` is `null` when no target was set, so guard any loop with `budget.total &&`; otherwise `remaining()` is `Infinity` and the loop runs to the 1,000-agent cap. [Workflow authoring reference](../pages/orchestration/workflow-authoring.md)
- **Concurrent `agent()` calls are capped at `min(16, available CPUs - 2)` per workflow; excess calls queue.** A fan-out of 100 items still completes. Log what a bound dropped (top-N, sampling, no retry): silent truncation reads as full coverage. [Workflow authoring reference](../pages/orchestration/workflow-authoring.md)
- **The `Workflow` tool takes `script` (inline), `scriptPath`, `args` and `resumeFromRunId`; `args` must be real JSON values, not a JSON-encoded string** (a stringified list reaches the script as one string). To resume, relaunch with the same script and args: the longest unchanged prefix of `agent()` calls returns cached results, and `journal.jsonl` in the transcript directory records each agent's actual return value. [Workflow authoring reference](../pages/orchestration/workflow-authoring.md#resume)
- **Workflow agents reach every session-connected MCP tool through `ToolSearch`, loading schemas on demand,** and they receive the same CLAUDE.md files the launcher got, so a prompt should name a rule instead of pasting it. Interactively authenticated MCP servers may be absent in headless or scheduled runs. [Workflow authoring reference](../pages/orchestration/workflow-authoring.md)
- **`meta` may also carry `whenToUse` (shown in the workflow list), and each `phases` entry may carry a `detail`.** Scripts are plain JavaScript, never TypeScript: annotations, interfaces and generics fail to parse. [Workflow authoring reference](../pages/orchestration/workflow-authoring.md)
- **The size guideline defaults to `medium` (under 10 agents), or `small` (under 5) when signed in on a Pro plan with v2.1.271 or later.** It advises Claude how large a workflow to write, not a cap on a saved script; the `Large workflow` warning still appears above 25 agents. [Set a size guideline](../pages/orchestration/workflows.md#set-a-size-guideline), [Cost](../pages/orchestration/workflows.md#cost)
- **After adding or editing a saved workflow, `/reload-skills` re-reads the workflow directories in the running session.** Run `/<name>` again afterwards. [Edit a saved script](../pages/orchestration/workflows.md#edit-a-saved-script)

### Saving, distributing and resuming

- **Save to `.claude/workflows/` (project, shared) or `~/.claude/workflows/` (personal); it then runs as `/<name>`.** A project workflow beats a personal one of the same name; in a monorepo the closest `.claude/workflows/` wins. Saving refuses symlinked `.claude` or `.claude/workflows` locations. [Save the workflow for reuse](../pages/orchestration/workflows.md#save-the-workflow-for-reuse)
- **Ship workflows in a plugin's `workflows/` directory (or the `workflows` manifest key, which replaces the default scan).** They are namespaced by the plugin name, so `meta.name: release-audit` in `acme-tools` runs as `/acme-tools:release-audit`. [Distribute a workflow in a plugin](../pages/orchestration/workflows.md#distribute-a-workflow-in-a-plugin), [How each key combines with its default location](../pages/plugin/plugins-manifest-reference.md#how-each-key-combines-with-its-default-location)
- **A saved workflow takes input through the `args` global** (structured data, `undefined` when omitted); Claude passes a list as an array. [Pass input to a saved workflow](../pages/orchestration/workflows.md#pass-input-to-a-saved-workflow)
- **Runs resume within the same session by replaying agents in start order.** A completed agent returns its saved result until the first agent whose prompt differs (after an edit) or that failed; that agent and every later one run again. Order stages so stable, expensive work starts first. [Resume after a pause](../pages/orchestration/workflows.md#resume-after-a-pause)
- **The subagents a workflow spawns use the session's permission rules and choose their permission mode and model the way subagents do.** Add the tools a long run needs to the allow rules before starting, because a run pauses on agent permission prompts. [Approve the plan before it runs](../pages/orchestration/workflows.md#approve-the-plan-before-it-runs), [Cost](../pages/orchestration/workflows.md#cost)
- **Watch cost.** A run over 25 agents or a projected 1.5 million tokens shows a `Large workflow` warning; `workflowSizeGuideline` (`unrestricted`, `small` under 5, `medium` under 10, `large` under 50) advises Claude how big to write a workflow. Try one directory or a narrow question first. [Cost](../pages/orchestration/workflows.md#cost), [Set a size guideline](../pages/orchestration/workflows.md#set-a-size-guideline)
- **Matching agents share a prompt-cache prefix**: same model, effort, agent type, tools, schema and working directory. Claude Code staggers the rest of a fan-out until the first agent's response begins (`CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS`, default 5,000), and workflow agents cache for five minutes unless `subagentPromptCacheTtl` is `1h`. [Prompt caching in a fan-out](../pages/orchestration/workflows.md#prompt-caching-in-a-fan-out)

### Never busy-poll

- **Background work reports back on its own.** A background subagent's result arrives as a completion notification in a later turn, and Claude waits for it before reporting; a background Bash command notifies its owner when it ends. Do not loop on status checks. [Run subagents in foreground or background](../pages/agent/sub-agents.md#run-subagents-in-foreground-or-background), [Background commands](../pages/tools/tools-reference.md#background-commands)
- **`Monitor` turns a log, a CI status or a WebSocket into events** delivered to the conversation; plugin `monitors/monitors.json` can start one at session start or on first use of a skill. [Monitor tool](../pages/tools/tools-reference.md#monitor-tool), [Monitors](../pages/plugin/plugins-components.md#monitors)

### Agent teams (opt-in)

- **Agent teams are experimental and off by default**: set `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`. Enabling them changes ordinary delegation, because a subagent Claude names launches as a teammate (unless it is a fork or passes `isolation`). Teams need an interactive session; `-p` and SDK runs spawn plain subagents. [Enable agent teams](../pages/orchestration/agent-teams.md#enable-agent-teams), [How Claude starts agent teams](../pages/orchestration/agent-teams.md#how-claude-starts-agent-teams)
- **A teammate can reuse a subagent definition**: `tools` (plus `SendMessage` and, where available, the Task tools), `model` and the body apply; `skills` never apply, and `mcpServers` apply only to split-pane teammates. [Use subagent definitions for teammates](../pages/orchestration/agent-teams.md#use-subagent-definitions-for-teammates)
- **Teams have hard limits**: one team per session, no nested teams, the lead is fixed, no resumption of in-process teammates, split panes need tmux or iTerm2. Teammates start in the lead's permission mode (except `dontAsk`) and their permission prompts appear in the lead session. [Limitations](../pages/orchestration/agent-teams.md#limitations), [Permissions](../pages/orchestration/agent-teams.md#permissions)
- **Gate team work with hooks** (`TeammateIdle`, `TaskCreated`, `TaskCompleted`, exit 2) and give teammates the context they need, since the lead's conversation history does not carry over. [Enforce quality gates with hooks](../pages/orchestration/agent-teams.md#enforce-quality-gates-with-hooks), [Context and communication](../pages/orchestration/agent-teams.md#context-and-communication)

## Authoring notes (agents-united, not host behaviour)

- Classify each `workflow-*` skill as `pipeline` (fan-out with a synthesis or verification stage, so becomes a script here plus a thin skill or command trigger) or `runbook` (single-agent, stays a skill).
- Test every committed workflow as plain JavaScript: parses cleanly, first statement is a literal `meta`, no `import`, no `Date.now`/`Math.random`, and every `phase()` title is in `meta.phases`.
- A saved workflow needs the launching orchestrator to be a main-thread agent; the `orchestrator-*` realizations must state that in their body, and `--agent`/plugin `settings.json` `agent` is how the package selects it.

- Design consequences for our shipped workflows: keep one `agentType` per fan-out stage and vary only the prompt (agents with the same model, effort, agent type, tools, schema and working directory share a prompt cache); default each workflow to the Pro baseline of fewer than 5 agents and scale through `args` (never through unreferenced constants); end every fan-out with `.filter(Boolean)` and report a null result as unverified, not dropped; pass any timestamp through `args`.
- Unverified, to settle in a real session: whether a leading comment line (our managed marker) before `export const meta` is accepted in a saved workflow, and which wins when a skill and a saved workflow share a name.
