# Cline CLI 3.0.68: how a workflow file's paths resolve, read from the source (2026-10-05)

**These are observations of one build, read from its source and not run, and not documentation.** The guides in `../guide/` cite the vendor's docs snapshots; where this file disagrees with a guide, the guide's authoring notes say so. Nothing here is a vendor promise, and it may change in any release. Re-read the same files when the version changes.

- **Build:** the source of tag `cli-v3.0.68` of `cline/cline`, the release the installed CLI reports (`cline --version` printed `3.0.68`).
- **How it was read:** `gh api repos/cline/cline/contents/<path>?ref=cli-v3.0.68`, read-only. **No Cline session was started, no model was called, nothing was spent.** For the file-read tool the same lines were compared with `main` on the same day and did not differ.
- **Why:** Plan 035 had to decide how the Cline projection of a workflow skill (`.cline/workflows/<slug>.md`) should name the supporting files of its skill, and whether a path from the project root would resolve for a global install (ADR 0016, amendment of 2026-10-05).

## What the source says

| Question | Answer | Where |
| --- | --- | --- |
| How does the `read_files` tool resolve a path? | An absolute path is used as given (normalised); any other is `path.resolve(process.cwd(), path)`. There is no expansion of `~`, so `~/x` is read as `<cwd>/~/x`. A path that starts with `cline://` is a cached tool result, not a file. | `sdk/packages/core/src/extensions/tools/executors/file-read.ts`, the executor returned by `createFileReadExecutor` |
| Where are workflows searched? | In this order: `<workspace>/.clinerules/workflows`, `~/Documents/Cline/Workflows`, `~/.cline/workflows`, `<workspace>/.cline/workflows`. `~/.cline` is `$CLINE_DIR` when set. | `sdk/packages/shared/src/storage/paths.ts`, `resolveWorkflowsConfigSearchPaths` and `resolveClineDir` |
| Does that match the docs? | **No.** The config page of the docs snapshot says global workflows resolve from `~/.cline/data/workflows/`; that path is not in the list above, and `~/.cline/workflows` (which is where a global install of ours writes them) is. | `../pages/settings/config.md`, "Configuration Directory Layout" |
| What does a workflow file consist of? | A markdown file. The parsed workflow holds a name, a description, the instructions text (the body) and the front matter, and nothing that refers to a folder or a list of files next to it. | `sdk/packages/core/src/extensions/config/user-instruction-config-loader.ts`, `WorkflowConfig` and `parseWorkflowConfigFromMarkdown` |

## What follows for a workflow file

- A relative path in a workflow body is read against the **working directory of the Cline process**. For a project install started from the project root that is the project, so `.agents/skills/<name>/examples/x.md` resolves. For a global install the workflow is found in every project and the working directory is that project, so only an **absolute** path reaches the home directory's `~/.agents/skills/<name>/`.
- A relative link such as `examples/x.md` is read the same way, as `<working directory>/examples/x.md`. That is not where the skill's file is, and it could be an unrelated file of the project that happens to share the name.

## What was not established

- **Any live behaviour.** The source says how the tool resolves a path; no session was run to see a model call it with the path a projection names. A model may also expand `~` itself from the environment it is given; that was not looked at.
- **A session started from a subdirectory of the project**: the working directory is then that subdirectory, and a path from the project root does not resolve. The same holds for every other root-relative path our files name (the coordinator rule's `.agents/skills/<name>/SKILL.md`).
- **The IDE surface** (VS Code, JetBrains), a different code base (`apps/vscode`) that was not read, and **builds other than 3.0.68** (the library's docs are reviewed against the 4.1.22 changelog line).
- Whether the docs' `~/.cline/data/workflows/` is read by some other build or surface. It is not in the 3.0.68 list.
