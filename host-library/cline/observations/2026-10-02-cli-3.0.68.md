# Cline CLI 3.0.68 — observed behaviour (2026-10-02)

**These are observations of one installed build, not documentation.** The guides in `../guide/` cite the vendor's docs snapshots; where this file disagrees with a guide, the guide's authoring notes say so. Nothing here is a vendor promise, and it may change in any release. Re-run the checks when the CLI version changes.

- **Build:** Cline CLI `3.0.68` (`cline --version`). The docs library is reviewed against the changelog line `4.1.22`, a different version line (Cline's repository changelog), so a doc and the CLI can describe different builds.
- **Model and cost:** every real run used provider `cline` with model `google/gemini-2.5-flash` and `--auto-approve true`; the whole investigation cost about 0.09 USD of Cline Credits (a trivial run costs about 0.006 USD, because Cline's system prompt is large).
- **Project:** a scratch git project outside this repository, with probe files under `.cline/`, `.clinerules/`, `.claude/`, `.agents/` and `AGENTS.md`.

## How to run it headless

- Redirect stdin (`< /dev/null`); an inherited stdin makes `cline "<prompt>"` hang at startup, before any output.
- Use `--json -t <seconds>`. The stream is one JSON object per line: `hook_event`, `agent_event` (`iteration_start`, `content_start`, `content_end`, `usage`, `done`) and a final `run_result` with `finishReason`, `text` and `aggregateUsage.totalCost`. A tool call is a `content_start` with `contentType: "tool"`, `toolName` and `input`.
- `cline config` and `cline auth` need a terminal. `cline config skills|agents|workflows|rules --json` lists discovered items without a model call or any cost.
- A prompt that starts with `/` is rejected as an argument ("Unknown command or unquoted prompt"), and piping it on stdin produced no result in 90 seconds, so slash commands and workflows cannot be invoked headless in this build. On Windows under Git Bash, set `MSYS_NO_PATHCONV=1` or a leading `/` is rewritten into a path.
- The first run starts a background hub daemon (`cline.exe --cline-hub-daemon`); that is normal.

## Tool names (real session, and the build's own tables)

- **Observed in a session:** `read_files` (input `{files: [{path}]}`), `search_codebase` (`{queries: []}`), `run_commands` (`{commands: []}`, also used to list a directory with `ls`), `editor` (`{path, new_text}` to create a file), `skills` (`{skill}`) and `spawn_agent` (`{systemPrompt, task}`; the sub-agent then used `read_files`).
- **From the binary (strings, not a session):** the canonical set is `read_files`, `search_codebase`, `run_commands`, `fetch_web_content`, `apply_patch`, `editor`, `skills`, `ask_question`, `submit_and_exit`. An alias table maps legacy names onto it: `read_file` to `read_files`; `search_files` and `list_code_definition_names` to `search_codebase`; `execute_command`, `bash` and `list_files` to `run_commands`; `replace_in_file`, `write_to_file` and `apply_diff` to `editor`; `use_skill` to `skills`; `attempt_completion` to `submit_and_exit`.
- **Not present:** the strings `use_subagents` and `fetch_web` do not appear in the binary, although the docs' subagents and tools pages name them.

## What it loads from disk

| Item | Where it was found | How it was checked |
|---|---|---|
| Skills | project `.cline/skills/`, project `.agents/skills/`, global `~/.agents/skills/` | `cline config skills`, and a session loading each by name |
| Skills in `.claude/skills/` | **not loaded** (`probe-claude` reported not available) | session |
| Same skill name in two places | `.agents/skills` **wins over** `.cline/skills` (marker from `.agents`) | session |
| Rules | `.clinerules/*.md`, `.cline/rules/*.md` and `AGENTS.md` all present in context | session |
| Conditional rule (`paths: ["src/**"]`) | present in context even with no matching file mentioned (not gated in headless CLI) | session, two runs |
| Agent definitions | `.cline/agents/<role>.yml` (also `.yaml`): fenced YAML frontmatter plus a markdown body that is the system prompt; each becomes a tool `subagent_<name>` | `cline config agents` lists them, **and verified in real sessions** (section below) |
| Workflows | `.clinerules/workflows/*.md` and `.cline/workflows/*.md` are listed | `cline config workflows` only; invocation unverified (see above) |
| Project plugin | `.cline/plugins/<file>.js` (single file, default export) was discovered without an install step | session |

`spawn_agent` and `team_spawn_teammate` take the prompt in the call itself (from the binary). Configured agent files are reached a different way: each file becomes its own tool, `subagent_<name>` (section below).

## Guard hook (plugin) behaviour

A single-file plugin in `.cline/plugins/` with `hooks.beforeTool(context)` that throws when `JSON.stringify(context.input)` contains `echo done`: the `run_commands` call for `echo done` was **blocked and never executed**, the run ended with `finishReason: "error"`, and the thrown message was the run's text. So a `beforeTool` hook sees the tool input and can stop a call; throwing ends the run rather than returning an error to the model for another attempt (in this build). Whether the hook can tell which agent made the call, and whether a plugin can instead return a refusal the model can recover from, are not verified.

## Guard hook and subagents

The same blocking plugin (`beforeTool` throws when the tool input contains `echo done`) was tested against a configured agent. A first probe was confounded: the lead's own delegation call carried the guarded text in its prompt, so the lead was blocked before any subagent ran. Redone with the command held in a file (`src/cmd.txt`) that the subagent had to read and then run: the subagent read the file, its `run_commands` call was **blocked**, the subagent's run ended with `finishReason: "error"` and the thrown message, and the **lead's run continued** and reported "the subagent was blocked by a guard". So a plugin hook sees a subagent's tool calls, and a block ends only that subagent's run (for the main agent it ends the whole run). Not verified: whether a hook can tell which agent made a call, and whether a recoverable refusal is possible. About 0.01 USD.

## Hook context, and the shipped agents and guard in real sessions

- **The `beforeTool` context** (captured by a logging plugin): `{ snapshot, tool, toolCall, input }`. The tool name is `toolCall.toolName` (the docs example says `toolCall.name`; `tool.name` also carries it), `input` is the tool input, and `snapshot` holds `agentId`, `conversationId`, `runId`, `iteration`, `messages` and `usage`. A subagent's call has a **different `agentId`**, conversation and run from the lead's, so a hook can tell the lead from a subagent, but the id is opaque and carries no role name.
- **Tool inputs seen:** `read_files {files: [{path}]}`, `search_codebase {queries: []}`, `run_commands {commands: []}`, `editor {path, new_text}`, `subagent_<name> {prompt}`. `apply_patch` was never chosen by the test model (it used `editor` when asked for a patch), so its input shape is unobserved; the guard scans every string of a patch-like input for file headers.
- **The shipped files** (`registry/hosts/cline/agents/*.yml` and `plugins/agents-united-guard.js`, copied into a scratch project, model `google/gemini-2.5-flash`, about 0.06 USD): `cline config agents` lists the four agents and `config plugins` the guard; Cline exposes `subagent_backend_architect`, `subagent_code_reviewer`, `subagent_frontend_architect` and `subagent_repo_index`.
  - the reviewer, asked to create a file, did not (the file was not created) and said its tools are limited to reading, searching and fetching;
  - a writer created its file and returned a report in the Output Contract shape;
  - the guard blocked the lead's `echo git push --force` and its `.env.test` write through `editor` (each ends the lead's run with the guard's message), let `echo hello` run, and blocked a **subagent's** forced push while the lead continued and relayed the error.
- **Operational lesson:** told only to "delegate to the configured subagent code-reviewer", the test model reached for `team_run_task` and reported the agent not found; told to call `subagent_code_reviewer`, it worked. A coordinator's instructions must name the `subagent_<name>` tool, not just the role.

## Configured agents (verified in real sessions)

**Prior art first.** ADR 0013 (verified against CLI 3.0.61 and the `cline/cline` source) already records configured agents and workflows, and the legacy Cline lane (`src/core/cline-projector.ts`, `renderConfiguredAgent`) already writes `.cline/agents/<role>.yml` and `.cline/workflows/<slug>.md`. Earlier text in this file and in ADRs 0026 and 0027 called them undocumented or unverified because that prior art was not read; ADR 0028 corrects that. Verified again on 3.0.68 (provider `cline`, `google/gemini-2.5-flash`, about 0.04 USD):

- **Format:** `.cline/agents/<role>.yml`, fenced YAML frontmatter (`name`, `description`, `maxIterations`, and per ADR 0013 optional `tools`, `skills`, `providerId`, `modelId`) and a markdown body that is the agent's system prompt. A plain YAML file with no body is listed by `cline config agents` but is not a usable agent.
- **Exposure:** the lead model gets one tool per agent, `subagent_<name>` (non-alphanumerics become underscores), taking `{prompt}`. An agent `probe-reviewer` whose body says "reply with exactly AGENT-MARKER" returned `AGENT-MARKER...`, so the file's prompt is what runs.
- **Default power:** a configured agent with no `tools:` key could write: asked to create a file, it did, through `editor`.
- **`tools:` restricts, and the host enforces it:** with `tools: [read_files]` the agent reported "I cannot create or write files" and the file was not created. A read-only role therefore needs no hook. Only canonical tool names were tried; the alias table suggests legacy names work too (unverified).
- **Not verified:** parallel delegation, the effect of `modelId`/`providerId` and of `skills:`, IDE behaviour, whether the lead agent itself can be defined by a file, whether a plugin hook also sees a subagent's tool calls, and which file the CLI reads for MCP servers (ADR 0013 found `.cline/mcp.json` documented but absent from the 3.0.61 binary; this was not settled for 3.0.68).

## Release notes cross-check (CLI 3.0.58 to 3.0.68)

Checked from the terminal on 2026-10-02. `cline` has no `changelog` command (it is rejected as an unknown command), and the package ships no changelog file. The CLI's release notes are GitHub releases tagged `cli-v3.0.x` in `cline/cline` (`gh release list -R cline/cline`), and the build tested here, 3.0.68 (published 2026-10-02), is both the latest release and npm's `latest`. **The docs library's changelog source is a different stream:** `sources.json` tracks the repository's root `CHANGELOG.md` (the 4.1.22 line), while the CLI (`cli-v3.0.x`), the SDK (`sdk/v0.0.x`) and the Desktop app (`desktop-v0.0.x`) each release separately, so a CLI release does not appear in what the changelog-first host update reads.

Items in those releases that bear on the areas observed above:

- **3.0.62**: "Agent Plugins" are managed through the Hub. Packages under `~/.agents/plugins/*` are discovered and validated, their skills are exposed through the skills tool as `plugin-name:skill-name`, and their MCP servers start without touching `cline_mcp_settings.json`. *Not reproduced:* with an isolated home directory and a package at `<home>/.agents/plugins/<name>/` (one with `.claude-plugin/plugin.json`, one with `plugin.json`), `cline config plugins` and `cline config skills` listed neither, and a project-level `.agents/plugins/` package was not listed either. Unverified. The same notes say web search is now on by default in non-yolo sessions on models that support it.
- **3.0.63**: configured subagents no longer ask for approval of their own tool calls once the delegation is approved; subagents run their tool calls concurrently; `.cline/rules` and global rules are found consistently; on Windows a bare `rg`, `git` or `powershell` is no longer resolved from the workspace.
- **3.0.61**: global rules are also read from `~/Cline/Rules`; aborting a session cancels the subagents and teammates it spawned; a rejected tool call names the tool to the model.
- **3.0.65**: a plugin that fails to load no longer costs a sandbox spawn on every prompt (it is retried after 30 seconds), and a failing plugin's slash commands are skipped; yolo mode (`-y`) uses tighter output rules.
- **3.0.66**: yolo mode no longer includes plan/act instructions; `.cline/cron/*.md` and `*.task.md` specs saved with a BOM now parse; `search_codebase` covers PHP sources and skips Composer's `vendor`; hub diagnostics improved.
- **3.0.67**: when an MCP tool's output is too large, the agent reads the rest through `read_files`.
- **3.0.68**: agent teams stay fast in long sessions (team state in `~/.cline/data/db/teams.db` is compacted).

The notes do not mention how `.claude/skills` or `.agents/skills` are handled, so the skill observations above stand for 3.0.68.

## Named delegation and flags

- The model has a `team_run_task` tool (`{task, agentId}`) that delegates to a *teammate* by id. My first probe put a plain YAML file (no body) in `.cline/agents/` and asked the model to delegate to it by name; it reached for `team_run_task` and got `Teammate "probe-reviewer" was not found`. **That probe was malformed (no body, so not the configured-agent format) and said nothing about configured agents; an earlier version of this file wrongly read it as "effect unverified".** The correct probe is below.
- `cline --help` in 3.0.68 lists no `--team-name`, `--no-teams`, `-y` or `--yolo`, although the docs describe the first two and the release notes mention `-y`. They may be hidden or absent in this build; not verified.
