# Antigravity CLI (`agy`) 1.2.15 — project skills in a headless session (2026-10-03)

**These are observations of one installed build, not documentation, and the result is negative-by-absence: read "Not established" before using it.** Same caveats as `2026-10-02-agy-1.2.15.md`. Environment: Windows, `agy` 1.2.15, headless `-p`, default settings, the maintainer's own sign-in (ceiling 10 USD, quota use not measured), a scratch git project outside the repository.

## What was run

The question: does the host load the renamed skill `generative-ui` (the canonical skill was renamed from `generative_ui` on 2026-10-03, ADR 0018 addendum)?

The built CLI installed `product-design` with the native lane into the scratch project (`agents add product-design --native -y`): `.agents/skills/` held 22 skills, `generative-ui` among them with `name: generative-ui`, and `.agents/agents/`, `.agents/rules/`. Then three headless sessions from the project root, each told not to call any tool and to answer from the skills list already in the model's context:

1. Skill names containing `generative`: **`NONE`**.
2. Count, first eight names alphabetically, names containing `generative`: **`COUNT=58`**; the eight names were global skills (`ab-test-setup`, `agent-browser`, `agy-customizations`, `analytics-tracking`, `android-cli`, `antigravity-guide`, `architecture-design`, `brainstorming`); `GENERATIVE=NONE`.
3. Five skill names that exist only in the project (`ux-writing`, `user-flow-mapping`, `micro-interaction-design`, `responsive-design-audit`, `interaction-pattern-library`) plus `generative-ui` and `generative_ui`: **every one `OUT`**, `COUNT=58` again.

## What this shows, and what it does not

- **The renamed skill was not in the model's list, and neither was any other project skill.** The five controls sit in the same folder with the same installer output, so the rename is not the cause. The list held the 58 skills of the user's global skills (and built-ins) and none of the project's 22.
- **Not established:** *why* the project skills were absent. Candidates, none tried: workspace trust in print mode (the CLI has a workspace trust dialog, and the log has no trust line either way); headless print mode not loading project skills at all; something in the registry skills' frontmatter that the global ones do not have (a multi-line `description`, a nested `metadata:`, `disable-slash-command`); or the model's own report of its context being wrong (it is a model's answer, not an instrument, and the count was model-reported). Earlier sessions showed that project **rules** and project **agents** do load in scratch workspaces (observations 2026-10-02), so this is specific to skills, or to what the model was able to report.
- The CLI log shows `Reloading system slash commands and skills` and `loaded 0 named hooks from 0 hooks.json file(s)` (no hook was installed for this bundle) but nothing about which skills were found.
- So **"the renamed skill loads on Antigravity" is still unverified**, and a wider question is opened: whether the `.agents/skills/` copies this repository installs are visible to Antigravity at all.

In a workspace that is trusted, a minimal skill with only `name` and `description` in `.agents/skills/<name>/SKILL.md`, and the same IN/OUT question against that skill, against one registry skill, and against a global control. ## Addendum (2026-10-03, cause found)

The next experiment above was not needed in the form planned: the cause was the install method, not trust, print mode or the frontmatter. The skills in these sessions were installed by the default method, NTFS junctions into the registry, and `agy` 1.2.16 listed real-folder skills (a minimal one and a registry skill copied in, frontmatter and all) while not listing the junctions. See `2026-10-03-agy-1.2.16-probes.md`, probe (b), for the setup, the result and what is still not established.
