# Antigravity CLI (`agy`) 1.2.15 on Linux (WSL Ubuntu) — observed behaviour (2026-10-03)

**These are observations of one installed build, not documentation.** Same caveats as `2026-10-02-agy-1.2.15.md`, which records the Windows sessions. Environment: WSL2 Ubuntu 24.04 on the maintainer's Windows machine, `agy` 1.2.15 (sign-in as the maintainer's own account, ceiling 10 USD, quota use not measured), headless `-p`, default settings, scratch git workspaces under `/tmp`.

## Why the first attempts hung, and the fix

Three headless runs, even a no-tool "reply PONG", ended in `print timeout ... with turn in progress` with nothing printed. The log showed the sign-in was fine (`keyringAuth: loaded token ... expired=false`, `OAuth: authenticated successfully`) and the model request was sent, but `agy` first waited on the global MCP servers: `MCP: 3 server(s) still connecting after 30s...: StitchMCP, canva-dev, comfyui-mcp` (the WSL home's `~/.gemini/config/mcp_config.json` lists four servers, three launched through `npx`). WSL had no Linux Node on a non-interactive `PATH`: Node 22.14.0 was installed through nvm, which only an interactive shell loads, so `npx` resolved to the Windows one and the servers never connected. With `~/.nvm/versions/node/v22.14.0/bin` on `PATH` the same prompt answered `PONG` at once (one server, `comfyui-mcp`, still connecting, which did not block). A throwaway `HOME` with an empty MCP config does not work: the sign-in is not found without the real home. **A headless run on a machine whose MCP servers cannot start waits on them**, and an unusable global MCP config makes every session hang.

## Permissions and the sandbox

- **A plain command needs permission by default.** `echo LINUX_OK` asked to run a shell command with default settings was auto-denied: `a tool required the "command" permission that headless mode cannot prompt for`. The permissions page describes the Default preset on macOS and Linux as running commands in a sandbox without prompting; the CLI reference (sandbox off by default, `toolPermission` default `request-review`) is what matched. The same result as on Windows.
- **`--sandbox` alone does not change that:** the same command with the flag was denied the same way. Running commands in the sandbox without prompting needs `toolPermission: proceed-in-sandbox` with `enableTerminalSandbox`, or a `command()` allow rule, in `~/.gemini/antigravity-cli/settings.json`. That was then tried, with the maintainer's consent, in the section below; `--dangerously-skip-permissions` was never used.

## The shipped guard on Linux

`registry/hosts/antigravity/hooks/` copied into a scratch workspace (`.agents/hooks.json` and `.agents/hooks/agents-united-guard.js`, with the nvm Node on `PATH`, because the hook command is `node hooks/agents-united-guard.js`): `echo git push --force` was denied with the guard message (`tool call denied by pre-tool hook: Blocked by agents-united guard: git push --force requires explicit human approval outside the agent session.`) and `ok.txt` was created normally, exactly as on Windows. The guard answers `deny` or `ask`, so with default settings its `ask` is indistinguishable from the permission default here; with the sandbox on it was tested in the section below.

## The sandbox, tried with the setting on (2026-10-03, with the maintainer's consent)

The WSL `~/.gemini/antigravity-cli/settings.json` was backed up (checksum recorded), `enableTerminalSandbox: true` and `toolPermission: "proceed-in-sandbox"` were added with every other key and the maintainer's 32 allow rules kept, the sessions below were run, and the file was restored from the backup with the checksum verified identical (the two keys gone, the rules intact, no stray file, no `agy` process left).

- **One session, four commands, none retried.** `echo SANDBOX_OK` **ran without a prompt**. `curl -s -m 8 -o /dev/null -w http=%{http_code} https://example.com` gave `http=000`, exit 6, "could not resolve host": **the network is cut**. `ls ~/.ssh` printed **nothing** inside the sandbox while a normal listing outside it shows four files (`id_ed25519`, `id_ed25519.pub`, `known_hosts`, `known_hosts.old`): **the sandbox hides `~/.ssh`**. `sh -c "echo x > ~/outside-probe.txt"` failed with `Read-only file system` and **no file was created**.
- **The guard's `ask` does not force a prompt.** In a workspace with the shipped guard installed, with the sandbox on: `echo ASK_CHECK` **ran** (no prompt, output `ASK_CHECK`), and `echo git push --force` was **denied** by the guard with its message. So the answer `ask` defers to the user's own permission settings there too, and the guard needs no change for Linux.
- One build on one machine. Not tried: macOS, the older Windows system, the 2.0 and IDE surfaces, and what a `command()` allow rule does beside the guard.

## Ledger
