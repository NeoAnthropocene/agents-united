# Antigravity CLI (`agy`) 1.2.16 — four real-session probes (2026-10-03)

**These are observations of one installed build on one machine, not documentation. Read "Not established" under each probe before relying on a result.** Environment: Windows, `agy` 1.2.16 (it updated itself from 1.2.15 between the earlier sessions and these), headless `-p`, default settings, the maintainer's own sign-in, a scratch git project outside the repository for each probe. Every answer below that comes from the model is the model's report of its own context, not an instrument; where a file or an exit status could be checked, it was.

Ledger: 4 headless sessions this session (the maintainer allowed up to 4), all on Windows. With the earlier 27 headless sessions and the 2 accidental calls that makes 31 headless sessions plus the 2 accidental calls; quota use was not measured; ceiling 10 USD. Free commands also used: `agy mcp --help`, `agy mcp list`, `agy changelog`, `agy --help`.

## (a) `GEMINI.md` without frontmatter

Setup: `agents add software-engineering --native -y` with the built CLI into a scratch project, so `.agents/rules/` held the six native rules (two `always_on`) and the legacy host-entrypoint `GEMINI.md`. In the scratch copy only, the symlink `.agents/rules/GEMINI.md` was replaced by a real file (a copy) with the line `MARKER_RULES_GEMINI=alpha7` appended (no frontmatter), and `.agents/GEMINI.md` was created holding `MARKER_AGENTS_GEMINI=beta3`. One session, no tool allowed, answer from the context: list the `MARKER_` lines and count two phrases, `Zero Force-Pushes` (only in `GEMINI.md`) and `Never Execute Force Pushes` (only in the native `git-guardrails` rule).

Result: both marker lines were reported, and both counts were `1`.

What it shows: a frontmatter-less `GEMINI.md` is read in both places, unlike the other files of `.agents/rules/` (observations 2026-10-02: those are dropped). The same policy reached the agent twice, once from each text, so the legacy `GEMINI.md` overlaps the native `always_on` rules instead of being replaced by them.

Not established: the `GEMINI.md` that the default install really creates, which is a symlink (the probe used a real file, so whether the link is followed is untested; see probe (b) for what links did); how much context the overlap costs; whether the lane should leave the legacy file out (a product decision, not made here).

## (b) Why the project skills were not listed

The question left by `2026-10-03-agy-1.2.15-skills.md`: project skills were absent from a headless session, controls included. One of its candidate causes was never tried: how the files were installed. The default `agents add` method makes each skill folder a link into the registry; on Windows `Get-Item` reports `LinkType: Junction` (`fs.ensureSymlink(..., 'junction')` in `src/core/installer.ts`).

Setup: the project of probe (a) (36 skills installed as junctions), plus two real folders added by hand: `probe-min` (only `name` and `description`) and `probe-copy-refactoring` (a copy of the registry skill `code-refactoring` with its name changed, keeping its multi-line description, its nested `metadata:` block and `disable-slash-command: true`). One session, no tool allowed, IN or OUT for six names against the skills list in context, and a total.

Result: `probe-min` IN, `probe-copy-refactoring` IN, `backend-api-design` OUT, `database-design` OUT, `code-refactoring` OUT (all three junctions, none of them a global skill), `brainstorming` IN (a global control), `COUNT=60`, which is the 58 global skills of the earlier sessions plus the two real folders.

What it shows: **skill folders installed as junctions are not listed, real folders are, whatever their frontmatter.** That is the cause of the absence in the 1.2.15 sessions; it is not the registry frontmatter, not workspace trust and not print mode. The extra keys (`metadata`, a multi-line `description`, `disable-slash-command`) did not stop a skill being listed. So on this host the default symlink install leaves every installed skill invisible, and a `--copy` install is needed for Antigravity.

Not established: POSIX symlinks on Linux or macOS (a different mechanism, not run); file symlinks (a symlinked rule or agent); a junction that stays inside the workspace; any other agy version; what `disable-slash-command` and `metadata` *do* here (only that they do not hide the skill); that the renamed `generative-ui` loads (a real-folder copy of it was not tried); how the installer should change (a separate decision).

## (c) The guard installed by the lane

Setup: the project of probe (a); `.agents/hooks.json` and `.agents/hooks/agents-united-guard.js` were written by the lane (`--native`), not by hand. One session: run `echo git push --force` with the command tool and quote the result.

Result: the tool call was denied: `Encountered error in tool execution: tool call denied by pre-tool hook: Blocked by agents-united guard: git push --force requires explicit human approval outside the agent session.`

What it shows: the files the lane installs, as installed, are read by the host and deny a forced push with the guard's own message, so the claim of PR #110 is now backed by a real session through the lane and not only by the earlier hand-copied files.

Not established: the `ask` path through the installed files, a user's own hooks beside ours in a real session, the 2.0 and IDE surfaces, macOS and Linux for the installed files.

## (d) MCP wiring

Setup: a scratch project with a hand-written `.agents/mcp_config.json` (not written by the lane, so the shipped entries were not themselves exercised) and a local stdio probe server that writes its environment to a file when it starts and answers `initialize` and `tools/list`. Three entries: `probe-ok` (`env`: a literal value and `"PROBE_B": "${PROBE_B}"`), `probe-off` (the same server, `disabled: true`, no `env`), `probe-broken` (a command that is not installed). The session was started with `PROBE_A` and `PROBE_B` set in the environment; the prompt was only "reply OK, no tool". Timed.

Result: the run finished in 10 s with `OK` and exit status 0. Both `probe-ok` and `probe-off` wrote their files, in the workspace directory: `probe-ok` had `A=inherited-a` (inherited), `B=${PROBE_B}` (the literal text), `D=literal-d`; `probe-off` had `A=inherited-a` and `B=expanded-b` (inherited, since it set no `B` of its own).

What it shows:
- **agy reads `.agents/mcp_config.json` in a session** (the free `agy mcp list` prints only the global servers, so it is not a test of the workspace file).
- **A stdio server receives agy's own environment**, so a variable set where agy starts reaches it.
- **`${VAR}` in `env` is not expanded**: the server got the literal text, which would break it. No placeholder should be written.
- **A server whose command is not installed did not hang or delay the run** (the Linux observation of the same day saw every headless session hang while the global servers could not start, because the wrong `npx` was on the path; a command that is simply not installed did not reproduce a hang here, so what made that run hang is not established).
- **A server marked `disabled: true` in the workspace file still started.** This contradicts the docs and the design of ADR 0032 (credentialed servers shipped switched off). agy writes `disabled: true` the same way in its own global file (seen by key name only), and `agy mcp list` reports those as disabled, so the workspace file may be treated differently, or headless mode ignores it. One observation.

Not established: why `disabled` was not honoured; whether `agy mcp enable|disable` writes the same field to the workspace file; a server that starts and then fails to connect in a longer session; whether an agent's `mcpServers:` frontmatter resolves; the shipped entries run through agy (the servers need `npx` and network); macOS and Linux for any of this.

A caution found on the way: `agy mcp list` prints header and argument values of the global servers in plain text. One of the maintainer's own was printed in the terminal of this session. Nothing was copied into a file, but the output of that command must never be pasted into a report or a file.
