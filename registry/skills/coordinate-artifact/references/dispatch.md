# Reviewed ordinary subagent dispatch
For native startup use the installed receipt-driven main selection, not a manifest orchestrator fallback. When manually entering with claude --agent orchestrator-agent-factory, do this before first dispatch. Run the pinned checkout's built CLI, `node <checkout>/dist/cli.js start agent-factory --host claude --dry-run`, from the workspace root (the folder the session was started in, which holds the installed bundle; not a subfolder), never a bare `agents` from the path, and save its output in the evidence folder. The planned agent must be `orchestrator-agent-factory`; anything else, or a nonzero exit, is recorded and the route stops there and reports, without a workaround. The launcher turns agent teams off for the factory's own session and does not refuse a dry run because `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` is set; with direct `claude --agent` entry that switch does not apply, so a worker that starts as a teammate is refused and reported. Direct Host entry bypasses launcher enforcement: this is guidance, not a guaranteed pre-start barrier. Inspect the actual native main/header. A main session started with `--bg` or in a worktree, an unavailable required closure or the wrong main blocks this journey.

The workers are ordinary subagents, never a fork of this conversation. The Host decides whether an Agent call returns the worker's result at once or only a launch notice (its fork-mode default varies); do not change user settings, invent a per-call flag or switch to teams/workflows. Realization goes to `factory-realizer`, review to `factory-evaluator` and host-update sync planning to `factory-sync`.

Start one worker at a time with Agent: `subagent_type`, a description and a prompt that carries the fixed job, or its path where the route says so, and the caller-held digest; no teammate name, no model override. Pass no `run_in_background`, except `false` in a headless session (`claude -p`) when the tool offers it: there, ending your turn ends the session. If the call returns the worker's finished result, go on with the checks. If it returns a launch notice instead, the worker runs in the background: say in one line which worker runs, start no other worker, do nothing that depends on its result, and end your turn; do not poll, sleep or read Host session records. Its result arrives later by itself, as a hand-back message or a completion notice: accept it only if it comes from the worker you started and repeats the digest you hold, then treat it as the actual return and go on with the checks. While you wait you may answer the human, but change nothing under the job's roots and advance no step. Refuse and report a teammate, a fork of this conversation, a result from a worker you did not start, a result with another digest, and a partial or failed return. If no result has come and the human asks, say that the worker still runs and the dependent step is not done; if the human tells you to stop waiting, report the journey as blocked at that worker and whatever it may have written as unverified. Never invent a result or a timeout.

After actual final-byte checks, call a fresh independent factory-evaluator with complete P5 job and caller-held job/candidate digests. Every evaluator prompt, the first and a fresh one alike, carries these two sentences word for word: "A citation gives its source and a quote copied exactly from that file, at most five lines and 1024 bytes, and no line range: the checker finds the lines itself; give `line` (the line the quote begins on, as the Read tool numbers it) only when the quote occurs more than once in the file; one bad citation gets the whole result refused." "Your hand-back (the SubagentHandback message, or your final message where that tool is absent) is exactly ONE JSON object that validates against `assets/result.schema.json`, with no text before or after it, no code fence and no headings." Start it as an ordinary subagent and, when it runs in the background, wait for its hand-back as the waiting rule above says. Assume no inherited conversation history. Worker SubagentHandback is conditional; ordinary final-response data is the fallback. Do not grant workers Task tools or ask the read-only evaluator to run checks, persist records or repair. No team shutdown frames, peer-session discovery, mailbox polling or nested CLI/provider workaround.

For host-update sync, after the sync checker's preflight passes, request Agent({subagent_type: "factory-sync", prompt: the absolute sync job path plus the preflight jobDigest, nothing else}) with no teammate name or model override. Start it as an ordinary subagent and, when it runs in the background, wait for its hand-back as the waiting rule above says; inspect its actual return the same way. factory-sync is read-only: it cannot run the sync checker, write the plan or repair it. Save the returned plan unedited in the evidence folder and run the postflight check yourself, as in [host-update sync](host-sync.md).

Only the main owns accepted progress tracking: discover actually available Task tools and reuse returned IDs. Consultation does not authorize assigning a deliverable. Before authorized revision reopen the assigned task or link an owned fix, invalidate dependent acceptance and close after changed-byte readback and applicable rechecks. If Task tools are absent use supplied TodoWrite, otherwise concise briefs/handoffs. Missing tools are not permission for retries, invented IDs, status polling or expanded scope.
