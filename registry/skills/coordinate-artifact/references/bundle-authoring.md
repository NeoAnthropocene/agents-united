# One Bundle proposal through a typed fork, a checked return and bundle-check
This route coordinates one Domain or Organization Bundle proposal written by the `author-bundle` fork. This coordinator holds no Skill tool and does not start the fork: the maintainer types `/author-bundle <absolute task path>`, then the coordinator checks the files the fork wrote and runs `node <checkout>/dist/cli.js bundle-check` on them. Nothing is installed, committed, pushed or published, and no check here starts a Host session. Each step below names what enforces it: tool pool, hook, deterministic script or prose. Prose is an instruction, not a barrier.

## Task and return
The task is `bundle-task.json` at `<evidence>/bundle-task.json`, valid against `assets/bundle-task.schema.json`. It selects `operation` (`create`, `reuse` or `update`) and `intent` (`local` or `upstream`) and fixes the literal Bundle fields in `bundle` (`name`, `tier` `domain` or `organization`, `version`, `status`, `domain`, `category`, `description`, plus the roster: `parentBundle`, `orchestrator`, `agents` and `skills`, which names `host-agent-router`, `handoff` and `git-guardrails` once each). The fork writes only the four proposal files `bundles.json`, `leader-responsibility.md` (both role `subject`), `bindings.json` and `report.json` (both `support`) at the top of the draft root; `allowedPaths` lists all four for `create` and `reuse` and the files an `update` may change. `create` and `reuse` have an empty `baseline[]` and an absent draft root; an `update` carries the full baseline, including all four proposal files, every other file as `preservation-only`, and optional `protectedNotes`. `inputPins[]` and `provenance.evidence[]` are full pins outside the draft, within `budget.maxPinnedInputs` and `budget.maxPinnedInputBytes`; adapted work needs evidence and `provenance.unresolved` stays empty. `runtime.validator` pins the checkout's built `dist/cli.js` and `validation.allowUnresolved` says whether `bundle-check` may accept members the registry does not have yet. An upstream task pins `.github/PULL_REQUEST_TEMPLATE/artifact-contribution.md` inside the checkout as `contributionTemplate` (path, bytes, sha256); a local task sets it to `null`. A repair is an `r1` `update` revision, at most one.

The return is `bundle-return.json` at `<producer>/bundle-return.json`, valid against `assets/bundle-return.schema.json`. The fork does not write it by hand: after writing the four files it runs the `author-bundle` helper `scripts/bundle-return.mjs` once, which reads the task, inventories the draft root without following links, works out `changed` against the baseline, pins `report.json` and echoes `taskId` and `taskDigest`; status, open items, unverified statements, claimed checks and the upstream evidence come from an optional notes file the fork writes in the producer root. Every field is still a claim: the checker recomputes inventory, changed list and report pin from the bytes. `taskDigest` is the sha256 of the task's canonical JSON (keys sorted at every level, no whitespace); the preflight success line prints it, and a mismatch is `DIGEST_MISMATCH`.

Place the evidence, producer and draft roots under a path with no managed Host directory segment (`.agents`, `.claude`, `.cline`, `.cursor`, `.codex`, `.opencode`, `.gemini`), disjoint from each other and from the source checkout, source registry, managed and protected roots. For an `update` or `r1` repair, copy every existing draft file into the evidence root before dispatch and pin it in `baseline[]`. Pass every path argument to a checker or to `git` as an absolute path in the platform's own form: on Windows a drive letter, never a `/c/...` form or `$PWD`. Save any helper script you write to assemble a record in the evidence folder and name it in the report.

## Sequence
1. Entry. The session is started through the launcher or with `claude --agent`. Run the pinned checkout's built CLI, `node <checkout>/dist/cli.js start agent-factory --host claude --dry-run`, from the workspace root (the folder the session was started in, which holds the installed bundle; not a subfolder), never a bare `agents` from the path, and save its output in the evidence folder. The planned agent must be `orchestrator-agent-factory`; anything else, or a nonzero exit, is recorded and the route stops there and reports, without a workaround. The launcher turns agent teams off for the factory's own session and does not refuse a dry run because `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` is set; with direct `claude --agent` entry that switch does not apply, so a worker that starts as a teammate is refused and reported. Enforced by script when the launcher starts the session; by prose when `claude --agent` is typed directly.
2. Fix the roots, the baseline for an `update`, and the pins, each as path, bytes and sha256: the twenty installed `author-bundle` files in `installed[]` (the helper included), `runtime.validator` at `<checkout>/dist/cli.js`, `runtime.checker` (this installed `check-bundle-return.mjs`) and `runtime.executable` (the physical path of the running Node >=24 binary). Record `source.head`, the checkout's HEAD, which the checker reads once with `git -C <checkout> rev-parse --verify HEAD`. Prose; the checker verifies the pins in the next step.
3. Write the task, then run `node "${CLAUDE_SKILL_DIR}/scripts/check-bundle-return.mjs" --job <absolute task>` (preflight). Read stdout, stderr and the actual exit. A nonzero exit blocks dispatch. Preflight alone checks the state before the run: `create` and `reuse` need an absent draft root, `update` needs the live draft to equal the pinned baseline. Deterministic script.
4. Ask the maintainer to type `/author-bundle <absolute task path>`. The text after the skill name is the invocation text. Prose plus a maintainer action; the coordinator cannot make this call.
5. Inspect what the Host actually returned: foreground, returned text, no background or teammate. Intended settings prove nothing. Prose.
6. The fork reads the task, writes the four files by ordinary editing, runs `bundle-return.mjs` once and answers with the paths. The helper writes only the return record; everything else the fork does is prose.
7. The caller never edits the four files and never reruns the helper. Read the files yourself. Prose.
8. Run the same checker with `--job <absolute task> --result <absolute return>` (postflight). It does not repeat the live-state checks of step 3, so step 3 must have passed before the fork ran. A `draft` return needs all four files, nothing outside `allowedPaths` and the baseline, no folder the baseline did not have, unchanged `preservation-only` and non-allowed baseline files and present `protectedNotes`; the four files must be UTF-8, the three JSON files must parse, `bundles.json` must hold `bundles[<bundle.name>]` whose `name`, `version`, `status`, `domain`, `category`, `description` and `tier` equal the task's, with the same `agents` and `skills` (same entries, same order) and the same `orchestrator` and `parentBundle` (absent or null where the task has null); every `fixedValues` entry must appear as a whole token (not directly preceded or followed by a letter, digit, `_` or `-`) in `bundles.json`, `leader-responsibility.md` or `bindings.json`; `report.json` does not count, though it must be a JSON object. The report pin and an upstream `templatePath` must be absolute, without `.` or `..` segments, and exactly `<roots.draft>/report.json` and the task's `contributionTemplate.path`. The checker does not check placeholders, other Bundle records in `bundles.json`, field shapes, the members the roster names, `bindings.json` beyond parsing, the leader file beyond UTF-8 or `report.json` beyond being an object: step 9 (`bundle-check`) checks placeholders, the manifest shape, the references to registry members and the Bundle rules. A `blocked` return names an open item and leaves the draft root exactly as before, folders included. A nonzero exit or a missing return is rework. Deterministic script.
9. Run `node <checkout>/dist/cli.js bundle-check --artifact <draft root> --registry <source.registry> --operation <operation>`, adding `--allow-unresolved` only when `validation.allowUnresolved` is true; the postflight success line prints these arguments as `bundleCheck`. Save the command, stdout, stderr and exit code in the evidence root. Exit 0 passed, 1 failed, 2 unavailable; a nonzero exit is rework. Deterministic script; writing the receipt is prose.
10. No evaluator step: `evaluate-artifact` has no subject kind for a whole Bundle, so an independent quality review of a whole Bundle is unavailable and the hand-back says so. Members the proposal names but that are not yet realized (shared pairs, native agents, Skills) are separate tasks with their own routes and reviews. Prose.
11. Repair only if the accepted brief already authorized one (at most one). Create a new `r1` evidence and producer directory, snapshot the current draft including preserved files, and write an `r1` task with `operation: "update"` whose `previous` records `taskId`, `taskDigest`, `returnSha256` and `reviewResultSha256` (null, as no review runs), with narrowed `allowedPaths` and the new baseline. The maintainer types the path again; repeat steps 3 to 9. r0 acceptance is invalid. Prose for the count, authorization and `previous` values, which the checker records but does not verify; script for the revision pairing and the baseline.
12. Deliver the candidate with the evidence (`bundle-task.json`, `bundle-return.json` and the notes file `bundle-notes.json` when the fork wrote one, both checker outputs with exits, the saved `bundle-check` output and exit), or precise rework. Local intent stops. Upstream intent only prepares the pinned `.github/PULL_REQUEST_TEMPLATE/artifact-contribution.md`, base `dev`, `sent: false`, following the checkout's `docs/artifact-contribution.md`; no commit, push, pull request or publication follows. A human continues from [contribution](contribution.md).

## Checker output
Success is one JSON line on stdout and exit 0: `version`, `kind`, `phase`, `recordValid`, `task`, `taskId`, `revision`, `operation`, `intent`, `bundleName`, `tier`, `bundlePaths`, `taskDigest`, `baselineDigest` (null for `create` and `reuse`), `pins`, `validation`, and after a postflight `result`, `returnStatus`, `candidate` (null when blocked), `bundleCheck` (null when blocked), `claimsNotAccepted` and `producerIdentity: "unauthenticated"`. It always carries `quality: "pending"`, `executionProof: "unverified"`, `live: "unverified"` and `acceptedDraft: false`. Failure is one JSON line on stderr and exit 1: `status` (`failed` or `unavailable`), `phase`, a stable `code`, `reason` and `path`; only the first failure is reported. `--help` alone prints usage and checks nothing. Codes: `USAGE`, `JOB_INVALID`, `ROOT_CONFLICT`, `CLOSURE_MISSING`, `LOADER_MECHANISM`, `RUNTIME_MISMATCH`, `BASELINE_MISMATCH`, `CHECKOUT_HEAD`, `LIMIT`, `STALE_INPUT`; after a return `RESULT_PATH`, `RESULT_INVALID`, `DIGEST_MISMATCH`, `HELPER_RECORD` (a report pin or template path that is not the absolute path the task implies), `EXTERNAL_ACTION`, `BLOCKED_STATE`, `SCOPE_VIOLATION`, `PRESERVATION`, `BYTES_MISMATCH`, `INVENTORY_MISMATCH`, `DIFF_MISMATCH`.

## Budgets
A journey has no aggregate process, time or output budget; see [repair](repair.md). The task budget caps four authored files at 256 KiB each and 1 MiB together, 32 preserved files and 2 MiB, 32 pinned inputs and 4 MiB, and six checks of ten minutes and 512 KiB raw output each, with zero external calls and no publication. At most one repair.

## What stays unproven
The checker compares final bytes with the baseline, the task and the return. It cannot show who wrote the files or the return (`producerIdentity` stays `unauthenticated`), that the helper ran once, that nothing outside the draft and producer roots was written, or that the fork followed any prose rule. Claimed checks are not run and their `raw` pins are not resolved. `bundle-check` does not show the leader file's content, the report's content and hashes, licence truth or quality, and neither does the checker: these stay prose and `unverified`. Unverified in a live session: that the Host passes the typed path to the fork as the invocation text, that the fork runs in the foreground, which tools it holds, and whether this coordinator's hook applies to it.
