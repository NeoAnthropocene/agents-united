# One host-update sync plan through a checked read-only worker
This route turns a host-library refresh that already happened into one adaptation plan. The read-only worker `factory-sync` joins the changed and held library entries against the realizer job records the maintainer names and returns a plan; this coordinator assembles the sync job, runs the sync checker before and after the worker, and saves the plan. Nothing is realized, installed, committed, pushed or published, no library page is refreshed, no hold is cleared, and no check here starts a Host session. Each step names what enforces it: tool pool, hook, deterministic script or prose. Prose is an instruction, not a barrier.

## What the maintainer supplies
1. The host name (kebab-case, at most 32 characters) and the checkout that holds the refreshed `host-library/<host>` folder.
2. The commit before the library refresh, from which the previous lock is read.
3. The realizer job records to consider: absolute paths of existing job files. The maintainer owns this list; neither the worker nor the checker searches for unlisted artifacts.
4. The held sources: each with its path inside the library, its locked and candidate hashes, the recorded rule and the reason.
5. Any guide or observation that changed outside the lock, with its path. The coordinator derives the lock-tracked changes itself.
6. An evidence folder inside the workspace and outside the checkout. Place it under a path with no managed Host directory segment. The sync job and the saved plan sit directly in it.
Ask for anything missing. A guessed record blocks the route.

## Assemble the sync job
The record is `host-update-sync-job` version 1, checked against the sync job schema (`.claude/skills/sync-host/assets/sync-job.schema.json`) and described in `.claude/skills/sync-host/references/job.md`; read both before writing it. Write it as `<evidence>/sync-job.json` with `version` 1, `kind` `host-update-sync-job`, a kebab-case `id` of at most 64 characters and `host` (the kebab-case host name). Every path is absolute without `.` or `..` parts and no part of it may be a link; the paths in `changedInputs`, `heldSources` and `targets` must each be unique. A hash that describes a file on disk (`sha256` in the pins, `newSha256`, `lockedSha256`) is the lowercase 64-hex SHA-256 of its bytes; `bytes` is the file length. The schema allows at most 256 `changedInputs`, 64 `heldSources` and 256 `targets`. Pass every path argument to a checker or to `git` as an absolute path in the platform's own form: on Windows a drive letter, never a `/c/...` form or `$PWD`. Save any helper script you write to assemble a record in the evidence folder and name it in the report.
1. `source`: `checkout` is the absolute checkout path; `head` is its current commit, read once with `git -C <checkout> rev-parse --verify HEAD`. The checker re-reads it and refuses on a mismatch.
2. `roots`: `workspace` and `evidence`. The evidence folder must be inside the workspace and disjoint from the checkout.
3. `library.lock`: pin `<checkout>/host-library/<host>/library.lock.json` (path, sha256, bytes).
4. `library.previousLock`: save the lock of the earlier commit into the evidence folder without editing it, using only a read-only `git -C <checkout> show <earlier-commit>:host-library/<host>/library.lock.json` redirected to a new file there (for example `previous-library.lock.json`, a file other than the job file). Never check out, reset or stash in the checkout. Pin the saved file.
5. `changedInputs`: one `{ path, oldSha256, newSha256 }` per library entry whose lock hash differs between the two locks, with the path under `<checkout>/host-library/<host>` and lock hashes without the `sha256:` prefix (`null` for an entry absent from that lock). A created input has `oldSha256: null`; a removed input has `newSha256: null` and the file must already be absent on disk; the two hashes are never both null and never equal. The checker refuses a missing or disagreeing lock difference. Add each guide or observation the maintainer named: `newSha256` is the hash of the file on disk, `oldSha256` is the maintainer's claim and the checker cannot verify it. A held path never appears here.
6. `heldSources`: one `{ path, lockedSha256, candidateSha256, rule, reason }` per held source (`rule` at most 128 and `reason` at most 512 characters). `lockedSha256` must equal that entry in both locks and, when it is not `null`, the file on disk; it is `null` only for a held source neither lock tracks, and then the checker skips the on-disk comparison. `candidateSha256` is the maintainer's hash of the candidate page (the checker cannot verify it) and must differ from `lockedSha256`. The coordinator never edits, advances or clears a hold.
7. `targets`: one `{ path, sha256, bytes }` per realizer job record, in the maintainer's order. Each target record must hold `id`, `source.checkout`, `artifact` and a non-empty `inputs` list; pins that sit in the checkout's library are joined by library-relative path.

## Sequence
1. Entry. The session is started through the launcher or with `claude --agent`. Run the pinned checkout's built CLI, `node <checkout>/dist/cli.js start agent-factory --host claude --dry-run`, never a bare `agents` from the path, and save its output in the evidence folder. The planned agent must be `orchestrator-agent-factory`; anything else, or a nonzero exit, is recorded and the route stops there and reports, without a workaround. When the launcher refuses the dry run because `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` is set in the session, report the refusal and stop; do not clear the variable yourself. The installed closure must include the `factory-sync` worker and the sync Skill. Enforced by script when the launcher starts the session; by prose when `claude --agent` is typed directly.
2. Write the record as above. Prose.
3. Preflight. Run `node <workspace>/.claude/skills/sync-host/scripts/check-sync.mjs --job <absolute sync job>`. It prints one JSON line carrying `jobDigest` (64-hex), `counts` and the job pin. Read stdout, stderr and the actual exit. Any refusal (nonzero exit, one JSON line on stderr with a `code` such as `PIN_MISMATCH`, `LOCK_DELTA_MISMATCH` or `HOLD_VIOLATION`) stops the route: fix the record only against the maintainer's real inputs, never to make the check pass. Deterministic script.
4. Start `factory-sync` in the foreground exactly as described for the evaluator in [dispatch](dispatch.md): `Agent({subagent_type: "factory-sync", run_in_background: false, prompt})` with no teammate name and no model override. The prompt carries the absolute job path and the `jobDigest` from step 3, nothing else. Inspect the actual return: foreground, returned text, no background or teammate. Intended arguments prove nothing. Prose plus the worker's native read-only pool and hook.
5. Take the one `host-update-sync-plan` JSON record out of the worker's `SubagentHandback` (or its final response, if no handback was supplied) exactly as returned and save only that record as a file directly in the evidence folder, other than the job file, for example `<evidence>/sync-plan.json`: do not edit, reformat or repair it. The short statement of limits and any `ReportFindings` text are not part of the record. A return with no such record, or with more than one, is rework. Prose.
6. Postflight. Run `node <workspace>/.claude/skills/sync-host/scripts/check-sync.mjs --job <absolute sync job> --result <absolute saved plan>`. It recomputes the plan from the job and the target records and refuses any difference in `jobId`, `host`, `jobDigest`, the artifacts (their `reason` text excepted), pins, `unpinnedChanges`, `heldSources` or the constants. Any refusal stops the route; the plan is not accepted. The worker may not run it. Deterministic script.
7. Report. Name which listed artifacts the plan marks affected, with their stale pins, and which changes pin no listed artifact (`unpinnedChanges`). State that nothing was implemented, that every held source is not advanced and not cleared, that the list of considered records is the maintainer's and its completeness cannot be proved, that an old hash outside the lock is a claim, and that live Host behaviour is unverified. Realizing an affected artifact is a separate realizer and evaluator run under the ordinary route with its own brief. Local intent stops here.

## Checker output
Success is one JSON line on stdout and exit 0: `version` 1, `kind` `deterministic`, `phase` (`preflight` or `postflight`), `recordValid`, `job` (a pin: `path`, `bytes`, `sha256`), `jobId`, `host`, `jobDigest`, `counts` (`targets`, `affected`, `changedInputs`, `unpinnedChanges`, `heldSources`) and, after a postflight, `result` (a pin of the saved plan: `path`, `bytes`, `sha256`). It always carries `claimsNotAccepted` (`targets-complete`, `untracked-old-hash`, `held-candidate`, `reason`), `proposalOnly: true`, `implemented: false`, `heldSourcesAdvanced: false`, `quality: pending`, `executionProof: unverified` and `live: unverified`. A pass is consistency of bytes and records, not acceptance. Failure is one JSON line on stderr and exit 1: `version`, `kind`, `status` (`failed` or `unavailable`), `phase` (`usage`, `preflight` or `postflight`), `code`, `reason`, `path` (the file concerned, or null), then `proposalOnly: true`, `implemented: false`, `quality: pending`, `executionProof: unverified` and `live: unverified`; it has no `heldSourcesAdvanced`.

## Budgets
Every checker run counts toward the aggregate in [repair](repair.md): at most 24 processes, 1800 seconds and 8MiB of raw output. The route has no repair: a refused plan is reported as rework, and a second worker run needs the maintainer's new decision.

## What stays unproven
Whether the target list is complete, whether an untracked old hash is true, whether a held candidate is safe, whether a `reason` is right, what the artifacts should become, and how the Host behaves when live. A passed postflight proves none of these.
