# Selected Remotion: setup, Skill loading and Element direction

Read before the first Remotion production assignment or an approved runtime upgrade. Chris owns the route and setup scope; Motion owns implementation. Reuse the user's recorded authorization: choosing Remotion for production includes the ordinary project-local runtime and required Skill setup unless the brief restricts installation. Do not ask the user to repeat that choice. Unknown licence eligibility, a machine-wide change, paid service, asset upload or new network exposure still needs its own missing fact or authorization. A Native brief installs no Remotion dependencies automatically; an explicit research/install request is a separate task and does not change the renderer.

## One setup owner, with evidence

1. Inspect `media/project.json`, existing source/package/lockfile, the purpose-specific licence record and the actual host Skill inventory. Preserve existing work. Chris assigns one setup owner before production; two agents must not install into the same project concurrently.
2. Run `scripts/check-release.mjs` before a new setup. Save its timestamp, actual exit and all four package versions. New projects use the freshly checked, supported exact release; never describe a remembered pin as latest. If the registry fails, state that freshness is unverified; if it advances beyond supported releases, return the exact compatibility gap for review. An existing locked project keeps its version unless an upgrade is requested or necessary and accepted. Resolve current facts once, then freeze versions for the job; never resolve `latest` during rendering.
3. Run preflight and scaffold with a matching reviewed versioned licence record. Install the scaffold's exact dependencies in `media/remotion/`, retaining the lockfile (`npm ci` for a compatible existing lockfile, `npm install` for a new one). Use an approved local browser and the shared FFmpeg resolve/verify helpers. Complete authorized missing setup rather than returning installation instructions as the deliverable. Report a specific installation failure; do not switch renderer silently. See [runtime](runtime.md) for supported versions and project confinement.
4. Reuse one compatible official plugin or Skill installation. If absent, follow [official Skills](official-agent-skills.md) for a project-scoped upstream install; avoid duplicate triggers and overwriting managed/user-edited Skill directories. Inspect the current upstream source/licence and record its revision or explicitly mark that pin unverified. The repository's older vendored add-on is not a claim of upstream currency or redistribution clearance.
5. Invoke `remotion-production`, then the discovered official `remotion-best-practices` router and `remotion-markup`; add `remotion-render`, `remotion-studio`, `remotion-docs`, `remotion-license` or other Skills only for the selected work. Use the actual host-discovered identifier, including plugin namespace when present. Record the tool result and returned Skill root. A file on disk, a discovery listing, a failed invocation and a successful invocation are different evidence. Reading SKILL.md in a shell is reference use, not a Skill invocation. Follow referenced files only as needed.
6. If newly installed Skills are not discoverable, inspect host loading guidance. In Claude, ask the user to run a necessary slash command or start a fresh worker only when that is actually needed; never claim an unobserved `/reload-skills` succeeded. Recheck invocation before assigning production. Native sitting `eb812ab3` demonstrated immediate discovery without a recorded reload, not a guarantee for every host/plugin.
7. Motion returns a small setup record at `media/specs/remotion-setup.md`: selected renderer; authorization reference; new/existing/upgrade decision; registry result/time; declared and installed versions plus lockfile; licence-record path; browser/FFmpeg checks; Skill source and installed/discovered/invoked/used evidence; Element decisions; exact failure or unverified boundary. Chris reads it before accepting production readiness. This record supplements the existing validators; it is not a replacement contract or automatic approval.

## Director selects Elements, Motion adapts them

[Remotion Elements](https://www.remotion.dev/elements) are editable React components, not one package to install wholesale. Consult the current catalog for the approved concept. The director chooses a small shortlist and records an include/adapt/skip decision, its shot/cue, creative reason, required dependencies/assets and review needs. Selecting none is valid when the original technique fits better. Do not ask the user to browse technical components unless their preference is genuinely required.

| Brief need | Candidate category to inspect | Reason to skip |
| --- | --- | --- |
| Approved numeric evidence | Number counter or chart | Numbers or claims are not approved, or a static label is clearer |
| Speech or typography | Caption/text animation | No speech, poor reading time, or conflicts with approved font hierarchy |
| Material atmosphere | Background/overlay | Distracts from signature action, weak contrast, excessive motion |
| Character acting/loop | Custom frame-driven scene, with an Element only if useful | Catalog effect cannot preserve pose continuity or cause and effect |

For each included component, inspect the actual source and its terms, record URL and commit/version or source hash, retain notices, check any font/image/third-party licence separately, and list adaptations. Visible source or a Use button does not establish universal MIT rights or that every dependency is free. Do not copy catalog media into the shared technique library.

Studio can copy an Element's source and install its dependencies through its UI; its confirmation/delivery result is not proof that installation or host Skill loading succeeded. For agent-only work, adapt inspected source into the project using the documented component API; do not invent a headless Element-install endpoint. Install only selected dependencies locally, with every `remotion`/`@remotion/*` package at the same exact selected version (no `^`); inspect non-Remotion peer requirements. Check the final package/lockfile and composition import/build.

Map preview dimensions, duration and fps onto the approved canonical timeline; the catalog preview is not a new timebase. Keep deterministic frame math, font/asset readiness, Sound revision/fingerprint and the proof/export gates. View the component in context, including transitions and reduced-motion/static alternatives where applicable. Source or timing changes require renewed proof. Record an omitted component's reason instead of claiming Elements were used from catalog research alone.
