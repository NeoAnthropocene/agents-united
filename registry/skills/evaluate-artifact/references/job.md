# Fixed review job

The caller prepares job.json under an absolute review root disjoint from the candidate, selected source registry/checkout, read roots and managed/protected inputs. It saves check logs/receipts under checks/<id>.{raw.txt,receipt.json}; the checker writes stdout/stderr only. Preserve all original task values and acceptance criteria, including explicitly unknown values.

## How the caller builds it

The caller, never the read-only evaluator, builds the job with the installed builder: `node <installed-skill>/scripts/review-job.mjs --spec <absolute spec.json>`. The spec holds only the caller's decisions; the builder computes the candidate inventory, roles fixed by the kind, digest and subject paths, every loading, guard, profile, tool-policy, library-lock, guide and snapshot pin, the shared core/contract pins of a claude-agent, the template pin of upstream intent, the runtime and checker pins, minimal read roots and the rubric applicability. It writes `checks/<id>.raw.txt` and `checks/<id>.receipt.json` for each check the caller ran, byte-identical copies of those two files and of each extra evidence file into the read folder (a sibling of the review root): a check output is copied as `<check id>.raw.txt` and `<check id>.receipt.json`, an evidence file as `evidence-<evidence id><its extension>` (the input id itself is unchanged), so two evidence files with the same name never collide and no copy takes a reserved device name such as `con`; the evaluator cites a copy by its input id and that file name, and job.json last. Each output is written as a new file and renamed over its destination, so an existing file, hard-linked or not, is never opened for writing; the temporary file has a short random name and is removed on any failure. If a write fails after earlier outputs were already moved into place, the refusal says that outputs were partly written and names the review root and the read folder; job.json, written last, is then absent or from an earlier build. If the candidate changes or a file vanishes after every output, job.json included, was written, the refusal says that outputs were all written and that the job there must not be used. It prints one line of JSON (`status: job-written`, the job pin, `jobDigest`, `candidateDigest`, counts) or a refusal with a reason and exit 1. Run check-review.mjs --job on the written job afterwards; that checker stays the authority.

Before each check runs, take the candidate digest with `node <installed-skill>/scripts/review-job.mjs --digest --spec <absolute spec.json>`: it prints the current digest, computed exactly as the job's, and writes nothing. Give that digest as the check's `candidateDigest`.

What the builder verifies: each executed check's pre-run digest equals the current candidate digest (otherwise the candidate changed after the check ran, and it refuses), its status agrees with its exit code (`passed` only with 0, `failed` only with another code), and its saved output exists. What it only records as the caller's statement: that the command ran, with that exit code and that output. Neither the builder nor the checker runs a check or authenticates its execution; the checker reports `executionProof: unverified`. The builder's only child process is `git -C <checkout> rev-parse --verify HEAD`.

It refuses, before writing anything: relative or linked paths; an output root overlapping an input; a HEAD other than `source.head`; candidate bytes as evidence or output; any input file (the spec, a saved output, an evidence file, an executable) that is also one of its destinations, compared by physical path (the real path of the deepest existing folder, so another spelling of one folder such as an NTFS short name is the same place; overlaps of roots are compared the same way), so keep the spec and saved outputs outside the review root and the read folder; a destination that is a link or a folder; and a job the checker's own rules would refuse, including a validator or provenance prerequisite that is not required. Path containment compares exact case on a case-sensitive filesystem; a refusal also uses the checker's case-folded comparison, so the builder can refuse what the checker accepts, never the reverse. The managed Host folder rule reads the root as given and its physical spelling, as `check-review.mjs` does.

Spec keys: `version` (1), `id`, `intent` (`local`/`upstream`), `authoringHost` (`observedVersion` or `unverifiedReason`), `subject` (`kind`, `identity`, `definition` for a claude-agent, `target` for a claude-agent, a rule, a workflow or a Claude Skill, given as `observedVersion` or `unverifiedReason`), `objective`, `fixedValues` (optional), `constraints`, `acceptance`, `source` (`checkout`, `head`, `registry`), `roots` (`candidate`, `review`, `readFolder`, optional `managed`, `protected`), `roles` (relative path to `subject`/`support`/`preservation-only` for every file the kind does not fix: a Skill fixes `SKILL.md`, a shared pair fixes `core/<definition>.{contract.json,core.md}`, a rule fixes `<identity>.md`, a workflow fixes `<identity>.js`), `checks` (`id`, `required`, `status` `passed`/`failed`/`unavailable`/`not-run`, `command` with `argv`, `cwd` and optional `executable` (default: this Node; a missing executable of an unperformed check makes its existing parent folder a read root), and only for `passed`/`failed`: `candidateDigest`, `exit` and `output`, the saved combined output), `evidence` (`id`, `kind` `provenance`/`validator`/`source`/`baseline`/`diff`/`observation`/`rule`, absolute `path`, optional `required` (default true), `sections`), `provenance` (`disposition`, `author`, optional `unresolved`, `notices` as candidate paths, `upstream` with `sourceId`, `licenceId`, `comparisonId`, `noticeIds` naming evidence ids), optional `rubricReasons` (criterion id to reason; applicability is never the caller's) and optional `budget` (any of the numeric limits below, each at most its maximum; every limit not given is the maximum; the builder applies the chosen limits while it inventories, collects evidence and writes, and the job carries them). Provenance evidence is every evidence file of kind `provenance` plus the upstream ids.

Each receipt is exactly eight keys, compared by the checker: `version` (1), `id`, `kind` (`deterministic`), `command` (the job's), `candidateDigest`, `status`, `exit` and `raw` (the raw log pin). Write paths in the platform's own absolute form.

Select one kind: shared-pair (host neutral), skill (portable or declared Claude target), claude-agent (explicit Claude CLI/workspace/native target), workflow (one native Claude workflow script `<identity>.js`, its explicit Claude target required, no shared definition; the builder pins the orchestration guide and the workflow page of the library, shared semantics is not applicable, and the job needs exactly one subject file and a required, executed check with the id `workflow-check`, both of which the builder and the checker require; the check records the command `node <checkout>/dist/cli.js workflow-check --artifact <path>` with the path of the registry copy, `<registry>/hosts/claude/workflows/<identity>.js` or `<checkout>/registry/hosts/claude/workflows/<identity>.js`, which must be a regular file with the same bytes as the candidate's `<identity>.js` (the candidate's own path is refused: workflow-check passes only at `registry/hosts/claude/workflows/<name>.js`), and its raw-log and receipt inputs carry the hashes the check record pins; the checker reads the registry tree, so a pass is recorded on the registry copy, and this is record consistency, the command stays the caller's statement; a workflow review covers the native Claude script only, Cline and Antigravity delivery are not covered, and an agent type the check listed as unresolved is not verified) or rule (one canonical rule file `<identity>.md`, its explicit Claude target required, no shared definition; the builder pins the rule guide and the rule page of the library, and shared semantics is not applicable; exactly one subject file, and a required, executed check with the id `rule-check`, both of which the builder and the checker require; the check records the command `node <checkout>/dist/cli.js rule-check --artifact <path>` with the path of the candidate's `<identity>.md` or of `<registry>/rules/<identity>.md` only when that registry file exists and has the same bytes as the candidate's `<identity>.md` (the sha256 the job pins for the subject), and its raw-log and receipt inputs carry the hashes the check record pins; this is record consistency, the command stays the caller's statement). A rule review covers Claude and Cline delivery of the canonical rule; Antigravity delivery is not covered. The Host running the evaluator is separate from the artifact's target. Record observed versions or explicit unverified reasons; the profile minimum/reviewed baseline is not an observed runtime.

Use the closed job schema. Declare every candidate file, including unchanged notes, with path/length/SHA-256 and subject/support/preservation-only role. Give each selected input a unique ID, kind, exact pin, sections, disposition and required/optional meaning. Include installed entry/receipt, every required support/rule/role/guard edge, executable schemas/rubric, relevant guides/snapshots/observations, profile/policy/lock, provenance and caller-selected validator declarations. Missing reviewed tools are unavailable prerequisites, not permission to invent a replacement.

The caller pins the physical Node>=24 binary and actual installed checker. Executable hashing has a separate <=128 MiB cap; binaries are not model-review text. Candidate bounds are <=32 files/1 MiB total/256 KiB each; ordinary evidence <=64 files/8 MiB total/1 MiB each. The result is <=256 KiB, <=32 findings and <=16 open items. At most six offline caller checks, 600 seconds and 512 KiB of complete raw logs are permitted per job. Smaller declared limits apply. Larger work needs explicit partitioning or a reviewed budget.

Canonical JSON sorts object keys recursively and preserves array order; the candidate digest uses sorted actual path/kind/length/hash inventory. Digests neither authenticate a sender nor prove a model read the files. Byte checks observe drift without promising an atomic snapshot or excluding concurrent writers. No job, ledger remainder or receipt authorizes live spending, publication or repair.
