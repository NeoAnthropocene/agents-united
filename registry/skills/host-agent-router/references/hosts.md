# Host details for host-agent-router

This file keeps what is true of the hosts apart from what a particular machine had: everything above "Machines seen" is about the hosts,
"Machines seen" lists the machines. Observations are per machine: what one machine showed says nothing about another, so each is dated
and attributed there. Nothing below starts a model: every limit readout is a local command or an account endpoint the host calls itself.

## How headroom is read

| Host | Source | Notes |
|---|---|---|
| Claude | `claude -p "/usage"` (text) | Rows `Current session` (5-hour) and `Current week (all models)`, as percent used. A model-specific weekly row counts only for that model family. |
| Antigravity | `agy -p "/usage" --output-format json` | Groups with `5h` and `weekly` buckets (`remaining_fraction`). The group is chosen by the entry's own `quotaGroups` or else by model prefix (`quotaGroups` in the config); a model may draw on several groups, and the smaller headroom of them counts. Gemini 4 Argon has a weekly bucket only. Hydrogen is charged to Gemini Models through the prefix: confirmed by the maintainer in the Antigravity app on 2026-11-13 (the Gemini Models quotas went down after the Hydrogen runs), and the description of the Gemini Models group names it in the readout of 2026-11-19 (see "Tiers, efforts and skills"). |
| Codex | `codex app-server`, JSON-RPC `account/rateLimits/read` | `primary` is 300 minutes (5-hour), `secondary` is 10080 (weekly). If that fails, the newest session log is used and a window whose reset time has passed counts as unused. |
| Cline | none | ClinePass has 5-hour, weekly and monthly limits, shown only on the web dashboard. Headroom is unknown, so Cline is tried first as configured, and a refused request falls through. See "Cline quota" below. |

## What `run` executes

| Host | Command shape | Prompt via |
|---|---|---|
| Claude | `claude -p --model <id> --effort <e> --permission-mode plan\|acceptEdits [--allowedTools Bash(<cmd>:*)... --disallowedTools Bash(<cmd>:*)...] [--max-budget-usd <n>] --output-format text` | stdin |
| Codex | `codex exec -m <slug> -c model_reasoning_effort="<e>" -s read-only\|workspace-write --skip-git-repo-check --color never -C <cwd> -` | stdin |
| Antigravity | `agy -p <prompt> --model <slug> --mode plan\|accept-edits [--sandbox --settings '{"permissions":{"allow":["command(<exact line>)"]}}'] --output-format json` (the effort is part of the slug) | argv |
| Cline | `cline [--config <isolated dir with the hook> --data-dir <real data dir>] -P cline-pass -m <id> --thinking <e> --json [--plan] -c <cwd> -- <prompt>` | argv |

`read-only` is Claude `plan`, Codex `read-only`, Antigravity `plan`, Cline `--plan`. `edit` is `acceptEdits`, `workspace-write`, `accept-edits`
and Cline's act mode. No `--dangerously-*` flag is ever passed. On Windows, Cline (and an npm-installed Codex) starts as `node <package entry>`, never through its
`.cmd` shim, so prompt text is not reparsed by `cmd.exe`. The contract every edit run carries, and what enforces it on each host, is in
[worker-contract.md](worker-contract.md).

The hosts differ in what they do without a rule. Codex `workspace-write` is a sandbox. Claude and Antigravity deny every command that is not
allowed. Cline's act mode allows everything, shell commands included (its docs say the CLI has no allow or deny list), so the router gives
each Cline run a `PreToolUse` hook (`guardDecision`) in a throwaway `--config` directory. `--config` alone loses the login (Cline answers
"Unauthorized"), so the real `--data-dir` is passed too; the `--hooks-dir` flag and `CLINE_HOOKS_DIR` did not load a hook in tests. A
cancelled call ends the run with exit 0 and `finishReason: "aborted"`, so the router judges the finish reason and the blocked list, not the exit code.

Cline runs with `--json` so that `output` is the final answer and not the activity log: plain text mode printed 4.6k characters of thinking
and tool calls before a one-file task's report. A run that never reaches its final line (killed, crashed) comes back as a short `partial`
summary (events, iterations, tools used, last words) and not as the raw stream, which filled the 200,000-character cap. Cline's refusal path,
seen once (an unauthorised run): exit 1, a JSON `error` line on stderr, and a `run_result` with `finishReason: "error"` carrying the message.

Antigravity (headless) has its own quirks, all seen live. A command that is not allowed is denied and **ends the run with exit 0, status
SUCCESS and an empty response** (the message is on stderr; `--output-format json` adds `denied_actions`). Its allow rules match an exact command
line or a bare program name (`command(npm test)`, `command(npm)`); wildcards of every form tried are ignored. The router therefore allows exact
lines, tells the worker to run them exactly, and treats an empty or denied exit-0 run as a failure that did no work.

A model can lack an effort on an account: the pool lists the efforts of each Codex model (Luna has no `ultra`), and an asked effort that the chosen model does not list is not applied (a note says so).

Hydrogen's quota group: the `/usage` readouts of 2026-11-06 (the capture in the repository) and of 2026-11-13 (second machine), with no model started, named three groups, Gemini Models (described as Gemini Flash and Gemini Pro; weekly and 5-hour buckets), Claude and GPT models (weekly and 5-hour) and Gemini 4 Argon (a weekly bucket only), and none of their descriptions named Hydrogen. That Hydrogen counts in Gemini Models and that only Argon has its own group was confirmed by the maintainer in the Antigravity app on 2026-11-13 (the Gemini Models quotas went down after the Hydrogen runs). The readout of 2026-11-19 replaces the earlier description of the group: the description of Gemini Models now names Gemini 4 Neon, Gemini 4 Hydrogen, Orchestrator (Neon) and Gemini 3.8 Flash, so the `gemini-` prefix in `quotaGroups` charges all of them to Gemini Models, and Argon to its own group. If `/usage` ever shows a group of its own for Hydrogen, add a `gemini-4-hydrogen` entry to `quotaGroups` in your config.

`high` on Cline is for genuinely hard problems only: it uses a large share of the 5-hour quota. Keep other high-tier work off Cline with `--host <host>` (repeat it for a list; on `run` a fall-through stays inside the list) or `--pin-host <host>` (`run` only, one host, no fall-through; not together with `--host`), or by moving `cline` down `priority` in your config. (Cline's `high` is `cline-pass/kimi-k3.1-pro`; its share of the quota is the maintainer's report, not something the router can measure, because Cline has no usage readout.)

Router exit codes: 0 ok, 1 the run failed, 2 no usable host or side, 3 refused inside a routed worker, 64 usage error (a wrong flag, a missing or empty prompt, `--pin-host` with `--host`, an invalid config file: nothing ran).

An effort inside a tier is an optional `efforts` map on each model entry of the tier in the config. The key is the name given to `--effort`; the value is either a plain effort value (a host whose effort is a flag, for example `"max": "max"` for Codex; the model stays) or `{ "label", "model", "effort" }` (any of them overrides the entry's; a host whose effort is part of the model name, Antigravity, needs a `model`). The entry's own default effort is always a valid name. The user config merges into it key by key: a tier given with only `efforts`, `effort` or `label` changes the first model of the shipped list, so one effort can be changed or added without restating the others. An entry with `"fixedEffort": true` (the Orchestrators) takes no effort: with `--effort` it keeps its model, its effort reads `fixed`, and the candidate carries an `effort_note` that says the effort was not applied and why. With `--effort`, a model whose entry has no such name keeps its default and the result carries a note (`effort_note` on its candidate and in `ran`); a name that no model of the tier on any host in scope offers (the fixed ones offer none) is a usage error. `ran` always shows the model and effort that were used. Antigravity ships effort entries by slug, Codex by plain value (`low`, `medium`, `high`, `xhigh`, `max`); the other hosts' effort values are not listed offline, so none is claimed here.

`--skill <name>` (up to three, `run` only) puts the `SKILL.md` text of a sibling skill folder into the worker's prompt, after the contract, under a heading of its own: a git worktree does not inherit installed skills. The folder is found beside the router, in `registry/skills/` or in the installed skills folder. A skill is limited to 20,000 characters (front matter stripped), and `--dry-run` lists what was attached and the size of the prompt each host would get. Cline and Antigravity take the prompt as a command-line argument, so a prompt over about 30,000 characters is skipped for them on Windows (the process limit is about 32,000) and over about 120,000 on Linux; Claude and Codex take it on stdin. This size guard and the skill text itself were not run live.

## The model pool

Which models an account can use depends on its plan (the tables above give the vendor's statements, read on 2026-11-19 from `antigravity.google/docs/plans`, `antigravity.google/docs/models` and `learn.chatgpt.com/docs/models`). The router does not keep a table of plans. Before it chooses, the probe of each host and side reads the list of models the logged-in account can use, once per invocation and never per attempt, and the plan chooses from that list.

| Host | Where the list comes from | Seen |
|---|---|---|
| Antigravity | `agy models`: one `slug<TAB>display name` line per model, nothing else on stdout (the "Fetching available models..." progress line goes to stderr). The vendor says it shows every model ID available to the account (`antigravity.google/docs/models`). | On this machine on 2026-11-19 (agy 1.5.11, then 1.5.12): 23 lines: Neon (4), Argon (3), Hydrogen (4), the two Orchestrators, Flash (3), Claude Opus 5.5 and Sonnet 5.5 (3 each) and `gpt-oss-120b-medium`, which the vendor schedules for removal on 2026-11-18; no Carbon model of any kind, so no Orchestrator (Carbon). |
| Codex | the app-server request `model/list` (`limit` 200, picker-visible models only), the protocol the router already speaks for limits. Each model comes with the efforts it supports. The repository's snapshot (`host-library/codex/pages/orchestration/app-server.md`) describes the answer. | On this machine on 2026-11-19: `gpt-6.2-sol` (default), `gpt-6.2-astra`, `gpt-6.1-terra`, `gpt-6.1-sol`, `gpt-6-astra`, `gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, with the efforts low, medium, high, xhigh, max and ultra (Luna has no ultra). The exact request the router sends (`limit` 200) was not run. `codex debug models` prints the catalog with no plan field, so it is not used. |
| Claude, Cline | not read. Their tiers have one model each; Cline's id is already checked against its installed catalog before a run. | |

**Choosing.** Entries are tried in order. One that is not in the list is passed over, and the plan names it with the reason (`skipped_models` on the candidate: "not in the account's model list"); one whose quota group is below the headroom floor is passed over the same way. The first entry left is the model; the rest are kept as `alternates`. A tier with no entry in the list is unavailable on that host and side: the plan skips them with the reason and the next host is tried. `pools` in the plan says where each side's list came from (`cli`, `config`, or `unknown`). If the list cannot be read (the command fails, the answer does not parse, or the Codex list has a second page, which would drop real models), the router behaves as before pools existed: it uses the first entry that has a model id, the plan says the pool is unknown, and nothing blocks. Orchestrator (Carbon) is the one entry without a model id in the config (slug not established: no Carbon model was listed), so the entry is matched against the display names in the account's list, case-insensitively, as "Orchestrator (Carbon)", and the slug is taken from there. That matching was tested only on a fixture with an invented slug. With an unreadable list that entry is passed over.

**A refused model.** When a run ends with `failure: model`, the next model of the same tier runs on the same host and side before any other side or host. `attempts` lists each try. This relies on the text `classifyFailure` already matches ("unknown model", "invalid model", "model ... not found / not available / not supported"). What `agy` prints for a model that exists but is not on the account's plan, and for a quota refusal, is not documented, so no extra wording was added.

**Quota groups.** Orchestrator (Neon) belongs to Gemini Models: the description of that group in the `/usage` readout of 2026-11-19 names it. No group description names Orchestrator (Argon). The config therefore requires headroom in both Gemini Models and Gemini 4 Argon for it (`quotaGroups` on the entry): this is a cautious assumption, not an observation, and it can make the router pass over Orchestrator (Argon) when only Argon is short. Orchestrator (Carbon): its group is not established either; the entry names Gemini Models, the group of Hydrogen, which the vendor says implements for every Orchestrator; add the group the readout shows for it, if there is one, to `quotaGroups` of the entry in your config. The headroom of an entry is the smaller figure over all its groups.

**Override.** If the list cannot be read on a machine, give the host an explicit `pool` in the user config: `"hosts": { "codex": { "pool": ["gpt-6.2-sol", "gpt-6.1-sol"] } }`. It replaces the list the CLI gives (the CLI is then not asked), `pools` shows `config`, and `null` clears it. A display-name entry cannot take its slug from it, so Orchestrator (Carbon) needs the real list or a `model` in your own entry.

**Not built.** Probing a model to learn whether the plan has it (that would spend the allowance), a table of plans, and any text match for a "not on your plan" refusal beyond what `classifyFailure` matches today: the wording of that refusal is not established. Also not built: skipping, on a later side, a model that an earlier side of the same host refused.

**Not run live.** The refused-model retry, the `model/list` request, the probes of both hosts in this version, and a run on an Orchestrator model were not run on a host (no model was started to build this version); they are held by tests on fixtures shaped like the real outputs. `router.mjs models` runs `agy models` and reads a Codex cache file; it sends nothing to a model.

## Editing: what the router does around a run

For `--access edit` the router fingerprints the working directory (path, size and mtime of every file, skipping `.git` and `node_modules`,
plus the git HEAD) before the first attempt and after each one. It returns `changed` (created, modified, deleted, `head_moved`). Inside a git work tree
the paths git ignores (build output, a scratch folder, found with one `git check-ignore --stdin -z` call that has a time limit and no shell) are listed apart
as `ignored`: their count and the ten biggest top-level folders, so that a build does not bury the one modified file. Nothing is hidden: `count` still
includes them, and a failed attempt that changed only ignored paths still stops the fall-through. Outside a work tree, or when git fails or is absent, the
lists are as they were. A failed
attempt (limit, login, model, missing binary, timeout, or an exit-0 run that was empty or had a command denied) hands over to the next host only
if the tree is exactly as it was; if files changed, or the directory is too large to compare (50,000 files), it stops with `stopped` and no other
host starts. A real task failure, a guard block or an unfinished Cline run never hands over. Read-only runs are not fingerprinted.

Codex edits go to WSL when that side is usable (`editSide` in the config): on the first machine its Windows sandbox started in `C:\` without
`node`, so `git` found no repository and tests could not run, while the WSL sandbox worked and kept `.git` and everything outside the workspace
read-only. `editSide` only puts that side first; with no usable WSL side (the second machine) the router uses the Windows side, which has not
been shown to work for edits there (see "Machines seen").

## Crossing between Windows and WSL

The script stages a copy of itself and a payload file in the Windows temp directory (visible from both sides as `C:\...` and `/mnt/c/...`)
and runs the other side's node on it. From Windows it uses `wsl.exe -d <distro> --exec bash -lc 'exec node ...'`; `--exec` matters because
`wsl.exe -- <command>` runs the line through the outer shell, which expands `$0` and `$@` itself. A user profile path with spaces under WSL
is untested.

Inside WSL the line finds `node` in this order, and the first hit runs the staged script (no interactive shell is used: it can print job-control warnings and run prompt code):

1. `wslNode` in the config (a Linux path such as `/opt/node/bin/node`; optional, default `null`, like `wslDistro`); it must be an absolute path with no control characters or backslashes, else the config is a usage error.
2. `node` on the login shell's PATH.
3. nvm: `${NVM_DIR:-$HOME/.nvm}/nvm.sh` is sourced quietly when the file exists, then `node` again. nvm is the usual way node is installed on WSL, and it puts `node` on the PATH from `~/.bashrc`, which a non-interactive login shell does not run to the end.
4. File tests, no globbing: `$HOME/.volta/bin/node`, `$HOME/.local/share/fnm/aliases/default/bin/node`, `$HOME/.asdf/shims/node`, `$HOME/.local/bin/node`.

Nothing found: the line prints `node: not found` and exits 127, and `plan`/`run` show the skip reason `WSL has no node (the config key "wslNode" can name it)`; install node there, or set `wslNode`. Once the script runs inside WSL it looks for a Host's executable on PATH, then in the folder of its own node (where the npm globals of an nvm node, such as `cline`, live) and in `~/.local/bin`, and it appends its node's folder to the PATH of every Host it starts. Windows resolution is unchanged.

## Budget cap

`run --max-budget-usd N` (or the config key `maxBudgetUsd`, a number or `null`; the flag wins) asks for a spend cap of N US dollars, a positive amount with at most two decimals. Only Claude has a flag for it: the router adds `--max-budget-usd N` directly before `--output-format`, and Claude's own help says it is the "Maximum dollar amount to spend on API calls (only works with --print)" (read from `claude --help` on 2026-11-16; the library's `host-library/claude/changelog.md` mentions the flag in several fixes, for example line 1400, and has no page that describes it). The help of `codex exec`, `cline` and `agy` shows no budget or spend flag, and the library has no page on one for them (its Antigravity changelog names a `BudgetConfig` in the SDK, which is not a flag of the `agy` command), so nothing is added to their command lines. Every attempt in the result and every `would_try` entry of `--dry-run` then carries `budget`: `{ "usd": N, "applied": true, "flag": "--max-budget-usd" }` for Claude, `{ "usd": N, "applied": false, "reason": "<host> has no budget flag; the run is bounded by --timeout only" }` for the others, and a run that ended on such a host adds the note `no budget cap applied: <host> has no budget flag`. Without a cap there is no `budget` field at all. `--require-budget` (it needs a cap) skips the hosts without a flag with the reason `no budget flag (--require-budget)`; when nothing is left the run ends as "no usable host/side". A run on the other side carries the flag in the command line it sends with the payload; the far side adds nothing.

## Cline quota

Checked 2026-11-07 against Cline 3.0.74 and the docs (`docs.cline.bot/cli/cli-reference.md`, `getting-started/clinepass.md`): no `cline` command or flag reports ClinePass usage, and the docs say to open the web dashboard. A `--json` run emits `usage` events with token counts and a `totalCost` of 0 (flat subscription), and `cline history --json` keeps the same per run, so consumption is visible and what is left is not. Asking a model is not a source either: one low-effort `--plan` run in an empty directory, asked to answer only from session facts, replied `UNKNOWN` (9,483 input and 4 output tokens). The account REST calls in Cline's own code (`/api/v1/users/me/plan`, `/balance`, `/usages`) need the stored account token, are undocumented for ClinePass windows, and would be a network call the script does not make; they were not tried.

What Cline does say is a refusal, in its provider code: `You have reached your … ClinePass limit … Please try again later.`, `Free limit reached on model …`, `No access to ClinePass subscription models yet. Subscribe to ClinePass …`, `Organization accounts cannot use ClinePass subscriptions …`. `classifyFailure` matches these, so the first two fall through as `limit` and the last two as `auth`. They are matched from Cline's source, not from a refusal seen live.

## Known limits

- Where the same account is signed in on both sides, the figures match and the side choice is a tie; the current side wins.
- Cline works only where its install runs. In WSL it can resolve to the Windows install and fail (`--version` exits non-zero), so that side is skipped.
- Antigravity may be installed on one side only: `agy` in WSL only on the first machine, on Windows only on the second.
- Parallel `run` calls each read the limits independently and reserve nothing.
- Antigravity matches an allowed command as a whole line, and its command line has a length limit (seen live 2026-11-15, three operator mistakes; the script now catches each before a worker starts; checked the same day: the refusal of (a) and the handling of (b) by replaying both briefs with `--dry-run`, and for (c) one live run on Antigravity, simple tier, `gemini-3.8-flash-medium`, with the single allowed line `node C:/<working directory>/probe-colon.js`, which ran and returned its output with exit 0; a first attempt of that run was denied for a `read_file` action, not for the command; a drive path inside a Claude `Bash(...)` rule has not been run live): (a) `--allow-cmd "node node_modules/vitest/vitest.mjs run"` was meant as "any vitest run", but the worker ran the acceptance line from the brief (`... run tests/x.test.ts --configLoader runner ...`); the host matched the whole line, denied it and ended the run in 12 to 34 seconds with `failure: "denied"` and nothing done. The router now refuses an edit run (exit 64, also under `--dry-run`) when Antigravity is a candidate and the brief holds a longer line that starts with an `--allow-cmd` value, naming both lines; `--allow-prefix-ok` turns the refusal into a note. Only the lines the operator passed are checked, not the configured defaults and not a one-word program name; the check is a heuristic over backtick spans and line starts, and the error text says "command line", not "prefix". (b) `--dry-run` exited 0 and the real run was then skipped, "the command line would be 32404 characters, too long for this host on windows (limit about 30000)", with `ok: false` and no `failure` code; each allowed line was carried again with the full path of its program, about 5,000 characters for eight long lines. A dry run already marked each such attempt with `skip`; it now also adds a top-level `notes` entry when every listed attempt is too long, a real run that skips every candidate for length reports `failure: "too_long"`, and on Windows the full-path duplicate of an allowed line over 120 characters is left out, longest first and only as far as needed, with a note that counts them. (c) `--allow-cmd "node dist/cli.js skill-check --artifact C:/work/x ..."` was refused for its colon, so no command with an absolute Windows path could be allowed. A colon is now accepted only as a drive prefix (one letter, a colon, then `/` or `\`, at the start of a word), a backslash only inside such a path, and `\` (a UNC path) stays refused; `--allow-cmd-file FILE` reads one line per line from a file. Claude takes the line in `Bash(<line>:*)` and Antigravity in `command(<line>)` inside JSON; Cline and Codex take no allowed lines.
- Antigravity's sandbox hides the user profile, so a worker cannot use a temp folder inside it (seen live 2026-11-15, three runs, medium tier, `--access edit`, one allowed command that printed `os.tmpdir()`, made a folder there with `mkdtemp`, then called `realpathSync` on it and `lstat` on each ancestor). (1) Unchanged: the temp folder was `<home>\AppData\Local\Temp`, `mkdtemp` worked, `realpath` failed with EPERM and the `lstat` walk failed with EPERM at `<home>\AppData\Local`; test suites that resolve or walk the temp path failed for that reason alone (four times that day, 98 failures of 133 in one case). (2) With `TEMP` and `TMP` set in the environment of the router process to a folder inside the working directory, the worker's command saw them and `mkdtemp`, `realpath` and the walk all worked. (3) The same with a folder outside both the user profile and the working directory. So the environment of the process that starts `agy` reaches the commands the worker runs. The script now does this for an Antigravity `--access edit` run whose default temp folder (`TEMP`/`TMP` on Windows, `TMPDIR` or `/tmp` elsewhere) lies inside the home folder: it sets `TEMP`, `TMP` and `TMPDIR` on Windows and `TMPDIR` elsewhere, in the order `workerTemp` from the config, a new folder beside the working directory (when that is outside the home folder), a new folder inside the working directory. The folder is made on the side where the host runs, removed after the run whatever its outcome, never counted in `changed`, and named in `notes` without its path; `--dry-run` shows the choice and makes nothing. Status: re-run live with the fix the same day, twice, on the medium tier (`gemini-4-hydrogen-medium`), environment untouched: the same probe then reported a temp folder outside the home folder with `mkdtemp`, `realpath` and the walk all working; and one real test file that builds its fixtures under the temp folder ran inside the sandbox with 152 passed and 2 skipped of 154 (one more skip than outside the sandbox: a test that needs to create a link). Both results carried the note about the temp folder beside the working directory, `changed` was empty and the folder was gone afterwards. Not run live: the in-directory placement, a configured `workerTemp`, the WSL side.
- Failure classification is a text heuristic over the host's error output. It only decides whether the next candidate may run, never whether a run succeeded.
- One observation, cause unknown: Cline started with a model id that does not exist (`cline-pass/does-not-exist-xyz`) printed nothing and was still running after more than five minutes, ignoring `-t 60`. Only the router's own timeout bounds a hung run: it ends the process tree and reports exit 124, a `timeout` failure. The timeout now follows the tier (`timeoutSeconds`: simple 300, medium 900, high 1800; `--timeout` overrides). Observed durations: simple edits 16 to 45 s, a medium bugfix 21 s, a 5-module feature 146 s, a high-tier design task 60 s, so each default is several times the longest run seen in its tier. The wrong-model-id cause is closed separately: before a Cline run starts, a `cline-pass/...` id that the installed Cline's catalog does not list is refused as `failure: model` (the catalog is read from its package; if unreadable the check is skipped).
- 2026-11-15: a read-only Antigravity run ended in 10 seconds with `failure: "denied"` and no output, because the worker ran a shell command to search files; one denied command ends the run. The worker's prompt now says that no shell command is available in a read-only run. Re-run live the same day on the medium tier with one search task: without the note the run was denied in 8 seconds; with it the run completed, and the worker reported that a read-only run has no tool to list a folder or search file contents, only one that reads a file by its path.
