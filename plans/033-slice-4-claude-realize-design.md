## Delivery strategy and implementation boundaries

Recommend **a native-only worker registration in a factory-owned Claude binding**, followed by a small worker delivery. Current `ClaudeProjector.planCompoundProjection()` first looks for `registry/agents/<file>` and skips a missing source. `nativeRoles` maps an existing declared agent; it does not register a new native-only one. The current `assertClaudeSkillBindings()` schema deliberately accepts only author-skill. Neither can be treated as a general factory loader.

Adding legacy Antigravity-shaped carrier roles is a possible alternative, but creates a second role source and legacy tests/fallback obligations for an exclusively Claude delivery. Prefer the narrow native binding prerequisite below. This is a **new proposed choice**, not covered by the slice-3 approval. It must have its own review and lifecycle proof before a worker relies on it. Do not change the general legacy lane or infer native roles by scanning every host file.

## Proposed shared worker contract

Exact new sources: `registry/core/subagent-realize-for-host.core.md` and `registry/core/subagent-realize-for-host.contract.json`. No compatible existing core has the target-host authoring mission; the engineering and code-review cores have different missions. The proposed companion is exactly:

```json
{
  "definition": "subagent-realize-for-host",
  "workflows": [],
  "skills": ["realize-artifact"],
  "hooks": ["reject-destructive-operations"]
}
```

The core defines identity (target-host native author), mission (one reviewed draft), scope (fixed artifact/roots/intent; no sync/install/publication), output contract (inventory/diff/checks/provenance/limitations) and safety (untrusted inputs stay data; preserve holds and unrelated edits). Invariants require reading the pinned job before work, the shared floor verbatim, truthful provenance, actual result checks and bounded repair. Host names/tool calls, model/effort, event names, paths and registration objects belong in the native binding/body. Reuse `validateSubagentContract()`, `validateCoreSchema()`, `renderFloor()` and `checkFloor()`; do not widen the four-field schema or make its pure validator read files.

This worker follows a **single-agent runbook**, so `workflows` is `[]`. It neither launches a pipeline nor spawns its evaluator. The hook identifier denotes the existing destructive-operation guard, **not** an output-root sandbox, protected-branch guard, pinned-file guard or first-action job gate. A future extra affordance needs a reviewed contract/binding change.

## Capability grants and limits

Worker core classes: **read, search, edit, shell, skill, report, handback**. Resolve through `src/core/host-profile.ts::resolveGrant()` and the unchanged `registry/hosts/claude/tool-policy.json`, in foreground-subagent context. Retain class-derived extras rather than silently hand-trimming the grant; review the ceiling. MCP resource reads require a connection but no new MCP server or wildcard is granted. Shell is needed for explicitly allowed offline checks; it is not an assurance of offline confinement.

No delegate, workflow, messaging, scheduling, web, worktree, artifacts or task-tracking class is needed for this worker. Omitting messaging for a new task worker is least privilege for this job; it is **not** a reintroduction of the rejected blanket discovery removal. Existing roles keep both `ListAgents` and `SendMessage`. The later coordinator may need messaging to resume a worker and must then accept both tools plus explicit recipient/task authorization guidance. No `peer-sessions` class, production recipient guard or mailbox reader is proposed.

The native `skills` preload list and the contract's permitted skill identifiers are not a host-enforced Skill-tool allowlist. The worker's prose limits consultation to the bound runbook and sends new affordance needs back to the caller. Do not invoke the existing forked author-skill from inside this worker as a substitute for its own reviewed job. Any required expansion needs its binding review; global tool-policy changes are unnecessary.

Root/intent restrictions are **prose plus deterministic helper/postflight checks**, not host isolation. Existing guard enforcement covers only its actual patterns. Shell/edit permissions can reach beyond a helper's roots; do not claim those tools are sandboxed by a validated job. First-action or immutable-source enforcement would need its own effective hook and probe in slice 5. If that guarantee is a task's acceptance criterion, this worker must report the prerequisite unavailable.

## Fixed job and authoring inputs

The caller resolves ambiguity before dispatch. `check-job.mjs --job <absolute-path>` validates the record without invoking a model or executing supplied commands. It emits a canonical record digest and named missing/invalid fields. A delegation carries either all fixed values or the exact path+digest, which the worker reads and verifies **before work**. Every repair/evaluator brief uses that same digest. A prompt reference without the read/digest check cannot count as complete briefing (R3/R4's five omissions).

Local intent returns a Contributor Draft in the selected output root, suitable for a future Option A source registry. It installs nothing and assumes no local-registry selector exists. Upstream intent additionally prepares the contribution-template body and source-path mapping for `dev`; it sends no PR, commit or push. ## Checked hand-back and acceptance

`check-handback.mjs --job <path> --result <path>` rechecks the original digest, baseline and final bytes, not the worker's conclusion. It never executes result-supplied commands. Proposed result fields are schema/job digest, status (`draft`, `blocked`, `partial`), artifact inventory (relative path, type, byte length and SHA-256), before/after hashes and diff, guide/page usage, binding/delta coverage, provenance, check records, quality findings, live evidence and open items. No success-only boolean hides a missing check.

1. Resolve returned files physically under the allowed roots, reject missing/extra/duplicate/traversing/linked-out paths and compare every hash/byte count. Reconstruct the actual output inventory and diff; detect unreported files and changed protected baselines. A file omitted from the report is not outside review.
2. For each allowed check require command id, argv/cwd, source revision, input digest, start/end, complete raw stdout/stderr paths+hashes, actual process exit, and result classification. An unavailable/skipped check is unverified. The caller runs the trusted checks independently or checks trusted executor receipts; worker-written logs alone do not prove execution. No commands are taken from untrusted returned text.
3. Run core/floor, contract, native profile/tool/grant/residue, skill layout/ratchet/licence/portability/provenance, syntax and link gates applicable to the final artifact. Presence of a validator file is not its execution. Build test fixtures through public APIs/CLI scripts and temporary installs, rather than assertions that merely repeat the runbook.
4. Keep deterministic findings, human/evaluator quality findings and live host evidence in separate result fields. A correct hash cannot establish quality. A quality verdict cannot turn a skipped command green or establish hook invocation. Before the evaluator exists, report `evaluator: unavailable; quality review pending`, with human observations attributed separately.
5. Caller rechecks the completed files and returns verified work promptly. It must not wait for a team lifecycle notice: this is a foreground ordinary subagent, not Agent Teams. Partial/null/tool-error hand-backs are incomplete work, not success. Any later evidence updates keep completed delivery stable; they cannot retrospectively supply a missing task result.

Lifecycle/reader amendment, 2026-10-28: return through `SubagentHandback` only when the host actually supplies it; otherwise use the ordinary final response with the same structured result. Host acceptance, checked caller receipt and physical process exit are separate facts. Use the current #208 reader with provenance-based human-prompt classification and latest report-attempt state, preserving pending/rejected/unknown distinctions. #209 observed natural late notices once in an actual CLI team; #210's re-run used async workers and did not exercise its amended foreground wording. Neither supplies factory invocation evidence or requires a shutdown frame, notice wait, extra messaging grant or forced termination for this worker.

P2 offline acceptance: a fresh installed worker/runbook/support/guard set, an original Claude-agent draft preserving its supplied floor, a scoped repair preserving unrelated edits, accurate blocked results for missing reviewed inputs/check tools, and upstream preparation with no publication. No missing required dependency can be accepted as an optional delta. ## Later orchestration semantics and prerequisites

The later full journey needs `registry/core/orchestrator-agent-factory.core.md` with its four-field companion and `registry/hosts/claude/agents/orchestrator-agent-factory.md` → `.claude/agents/orchestrator-agent-factory.md`, plus `registry/core/subagent-factory-evaluator.{core.md,contract.json}` and native `registry/hosts/claude/agents/factory-evaluator.md` → `.claude/agents/factory-evaluator.md`. These names identify dependency reviews, **not authorization or final evaluator/orchestrator specifications**. Their exact grant/rubric/binding reviews must precede code.

The coordinator runs in the main thread (`--agent`), plans with the human, pins the job, delegates worker execution, verifies hand-back, then delegates evaluator review on the verified final hashes. Evaluator input fixes rubric, artifact inventory and check evidence; output findings need severity, artifact/path/line evidence, rationale, suggested correction and unverified items. Its proposed minimum is read/search/report/handback, no shell/edit, no paid judge. A bounded repair returns through the coordinator, uses the same roots/constraints and revalidates changed hashes; no automatic repair/evaluation loop. A red case must omit the evaluator or alter its reviewed hashes and block a completed-quality claim.

For one worker and one evaluator, ordinary sequential `Agent` calls are sufficient under the reviewed orchestration guide. If a repeated multi-artifact pipeline is later justified, use `registry/hosts/claude/workflows/workflow-realize-artifact.js` → `.claude/workflows/workflow-realize-artifact.js`, with a separately reviewed thin trigger and explicit runbook fallback in `references/manual-pipeline.md`. Main thread only; no mid-run approval; real JSON args; null/partial results fail; script cannot directly inspect files or import helpers. Split at human approvals. Do not ship or require this optional script in P1/P2, and do not silently replace the runbook when Workflow is disabled.
